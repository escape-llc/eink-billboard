# Working on eInk Billboard

This file is for whoever (human or AI) is working **on** this repo. `CLAUDE.md` only imports it, so every agent reads the same rules.
The readme says what the project is and how to install a Pi; `docs/` is the documentation: `architecture.md` (layers, compositor, tasks, storage), `development.md` (running it, containers, the web API, metering, telemetry) and `pi-commands.md` (the Pi kit's commands). This file is the working agreement.
Process lives in its own docs, indexed in `CONTRIBUTING.md`: **`WORKFLOW.md`** (idea to merged) and **`SESSION_SUMMARIES.md`** (how a piece of work is written up afterwards).

## What this is

An e-Ink "billboard" server for Raspberry Pi (and Windows/Linux development): a Python task-based backend (threads + `asyncio`),
a FastAPI web API, and a Vue 3 / PrimeVue settings app. It is developed on Windows and Linux; keep both working.

## Commands

```
uv sync --frozen --no-group device         # install (Python 3.13)
uv run python -m unittest discover .       # all tests (about 2.5 minutes)
uv run python -m unittest python.tests.test_web_api   # the API tests (about 1 second)

# run the app (storage root is created and seeded on first start)
uv run python -m python.eink-billboard --dev --cors http://localhost:5173 --host localhost --storage ./.storage
cd app && npm ci && npm run dev            # web app on :5173

cd app && npm run build                    # type-check (vue-tsc), then the production bundle -> app/dist (served with --app)
cd app && npm test                         # web unit tests (Vitest + jsdom), src/**/*.test.ts
cd app && npm run lint                     # ESLint (eslint.config.js): the basic rule sets, no formatting rules
cd app && npm run e2e                      # build, then the browser tests (Playwright) against real servers
```

- `npm run build` runs `vue-tsc -b` first, which reports **zero** errors; keep it that way (a type error fails the build).
- The built app uses hash routes (`/#/settings`), and Vite's default layout: `index.html` and `public/` files at the root, bundles in `assets/`. The bundles are served `immutable` (their names carry a hash), everything else `no-cache` (`_mount_web_app`): an `index.html` with only a `Last-Modified` was kept by the browser, which ran the old app after an update. A tab that was open before an update still runs the old app until it is reloaded: the next page it opens asks for a chunk the update replaced, which is a **404** (a missing file under `assets/` is never the app's page, which a browser cannot run as a module: "Failed to fetch dynamically imported module"), and the app **reloads itself once** at that page (`StaleBuild.ts`, `router.onError`; the reload is marked in `history.state`, so a broken build does not reload for ever; not on `vite:preloadError`, which fires first and does not know the route). `stale-build.spec.ts` refuses the chunk until the tab reloads (Vite preloads it, then imports it).
- **Browser tests** (`app/e2e/`, Playwright Test): `playwright.config.ts` starts real servers, each on a storage built by `scripts/e2e_storage.py` (the factory defaults plus the **synthetic** fixtures in `app/e2e/fixtures/storage`: schedules, a system settings file, a fake API key).
  No secret and none of the real test storage is involved, so they run on fork PRs. One server is open (port 8099), one requires a token (8098, `e2e-token`), and two are unclaimed devices (8097, and 8096 for the phone project: a device is claimed once).
  **Two projects** (#510 A5): `chromium` (a desktop) runs every spec, `phone` (a Pixel 7) the specs in `PHONE_SPECS`: the first steps (setup, settings, the playlist), the lookups, the location picker, and `phone.spec.ts`, which fails when a view or a settings tab scrolls sideways (the page or the view's own area) on either. **A form row is a label column beside its control** (`.field-row`, `.field-label`, `.field-title` in `src/assets/main.css`, the width a `--label-width`); below 40rem the label is a line of text above the control, so a new row of a label and a control uses those classes, never a width of its own. A view's two columns stack below 40rem too, a dialog is never wider than `95vw`, and a grid's columns are `minmax(0, 1fr)` (a bare `1fr` does not shrink below its content). They need `uv sync` and, once per Playwright version, `npx playwright install chromium` (CI does this itself). `@playwright/test` is no longer pinned to the cloud sandbox's preinstalled browser; a sandbox session installs the matching one the same way.
  `watchProblems()` in `e2e/support.ts` fails a test on any page error, console error, failed request, or HTTP error that the test did not declare, so a page that merely renders is not enough.
  Gotchas: the servers serve the **built** `app/dist`: `npx playwright test` alone runs the last build, so a build that failed (a `vue-tsc` error) leaves the old bundle under test; use `npm run e2e`, or build first. The app uses hash routes (`/#/settings`); PrimeVue option accessible names are not their text, so match options by visible text; the factory `location: null` leaves Save disabled, so the fixture sets one.
- **ESLint** (`app/eslint.config.js`, #510 A7): JavaScript's and typescript-eslint's recommended rules and Vue's `essential` set, nothing about formatting (tabs on purpose). `no-undef` is off (vue-tsc knows every name, Vite's defines too), a name starting with `_` is unused on purpose, and `no-explicit-any` is on for the form engine (`BasicForm`, `BasicFormField`, `ArrayField`, `FormDefs.ts`, `FormValidation.ts`, typed in #510 A3: a field is a `ResolvedField`, a choice of a `schema` lookup a `SchemaChoice`, an installed item a `Descriptor`, the values `FormValues`) and off elsewhere for now. Lint is clean; keep it so.
- CI: `.github/workflows/web.yaml` runs the `web` job (lint, build, unit tests) and the `e2e` job (browser tests) on pull requests and pushes to `master`. They are not required checks until the maintainer adds them to the ruleset, and neither is CodeQL: the ruleset requires `unittest` alone, so whoever merges checks the others (WORKFLOW.md steps 7 and 9). **Every Action is pinned to the commit of a release** (`uses: owner/action@<full sha> # vX.Y.Z`, the commit looked up, never guessed: an annotated tag is dereferenced to its commit) and the Dockerfile's uv image by version and digest; Dependabot (`github-actions`, `docker`) proposes the updates (#456).
- **Logging:** production logs at INFO, `--dev` at DEBUG, `EINK_LOG_LEVEL` decides last; `watchdog`'s file events are WARNING everywhere. The setup code is a block of its own in the log (`setup_banner`), found with `grep "Setup code"`.
- Options: `--port` (default 8080 with `--dev`, else 80), `--token` or `EINK_API_TOKEN` (Bearer token on `/api`), `--app` (web bundle folder).
- Do not start the server with `pkill -f`/`pgrep -f` patterns that match your own shell command; start it in the background, record its PID, and signal that PID
  (`uv run` is a wrapper: signal the Python child, not the `uv` process).

## Test environment

- **No test needs a secret or a private storage.** `storage_path()` (`python/tests/utils.py`) builds one per test run in a temporary folder: the factory defaults (`hard_reset`) plus the synthetic schedules in `python/tests/fixtures/storage/` (nothing real, no keys). It is **read-only**: a test that writes copies it first (`WebApiTestBase` does), or builds its own with `temp_configuration_manager`. So the suite runs on a fork's pull request, in a cloud session and in the container with nothing to restore. The old `TEST_STORAGE_B64` secret and `prepare-test-data.ps1` are gone (#27).
  A fixture must stay valid for the data sources it names and use only ones the fake internet serves (a playlist track that fails strikes out and the layer tests then see an error). **Tests must not assume `datasources/` or `plugins/` content exists**: the factory storage makes a folder only for what has settings.
- The headless render tests need the headless browser: `chromium-headless-shell` on `PATH` (Linux), `chrome-headless-shell` on `PATH` (Windows), or whatever `EINK_CHROME` names (a path or a name on `PATH`, set in the environment or in a `.env` file at the repository root, see `.env.example`; no machine's path is in the code; `chrome_command()` in `image_utils.py`, read on every render). In the cloud sandbox:
  `ln -s /opt/pw-browsers/chromium_headless_shell-*/chrome-linux/headless_shell /usr/local/bin/chromium-headless-shell`.
- **No test needs the internet.** `python/tests/__init__.py` makes every `AsyncHttpWorkerPool` talk to `python/tests/fake_internet.py`, which answers the comic feeds, the Wikipedia API and the newspaper covers from text fixtures in `python/tests/fixtures/http/` and generated images (real ones are copyrighted); any other URL is a `ConnectError` naming it. A new download in the code under test needs a route there (and a fixture), not a real request.
  The text fixtures are hand-written in the sites' shapes; `uv run python -m scripts.record_http_fixtures` (needs the internet) replaces them with real answers, and `EINK_TEST_LIVE=1` runs the tests against the real network (the opt-in live check).
- `tkinter` is mocked in `python/tests/__init__.py`. In production it is imported only for the `tk` display, so a missing Tk fails that display and nothing else.
- **Never print, log, or commit the contents of storage files**: they can hold API keys. Inspect them with a command that cannot echo values (key names only), not `cat`.

## Core rules

- Python 3.13, **tabs** for indentation, type hints, `logging` (no `print`), config in JSON. Keep changes focused; do not reformat files you are not changing.
- **The web API.** Endpoints are plain `def` (they run in uvicorn's thread pool; the configuration code is blocking and lock-based), not `async def`.
  Errors are `ApiError(status, message, id)`, and every non-2xx body is `{ success: false, message, id }` (+ `rev` on 409, `errors` on 422). Never put exception text in a response.
- **Settings documents** carry `_id` and `_rev` (a content hash); a `PUT` must echo `_rev` or gets 409. Files are written atomically by `_internal_save`; never write settings files any other way.
  Anything that watches the files must therefore also handle a *move onto* the real file (the watcher reports the destination), not only modifications.
- **IDs from URLs are untrusted.** Plugin and datasource IDs must come from `cm.enum_plugins()` / `cm.enum_datasources()`; never build a path from a raw URL parameter.
  Validating is not enough for the analyser (or a reader): what builds the path must be **our own value** (the constant from our list, the ID declared in the descriptor), not the URL's string that passed a check. Files served for a URL are resolved with `realpath` and must start with the folder's prefix (see `_file_in_bundle`), which also stops symbolic links.

  **Descriptors use JSON Schema keyword names** (`title`, `type`, `format`, `minimum`, `maximum`, `minLength`, `maxLength`, `pattern`, `enum`, `const`, `default`, `writeOnly`, `items`); the old names (`label`, `min`, `max`, `secret`, `int`, `date`, `eq`, `ne`, `in`) are gone, and `test_web_api` fails on them.
  Our own keywords keep bare names, which JSON Schema ignores: `required` (a boolean on the property, not the array of the standard), `lookup`, `visibleIf`, `step`, `minFractionDigits`, `maxFractionDigits`, `header` and `description` as help text. Never give a standard keyword a different meaning.
  **Every descriptor is one the form can read** (`app/src/components/DescriptorSchema.ts`, run by `npm test` over every `*-info.json` and NVE schema, #540): a strict `zod` schema of a settings section, so an unknown keyword (a misspelled `minLenght`) or a lookup of no known kind is an error with its path, and a field's `lookup` (a row's too) must name one of its schema's lookups. The type-check holds it to `FormDefs.ts` both ways: a keyword added to a descriptor goes in both, or the build fails. What a value means (defaults, `visibleIf`) is the Python tests' to check.
  A property of a type neither side knows is not checked. A `number` shows the digits its descriptor declares (`step`, `minFractionDigits`, `maxFractionDigits`); only `integer` forces whole numbers. **`step` is a hint, not a rule** (#89): it is the increment of the input's up/down buttons, and neither side checks it, so a stored `0.15` on a `step` of `0.1` is valid (a grid check would fail on float arithmetic and reject values typed into a file by hand); `minimum`, `maximum` and `integer` are the checks.

  **A Test button** on a `string` field (or a field of a list row): `"test": { "url": "/api/..." }` names a route of ours that gets `{ "value": ... }` and answers `{ "ok": true|false, "message": "..." }`; the form shows the message beside the field and clears it when the value changes. Not caught: a name that answers differently when the client connects (DNS rebinding). Always read-modify-write through the store (a lock per file, then `_internal_save`); never write a schedule file any other way.
  **A timer task in a file that did not come through these routes** (edited by hand, seeded) is checked when the timer layer loads or reloads (`TimerLayer._check_tasks`): the trigger and the plugin's settings, by the same rules as the routes. A task that fails is skipped (the others run) and reported once as a `task-failed` event with the first problem in our words; a disabled task is not checked, and a plugin that is not there is left to its error page when the task fires. A file that does not parse (a missing `task` or `trigger`) still fails the whole load, and the schedule in use is kept.
- **A playlist is a self-contained document**, saved whole: `/api/schedule/playlist` has `POST` (create), `GET`/`PUT`/`PATCH` (rename)/`DELETE` per document, no single-track routes. The editor keeps a working copy (apply a track, add, move, remove) and one Save sends all of it; **a new track is a draft** (`draft` in `PlaylistEditor.vue`): edited like the others and shown dashed at the end of the list, but not in the working copy, and not an unsaved change, until it is applied; cancel, or choosing another track or playlist, drops it, so nothing invalid is left behind; a user may have many playlists. Choosing another playlist, leaving the page or closing the tab asks first while there are unsaved changes. The same store, rev and 422/409 conventions as the timer tasks; a 422 path is `["items", "<index>", "content", "<field>"]`.
- **Configuration changes reach every task.** The watcher's debounced file events go through a `FanoutSink` (evict the cache first, then the `Application`), which broadcasts `ConfigurationChanged(area, type, path)` (`area` from `ConfigurationManager.area_of`) on the `configuration` route to the display and both layers; a task that cares handles that message. The timer and playlist layers coalesce a burst of `schedules` changes (2 s) and re-plan when their part changed; a schedule that does not load keeps the one in use; startup tasks do not run again. The display only logs it (live reconfiguration is not built).
- **Dates crossing the API name their zone.** Every instant the server sends carries an offset (`start_ts`, `end_ts`, `scheduled_time`), and the response names the device zone (`timezone`); the browser reads days and minutes in that zone, not its own. An instant the server receives must carry an offset or `Z` too (`start` of `/tasks/render`: a time without one is a 422); a bare `YYYY-MM-DD` is allowed because it names a calendar day, which has no zone. The wall clock is `ConfiguredTimeOfDay` (system settings `timezoneName`, read on every call).
- **A new device has nothing scheduled, and that is a state, not a failure.** The web app's landing page (`/`) opens the playlist page when there is no playlist (`router/index.ts`: only the landing page, any other address is the user's choice). The factory storage has no playlist and no timer task (and git keeps no empty folder, so seeding makes the `schedules` folder itself, and every start puts it back in `ensure_folders`, for a storage seeded before): `ScheduleManager.validate` warns and lets both layers start, the playlist layer shows the "Nothing to show" page ("Create one in the web app and schedule it"), and a user may delete the last playlist. `NewDeviceHasNothingScheduled` runs both layers on a bare `hard_reset` storage. An emptiness that a layer can say on the panel never raises.
- **Play, stop and next belong to the playlist layer, and every plugin handles `resumed`** (#354, `docs/architecture.md`'s "Transport"). A command goes to `Application.transport(command)` first, which forwards on the `playlist-layer` route (the timer layer is not on it). **Stop** cancels the track and sets `halted`: anything that would start the layer (`StartPlayback` from a reload, the restart timer, the end of a pass) must check it. **Play** and a schedule reload re-enter the interrupted track with `PluginExecutionContext.resumed`; the layer decides nothing about what that means, **the plugin does** (the Slide Show continues a kept list and passes on, returning at once, for a single picture, an unkept list or a used-up one). A plugin class says `resume_contract = "honours"` (the playlist layer runs it) or `"ignores"` (the timer layer does, and never sets the flag); `test_transport` fails for a plugin that says neither, so a new plugin cannot forget it. The track the layer is on is `Position` (ids and indexes: an edit moves the indexes), and a pass starts at `Start(playlist, track, resume)`. **"Did the schedules change" compares the files as loaded** (`_snapshot`, `_loaded`), never the tracks the layer ran: running a track fills its defaults into the object, so comparing those reported a change on every save (a timer task's included).
- **A failing track strikes out, it does not spin.** The playlist layer counts consecutive failures per track: a transient one is a strike (three, the system setting `maxStrikes`, and the track is struck out: it is **not run, its slot shows its error page** instead), a permanent one (`PermanentError`, `ImportError`, `TypeError`, `AttributeError`, a plugin that is not there, settings that fail `plugin_content_errors`) strikes out at once; a success clears the strikes. A pass where nothing succeeded waits (1 s doubling to 60 s). **A strike-out is not for ever** (found when a comic that timed out stayed on its error page until the device restarted): a struck-out track is tried again after `strikeRetrySeconds` (60 by default; one attempt, a probe, struck out again if it fails with the wait doubled up to `strikeRetryMaxSeconds`, 900), and a success clears it; all three are system settings, read at each use (`_policy`), with the class constants as the fallback. When every track has struck out the layer is `faulted` (one telemetry message) and a timer tries again when the first is due (`RetryStruckOut`); a `ConfigurationChanged` of any area also does, and clears the strikes. Anything that gives up on something that may recover needs a way back (a retry time, a probe), not only a person's edit. A plugin that cannot be fixed by trying again should raise `PermanentError`.
- **A rendered page is one template.** An HTML-rendered page (`render/<name>.html`, extending `static/render/plugin.html`) carries its own CSS in its `{% block style %}`; there is no per-page stylesheet and `RenderSession` takes no CSS file. Only `plugin.css` (the base) and `themes.css` (the theme roles) are shared files, linked by `RenderSession`. Page CSS cannot contain `{{`, `{%` or `{#` (Jinja reads them). `plugin.html` carries a Content-Security-Policy (no script, no network: styles, fonts and stylesheets are our files, pictures are embedded as `data:`), because Chromium runs with `--no-sandbox`; a page that needs a remote resource embeds it first (as the RSS pictures are), it does not link to it. `test_error_image` renders a page with a script to prove it does not run.
- **The theme is computed in Python and cascades into CSS** (`python/model/theme.py`). The device theme (`theme-settings.json`: scheme, hue, saturation, lightness) becomes a few HSL inputs; `RenderSession` writes them into `:root` (`plugin.html`), and `themes.css` derives every role class (`text-primary`, `bg-secondary-1-accent`, ...) from them with relative color syntax, `hsl()` only. PIL code takes the same colors from `Palette` (`current_palette(scm)`, read on every render), so it is in theme too. Pages do not pick a scheme; every page wears the device theme. A new role is added in both places (a `Palette` field and a class); `test_theme` checks the class list and renders a swatch per role in Chromium against `Palette`. Design pages so they still read when both secondaries are the same hue (complementary, monochrome): tell parts apart by tone (light, accent, dark), not only by hue.
- **Typography is part of the theme.** `fontBody`, `fontHeading` (unset: the body font), `fontOverlay` (the overlays' text; unset: the heading font) and `fontScale` (0.8-1.4) are in the theme settings and in `ThemeInputs`; `css_vars` writes `--font-body`, `--font-heading`, `--font-overlay` and `--font-scale` into `:root` (family names unquoted: the page escapes quotes), `plugin.css` sets the body font, and PIL code reads `current_typography(scm)`. **A page sets no `font-family` of its own** (`test_theme` checks): headings use `var(--font-heading)`, overlay text `var(--font-overlay)`, text sizes are multiplied by `var(--font-scale)` (the calendar multiplies in `Layout`, which counts events from the text size). A figure that is sized to fill its page (the countdown's number, the year, the error page) is not scaled, so it still fits. Only families in `FONT_FAMILIES` are accepted, and `/api/fonts/{family}` serves a file from that table, never a path from the URL. **A font we ship is under the SIL Open Font License, unmodified, in a folder of its own with its `OFL.txt`** (and a line in `NOTICE`): read its licence in its name table before adding it (`fontTools`, name IDs 0, 13, 14), since a file's name and the text beside it can be wrong (the old `DS-DIGI.TTF` was Digital-7, "personal use", next to another font's shareware notice; Napoli was "all rights reserved"). A **variable font** (one file for every weight) is listed once per weight with its `wght`: PIL sets that axis (`get_font`), and Chromium sets it from the page's `font-weight`. **The page background** is a theme setting (`background`: `white` by default, `tinted` = the theme's light tone, `black` = dark mode); every page's container is `bg-page` (`--page-bg`), and the compositor's fill is `Palette.bg_page`. White is the default because a color e-ink panel has only a few pure colors and dithers a tint. Black swaps the light and dark tones (`l_text_dark`/`l_text_light`, `l_bg_light`/`l_bg_dark`) so every `text-*` and `bg-*` role stays readable on it; a page never hard-codes white or black. The Theme tab shows a sample in the real fonts. It also shows every role of the palette, computed by the server for the form's values (`POST /api/theme/palette`, the same `palette_of` as PIL), never re-derived in the browser.
- **Deployment is the container** (the readme's "Set up a Raspberry Pi", `deploy/bootstrap.sh` and `deploy/eink-container.sh`, below under Containers): a non-root user's rootless Podman, port 8080, the token passed to the container by name (never on a command line, which the process list shows). The old systemd unit for an install without a container is gone.
- **Who may use the device** (`python/web/access.py`, #36): there is no default credential. A device on the network starts *unclaimed*, logs a one-time **setup code** (and draws it on the panel through `Application.setup_notice`: a page with no expiry, so it holds the panel until the device is claimed, and the **layers are not configured until then**: `Application` keeps their `ConfigureEvent`s and sends them on `SetupDone`, so no track or timer task goes into play mode on a device nobody owns; a replaced code is redrawn, `SetupCodeChanged`), and whoever enters it at `POST /api/access/setup` chooses the password (kept as a salted scrypt hash in the `access` settings, which is not in `DEVICE_SETTINGS`, so no route serves it). `--token` / `EINK_API_TOKEN` stays the script credential and counts as claiming; `--no-auth` keeps a network device open on purpose; `--require-auth` applies the rules on a local bind (the browser tests); `--reset-password` forgets the password. A device bound to `localhost` is open until a password is set. Routes use `require_auth`; `EINK_SETUP_CODE` fixes the code for tests.
- **The server answers only to names it expects** (`python/web/hosts.py`, DNS rebinding): `localhost`, any IP address, this machine's name and `<name>.local`, and `--allow-host` / `EINK_ALLOW_HOSTS`; any other `Host` gets 421 in the error shape, on HTTP and on the telemetry WebSocket. The tests allow `testserver` through the environment (`python/tests/__init__.py`). A failed `POST /api/session` is logged (address and count, never the token) and the client waits longer after each one past three (`SignInThrottle`: 429 with `Retry-After`, no wait on a server thread).
- **An HTTP client of ours is made with `verify=tls_context()`** (`python/task/async_http_worker_pool.py`; `test_tls_context` scans for the rest). The container's OpenSSL 3.5 puts a post-quantum hybrid key exchange group first in the TLS 1.3 handshake, and some hosts (webcomicname.com on Tumblr) answer by dropping the connection: `RemoteProtocolError: Server disconnected without sending a response`, only from the container (the Windows host's older OpenSSL, `curl` and a browser were fine, and TLS 1.2 worked in the container too). The shared context offers P-256 only, which every TLS 1.3 server accepts. A failure that is the same address in one place and not in another is the stack, not the address: compare the TLS version and groups before the headers. **A client names its timeouts**: httpx's default is 5 s for connecting and for each read, which a small board on a slow link or a slow site (Dinosaur Comics, whose picture redirects to another host) does not meet; the shared pool's client is `REQUEST_TIMEOUT` (30 s, connect 15 s), and a client of our own sets one.
- **Every download of an address that is not our own constant goes through the URL guard.** `stream_to_buffer` (images and feeds) is guarded by default and `stream_checked` (`python/utils/url_guard.py`) is the same for any method: the address and every redirect are checked (not this device, not link-local, ...), because the address is typed in a settings page or taken from a feed, an answer or a redirect (found by the OWASP pass, #189). A new download uses one of them; `guarded=False` is for a constant only. The tests' fake internet makes every fake host resolve to a public address; a test of a refusal patches `url_guard._resolve` or uses an address literal.
- **Every file of the storage goes through the configuration manager, by name.** `ConfigurationManager` is the only holder of the storage root; it builds the sub-managers (settings, schedules, plugin, data source) and each gets a **local root** from it: the chain of trust on paths. A caller names a file (`dsm.file("tokens")`, `schedule_manager().read("tasks-x.json")`, `cm.read_schema("theme")`), never a path, and a name is checked to be a leaf (`leaf_name`), so nothing outside a sub-manager's root can be reached. Only `model/storage_files.py` (`save_json`: atomic; `load_json`), `configuration_manager.py` and `schedule_manager.py` open, write or delete files; `test_storage_access` fails on any other module that does (the few non-storage uses are listed in it: render scratch files, `/etc/timezone`, the log configuration, the mock display's output in the system temp folder). **A folder exists because something was written to it:** `save_json` makes the parent folder, a lookup or a read makes none, so a plugin or data source without settings or files has no folder. Folders the **user supplies** (the Image Folder's) are read in place, read-only, and are not storage. The calendar's `tokens.json` was the case that broke the rule (its own `open`, `makedirs`, private save); a new data source that needs a file of its own asks its `DatasourceConfigurationManager`.
- **An API data source's client is a metered one** (`python/datasources/metering.py`, `docs/development.md`'s "API Metering", #440). It is made with `metered_client("<the descriptor's id>", ...)`, which counts every call by exact status (or why there was none), with the bytes of the bodies, per day, and `cached` / `fetch_cached` tell the same meter what the cache did (`hit`, `miss`, `stale`, `coalesced`, `revalidated`, `bypass`). A client made with `httpx.AsyncClient(` in an API source (features `api` and `internet`) fails `test_api_metering`, as one without `verify=tls_context()` fails `test_tls_context`. **Counts only: never an address, a key, a query or a body** (the id and a status code are all a count carries). The counters are in memory and written about once a minute and on quit, never per call (SD-card wear); a new kind of answer an origin gives gets its own cache setting (above), and its outcome is already counted. A new API source is on the System page's API usage card with no work of its own, and so is a source that downloads through `download_for`: the pool's client is metered with no source, and `download_for` names the data source for the length of the download (`metered_as`).
- **A data source keeps its downloads in one pool, and the origin's headers decide how long** (`python/datasources/content_cache.py`, #400, `docs/development.md`'s "Kept Downloads"). A picture or feed that is fetched again and again goes through `download_for(dsec, url, default_hours=...)` (which calls `fetch_cached`), never `stream_to_buffer` directly, so it is kept in the data source's folder (`DatasourceConfigurationManager.read_blob` / `write_blob` / `delete_blob`: bytes go through `storage_files`, like the JSON) and shared by every task. A fresh download is read from disk and **nothing is sent** (no `HEAD`); an expired one is asked for with `If-None-Match` / `If-Modified-Since`; `Cache-Control` and `Expires` can shorten `contentCacheHours`, never lengthen it. The pool is capped (`contentCacheMB`) and tidied (`staleDays`, and `retain(scope, urls)` for a list that was just loaded: scoped, so another feed's pictures stay). The description is written before the bytes and a pair that disagrees in size is a miss; a file name is a hash of the address, which can carry a key. A source whose address always gives something new (a camera snapshot) keeps the default at 0.
- **A media list can outlast a visit, and the plugin that shows it keeps it** (`python/plugins/kept_list.py`, #222). The Slide Show opens the data source's list (`open_async`), shows the head, drops it and saves the rest in `plugins/slide-show/list-<hash of the slot>.json` (through its `PluginConfigurationManager`); only when nothing is left, or the list is older than the task's `refreshHours`, does it open the data source again. The **slot** is `PluginExecutionContext.slot`, the playlist's id and the track's (track ids repeat across playlists, so a track id alone is not an identity), and a slot runs one visit at a time, so there is nothing to share, lock or retry: two slots on one feed each have a list. A file carries a fingerprint (the data source, the task's settings that choose the list, the data source's settings revision), so a slot pointed at another feed starts anew. The **task** chooses `listMode` (`continue`, the default, or `restart`: a new list every visit) and `refreshHours`; the plugin's settings choose `staleDays` (a list unused that long, a deleted track's, is removed; 0 never; every file records `last_used`). The **data source** only says `"keepsList": true` in its descriptor (RSS Feed, Image Folder, Comic: every feed or folder is shown item by item until it is used up, then fetched again and started over, so new items turn up in time; no tracking of what was seen, `refreshHours` defaults to 0 = only when used up; `test_item_audit` lists the sources that are not kept): a source whose list is made fresh every time (the calendar's and the weather's pages are views of now) never is. An item is dropped once it has been shown (or failed), so a restart or cancel does not show it twice; an old list is used when the origin does not answer; a list that cannot be kept (too big, not JSON, an unwritable disk) is used from memory, so a slide is never lost to the disk. Another plugin that shows a list uses `open_list`. **A data source is called from several threads at once** (`open_async` and `render_async` run on the playlist layer's loop and the timer layer's, and for the settings routes' tests): it keeps no mutable state on the instance, or guards it; its files go through the configuration manager, whose objects lock and check the revision.
- **The generators' system prompts are the Master Prompts, a device-wide settings document** (`master-prompts`, its own Settings tab; #271): `inventInstructions`, `inventRequest`, `rewriteInstructions`, `rewriteRequest` and `canvas`, read by `python/datasources/ai/prompt.py` (`master_prompts`, `rewrite_request`, `with_canvas`) for the Generated Image and its image parts; nothing is hard-coded in Python. **The factory text is the `default` of the schema shipped in the NVE** (`python/storage/schemas/master-prompts.json`): a new storage is seeded with it, `GET /api/settings/{name}/defaults` serves it (`ConfigurationManager.shipped_settings`, from the NVE and not the stored schema or document), and the form's "Restore default" (a field) and "Restore defaults" (the tab) put it into the form for the user to save or not; a value missing or empty reads as the factory text. A new prompt is a new property in that schema (and its default). **A text's fields** (`{name}`, `{{` and `}}` for a brace; `python/utils/prompt_tokens.py`, `PromptTokens.ts`): a string property with `tokens: [{ name, description }]` may use only those names (any other is "Unknown field {name}" on the form and from the server, a shared case in `form_rules.json`), and the form lists them under the field. **Whatever supplies the values supplies that list**: a data-only source says its `tokens` (names with descriptions) and fills them, so a field is never a guess. A field with no value drops out of the text.
- **The Weather Visualizer** (`python/datasources/weather_image/`, #271) is the Generated Image with a prompt that talks about the weather, and the model of a prompt whose fields are **supplied by a capability**: the weather contract lists `tokens` (`TOKENS` in `contracts/weather.py`, names with descriptions) and fills them from any provider's `Report` (`prompt_fields`, only what is known; a field with no value is left out; `test_weather_image` checks the two agree). A task property says `"tokensFrom": ["data-weather"]` (capabilities, never a vendor's id; it also `requires` them) and the configuration manager copies the contracts' lists into its `tokens` when the descriptors are read (`_resolve_tokens`, `contracts.tokens_of`), so the form, which lists them under the field, and the server, which refuses another name, read one list whichever provider supplies the values. The generation after the prompt (rewrite by the text part, the image part, the blurred margin) is shared with the Generated Image (`ai/generate.py`). **Soft by default**: when the weather provider cannot be reached (not a `PermanentError`) the prompt is made with what is known and the picture is still drawn; a missing key or location reaches the error page. A dropped field leaves the words around it, so a prompt is best written so that it reads without any one field.
- **Comic Vine is the second API data source with a key in the address** (`python/datasources/comicvine_api/`, asked by Comic Vine Covers, `comic_vine/`, #237): the same shape as the weather (a page source `uses` an `api` source). `api_key` is hidden in the `httpx` log lines (`HideKey`), its failures are our words with the site's status code at most, and it sends a browser-like `User-Agent` (the site refuses the HTTP library's). It makes its own HTTP client (`comicvine_client`, as the Google source does) so the web app's Test route and the layers ask it the same way; the Test of a task's `series` (`test.url`) is a route of the API source's own router. A search keeps its answer for `volumeCacheHours` and a page of issues for `issuesCacheHours`; the page source picks a random page of the issue list, shuffles it, and is a kept list (`keepsList`), so each cover is shown once before the series is asked for again. Covers are portrait: `blurred_margin`, never a crop.
- **Thunderforest is the third API data source with a key in the address** (`python/datasources/thunderforest_api/` and `thunderforest_map/`, #428): the same split as Comic Vine (an `api` source holds the key, `contentCacheHours` and the kept maps and makes the Static Maps call; the page source `uses` it, holds the `places` list (a name and a `location` each) a task picks from by name, or the device's own location, and draws the map). The key is `apikey=` (hidden in the `httpx` log lines, `HideKey`), a failure is our words from `refusal(status)` and never the service's text (which quotes the key), and an `HTTPStatusError`'s text, which holds the address, is never chained. **Thunderforest's terms require the attribution on the map**: the page draws it (a solid strip, so the panel does not dither a tint), and a map is a foreground page so no overlay covers it. Only a style from `STYLES` ever reaches the address.
- **An origin's answers are kept by the data source, for all its tasks** (`python/datasources/response_cache.py`). The OpenWeatherMap API data source keeps what OpenWeatherMap answered in `datasources/openweathermap-api/cache-<hash of the question>.json` for **the time its settings give that kind of answer: one setting per kind of response** (`currentCacheHours`, default 0.5, and `forecastCacheHours`, default 6; 0 asks every time; neither cuts the other; `cached(..., setting=)`; a data source with another kind of answer gets another setting; `staleDays` removes an answer nobody used, default 30), through `cached(...)`: one task at a time asks the origin and the others wait for its answer, the old answer is used when the origin does not answer (never a `PermanentError`, so a refused key is not hidden), and a cache that cannot be read or written is no cache. The key is not part of the file name or the content. **The Calendar Sources keep what each calendar answered the same way** (`cacheHours`, default 0.25, and `staleDays` in its settings; it reads whole days and at least `MIN_READ_DAYS` so a page and an overlay of the same days share an answer). The Reminder Overlay (#158) asks it (`dsec.provide(CalendarApi)`), on demand, from the overlay task's own trigger: nothing runs between runs. Its `calendars`, and the pages', are chosen from the **provider's** list: a `settings` lookup with `"from": "<data source id or capability>"` reads another data source's list, and `"from": "data-calendar"` is the device's provider of it (`from_source` in `documents.py`: the system setting `calendarProvider` when it names an installed provider, else the only one; the lookup route and the task's validation do it; `test_web_api` checks the list). **A data source says which others it uses** (`"uses": [ids]` in its descriptor) and asks them with `dsec.use(id, Class)` (the source and the context to ask it with; a source that is not loaded is a `PermanentError` in our words): `test_item_audit` checks the ids exist, no cycle, and that the descriptor says `uses` exactly when the code asks (`use` / `context_for`); the form warns under the data source field when a chosen source's `uses` is not on the device (a disabled source is not loaded; `DataSourceUses.ts`). **A data source that needs another's data asks that data source**, never its origin (#157): it gets it from the `DataSourceManager` by its id and asks it with `dsec.context_for(other)` (both through `use`), a context whose settings and files are the other's (opened by its id). So the settings, the cache and its lock are shared, not copied, and a page and an overlay of the same hours make one call.
  **The data of an origin is an API data source** (`DataSourceApi` in `python/datasources/data_source.py`): `open_async(dsec, params)` answers the origin's data for `params`, possibly a kept answer, and it **renders nothing** (no `MediaRenderAsync`). Its descriptor has the `api` feature and no `layer-*` or `media-*` one, so no plugin offers it; it holds the origin's settings (key, kept times) and another source `uses` it or requires what it supplies (`test_layer_features`). **A provider operates on a contract** (#513, `python/datasources/contracts/`): each capability (`data-*`) has one, a `ProviderContract` subclass with the data it answers (`WeatherApi` and `Report`, `AiTextApi`, `AiImageApi`) and, where a prompt reads it, its `tokens`; a provider implements it, and a consumer imports only `contracts` (`test_layer_features` fails on an import of a provider's module the consumer does not `use`). A consumer asks **`dsec.provide(Contract)`**, which chooses among the loaded providers: the device's (the contract's system setting, `weatherProvider`) when it is `configured` (its settings are complete, never its last call), the only one configured, the device's anyway, the only one there is (so its own error says what to set), else a `PermanentError` naming the capability; `GET /api/lookups/providers/{capability}` lists the choices. **OpenWeatherMap is the model**: `open_async(dsec, { "needs": ["current", "forecast"] })` answers a `Report`; the Weather pages, the Weather Overlay and the Weather Visualizer only draw it, and its settings problems reach them in its words. `uses` stays for a vendor tie (a part and its key holder, a map and Thunderforest's styles). **A weather report is SI** (Celsius, metres per second): the units a person reads are the device's, never a provider's (system settings `units`, the master: auto, metric or imperial, and `temperatureUnit` / `speedUnit`, each overriding it for its kind, so units may be mixed; `units_of` / `device_units` in `contracts/weather.py`), applied by whatever shows the report (a page, the overlay, the prompt fields). A new kind of measurement a page shows gets its own override setting. **Open-Meteo is the second weather provider** (`python/datasources/open_meteo_api/`, #513 phase 5): no key, so it is set up as installed and a new device has weather at once; one call (`timeformat=unixtime`, `wind_speed_unit=ms`) fills the same `Report`, its WMO codes mapped to OpenWeatherMap's icon groups (`WMO` in `open_meteo_api.py`; the contract's icon codes are OpenWeatherMap's). Free for non-commercial use (a hobby device), data CC BY 4.0: **a report carries its provider's credit** (`Report.credit`), which the Weather pages draw (never a provider's name in a template); an overlay has no room for it (a longer line shrinks the whole overlay, its icon too), so the pages and the Credits carry it. With OpenWeatherMap's key set as well, two providers are set up and the device must choose (`weatherProvider`). **Settings that move to another data source** go through `SETTINGS_MOVES` in `configuration_manager.py` (once, in `upgrade_settings`, logged by key name): the values are copied and **removed from the old document**, whose schema no longer marks a key write-only, so the settings route would otherwise send it as it is.

A settings document has the `_schema` of its source (the schema file, the descriptor's `settings`, the schedule constants: the number at the end is the version, no `_schema` is 1); a document with no source (a kept list, the refresh state, the sign-ins) has an integer `_version` owned by the code that writes it (`migrate_file`). `put_document` overwrites whatever `_schema` the client sent: a version is the source's to give. A rename, a removal, a retyping or a new meaning of a setting is one PR with four things: the source's number raised, the migration (`@migration(family, n)`, `dict -> dict`, hard-coded: a person decides what it means), the shape recorded (`python -m python.tests.test_schema_versions --record`) and a fixture of the old shape; `test_schema_versions` fails until they agree. A new property with a default needs none (it is filled in). - **A schema belongs to the code, not to the storage.** `ConfigurationManager.refresh_schemas()` (at every start) copies the shipped `schemas/*.json` over the storage's, since a device seeded before a setting existed would otherwise never show it (found when the theme's fonts had no selector). - **A backup is encrypted, never carries the device password, and a restore is one event** (`python/utils/backup_archive.py`, `python/web/backup.py`, `python/web/routers/backup.py`, `ConfigurationManager.backup_files` / `write_backup`, `docs/development.md`'s "Backup and Restore", #368). Settings files hold real API keys, so there is one kind of archive: a ZIP sealed whole (AES-256-GCM, scrypt, the header authenticated) with a passphrase of its own, which is not the device password and is kept nowhere. `backup_file(name)` is the one place that says what a backup holds (settings, schedules, a plugin's or data source's own files; **not** `access`, `schemas`, `state` or `cache-*`), when it is made and again when it is opened, and a name from an archive is only ever a *name*: a plugin's or data source's folder is the descriptor's declared id, a file is written through the configuration manager's objects, never a path from the archive. An archive is untrusted: sizes are counted as the bytes come out (a ZIP bomb says it is small), every document is checked by the rules of the route that would have saved it (except "Required": a stored API key is `null` until typed in), a problem is reported by file and field and **never by value**, and a failure to write puts the files written before it back. It is a priority image marked `origin.kind = api`: the route renders the text (`message.html` through `render_message_image`, themed, escaped by Jinja, a plain page when the browser fails) or decodes the picture (`utils/upload_image.py`: size, formats and pixel count are checked before decoding, by content, never by name; every refusal is a `ValueError` in our words) in its own thread, and the Application's own thread does the sending (`PushedImage`). The Application keeps the pushed messages that are still about (at most 20, 429 beyond), makes their titles unique (a title is what `PriorityRevoke` takes down) and refuses before the device is claimed. A route gets the Application from `application_of(request)`.

An `em` follows the font size of whatever holds the element, so the same glyph or margin comes out a different size in each place (the gutter's glyph shrank with every nested `em`); `rem` is the same everywhere. A rendered page puts its computed size on `html { font-size: ... }` (the weather page's, the calendar's `font_px`), so `1rem` is the page's size, and where an element's own size varies a custom property holds it (`--fs`, the weather table's `--u` and `--p`) and its lengths are `calc(k * var(--fs))`. - **The web API is typed from the server's OpenAPI document** (#590). `scripts/export_openapi.py` builds the app as the server does (core routers and every enabled plugin's and data source's own) and writes `app/src/api/openapi.json`; `openapi-typescript` generates `app/src/api/schema.d.ts` from it; both are committed, and `cd app && npm run api` regenerates both. **Changing a route or its models means running it**: `test_openapi_document` (Python) and `schema.test.ts` (Vitest) fail on a stale file. An answer that carries what a person may have written into a file (a schedule: one odd value must not fail the whole list) or keys only a descriptor knows (a settings document, the descriptor lists, as open models) is `described(Model)` instead: the document names the model and nothing is checked or dropped at run time, so a test validates the real answers against it (`TestDescribedAnswers`, `TestDescribedSettings`). Every route has its answer typed except the telemetry events (their kinds are the hub's), the device schemas (JSON Schema files) and the AI providers' `/models` (read by no page). **A route a descriptor names** (a Test, `test.url`; a row action, `items.action.url` and its `/start`, `/continue`, `/poll`; a URL lookup) is called by the form by that address, so it cannot be typed by path: it declares the shared answer (`**test_route()`, `**row_step_route()`, `**answers(list[Choice])` in `python/web/openapi.py`), the components read that generated type (`TestAnswer`, `RowStep`), and `TestDescriptorAddresses` fails for an address of any descriptor or shipped schema that is not such a route. `SettingsForm` is given a `target` (a device document by name, or a plugin's or data source's settings), never an address.
- **Server data that more than one view or form reads is the cache's** (`app/src/api/resources.ts`, Pinia Colada, #549): its key is the route's path, so the server's `changed` paths (the telemetry link's `config-changed` and `restore`, opened once by `App.vue`) mark what they cover stale, and an open page shows a change made elsewhere (another tab, the CLI, a hand edit, a restore) without a reload. What is installed is `useCatalog()` (never `provide`/`inject` under a string key: a view that forgot one gave the form an empty list), a form's lookups are followed (`followResource`, so a provider set up elsewhere changes the choices) or read (`readResource`) through it. **Edit state is never the cache's**: an editor copies what it loads (the editor machine owns the draft), so a change from elsewhere cannot overwrite what a person is typing, and a 409 is the machine's to resolve. A composable that uses the cache runs in its test inside `inApp()` (an app with Pinia and the cache). A test that changes a stored file and puts it back waits until the server reads it again (the watcher's event evicts the cached document): the next spec loads it.
- **A view's data lives in a composable** (`app/src/composables/use*.ts`, #510 A6): the loading, the saving and the editing state, with every API call, are a `use...()` function that returns refs and operations; the view keeps its template, its dialogs, the form instance and the toasts. What goes wrong is told through a `notify(severity, detail)` callback (the view turns it into a toast), and what needs the form (a 422 on a field) is handed in as a function, so the composable runs without a component. Its test (`use*.test.ts`) stands in for the API with `vi.mock("../api/client")`; a shared service it uses (the telemetry link, the transport) is an option that defaults to the shared one (`useSystem(notify, { link, transport })`), so a test passes a fake. - **An editor's cycle is one state machine** (`app/src/composables/editorMachine.ts`, `useEditor.ts`, #550): load, edit, save, conflict, discard, leave. The form reports (`validate`, `submit`), the editor decides; the document stays with the editor, which tells the machine what happened (`values`, `edit`, `loaded`) and asks it to load or save (`useEditor` runs them and sends the outcome). **Unsaved is a comparison**: the values' key (`valuesKey`: unset is missing, `_`-keys left out) against the baseline, the first values the form reports after a load (a form fills in defaults and masks as it opens), so an edit put back is clean; an edit that cannot be compared (`edit`) is unsaved until saved or discarded. Leaving asks when `hasUnsaved` (the `unsaved` tag). A 409 is a conflict: keeping mine takes the server's revision from the 409, so the next save is not refused again, and taking theirs loads. **A loaded document is shown after the machine is told** (`load` answers `{ rev, show }`), or its first values would not be the baseline. The machine is pure (no invoked actors), so `editorMachine.test.ts` walks every path `@xstate/graph` finds and checks the rules at each step; a new state or event is added to its `EVENTS`. A revision that changes under the edits (a playlist renamed on its own) is `revised`, which leaves what is unsaved as it was. `SettingsForm`, `usePlaylists` (the playlist's values are its tracks: one moved and moved back is no change, and Discard puts back the copy it loaded) and `useSchedule` (one task dialog at a time; a fresh form for every task shown, `formKey`, so its first values are that task's) use it; a delete's 409 is a notice with Reload only, not the machine's conflict. **An editor follows its document** (`useEditor`'s `follow`: the address and how to read the stored revision): a `changed` path of the telemetry link that covers the address, a `gap` or the link coming back makes it ask for the stored revision, and only one that is not its own is a change (the watcher reports the editor's own saves too, and the replayed history is checked as well, since a save between the load and the link's opening is in it). With nothing unsaved the document is loaded again; with edits it is `stale` (still `unsaved`): the banner "Changed elsewhere" offers Reload or Keep editing (unsaved until saved or discarded), and a save then goes over the loaded revision, so the 409 asks whether to overwrite. **Work the machine does not compare is `held`** (`follow.held`: the playlist's draft, or a track edited and not applied, which the page tells as `trackPending`): a load would drop it, so a change elsewhere is stale then too. `SettingsForm`, the playlist (the selected track stays selected by its id) and the Scheduler's task dialog (a stored task; a new one follows nothing) follow. A browser test that changes a stored file and opens a page next waits until the server serves it (`untilServed`), or the page loads the old copy and then hears of the new one.
- **Web app, schedules.** The Scheduler shows a **day**, a **week** or a **list** (each task once, its next run and runs in that week), from an offset in days from today (`SchedulerView.ts`; the list also has each task's *Run At Startup*): a week is the seven days from today's weekday, not a calendar week, and nothing before today is shown (Back stops there). A later window is asked for with `start=YYYY-MM-DD&days=` (today is the server's own). `Scheduler.vue` saves one task at a time (see the editors above for playlists) (`PUT /api/schedule/timer/{doc}/items/{id}`, `POST .../items` for a new one, `DELETE ...?rev=`); a task carries the document id and its `_rev` from the render response, a 409 offers Reload/Overwrite, a 422 for `task.content.<field>` shows on that field. A stored task can be saved once it differs from what the dialog first showed; closing the dialog with its own close button or Escape, or leaving the page, asks while it does (Cancel is "close without saving"). The fixture timer tasks must stay valid for the plugin descriptors (the server validates a `PUT`).
- **A task that swallows a failure reports it** (`DispatcherTask.report_failure`, `MessageRouter.failure_sink`): `except Exception` in a task thread exists to keep the thread alive, not to hide the failure. It calls `report_failure(our sentence, error)`, which logs the exception in full and sends an `error` event with `safe_reason` (and `detail` for a viewer on the device), once a minute per failure so a loop that keeps failing cannot flood the hub. Narrowing the handler would trade a logged error for a dead task. Shutdown handlers stay log-only (every step must run, and nobody listens). `test_failure_telemetry` pins it down.
- **Telemetry is a response** (`python/task/telemetry_hub.py`, `python/web/routers/telemetry.py`, `docs/development.md`'s "Telemetry"). What a task sends on the `telemetry` route reaches the web app over a WebSocket:
  - Never raw exception text: send our sentence and `safe_reason(e)` (an actionable reason: the HTTP status and what to check, or the type's name with the text cleaned of addresses and secrets; the user must be able to tell what to fix), and log the rest.
  - **The exception in full** (`detail`, from `error_detail(e)`) is on a failure's event, but the telemetry routes and the WebSocket send it only when the connection comes from a loopback address (`_on_device`); anyone else gets the cleaned `message`. Forwarded headers are not trusted, so a proxy on the same machine (or a container's published port, which arrives from the gateway) makes viewers remote. The gutter shows it under the message.
  - The hub keeps only JSON scalars, short lists and small objects; any other object becomes its title or its type's name.
  - A shown image goes to the hub with the `shown` event and is served by its digest, never through the link and never by a path.
  - The WebSocket checks the session itself (it is outside the `/api` token dependency) and the `Origin`, since CORS does not cover a WebSocket.
  - A new event kind goes in the table in `docs/development.md`.
  - **A change of the storage names the API routes it changes** (`python/model/changed_paths.py`, #549): `config-changed` and `restore` carry `changed`, the paths of the GET routes whose answers may differ now (`/api/settings/system`; a path covers every route it starts, by whole segments; `/api` is everything), worked out from the file the watcher saw, so a save through the CLI, by hand or by a restore counts as one through the API. A provider's settings also change the choices of what it supplies and the `from` lookups that read its lists; what the device keeps for itself (kept lists, downloads, answers, tokens, `state`) changes none. Only our own names: an item by its declared id, never a value. A new route that reads a stored file gets its path there; `test_changed_paths` fails for a path that starts no route.
  - **`seq` starts again at every start of the device**: the WebSocket opens with `hello { run, seq }` (`TelemetryHub.run`, random per start; `seq` the newest event, so what follows up to it is history: the cache of the API's answers acts only on what comes after), and a page that names another `run` gets everything kept; the link then starts over. Without it a page open across a restart asked `since` an old number and showed nothing new (found after a container rebuild).
  - **Every image says who made it** (`DisplayImage.origin`, `OverlayImage.origin`, `python/task/source_router.py`): the layers hand each track and timer task a router that marks the images sent through it, the compositor's `layers()` carries the mark into the `shown` event, and the System page lists it under "Now showing". A plugin sends through `context.provider.required(MessageRouter)` and gets the mark for free; code that sends an image on its own (an error page, the setup page) marks it itself or leaves it blank.
- **A descriptor is named by one rule** (#543): its id is the vendor, if there is one, then what it is, in kebab case and whole words or the vendor's own abbreviation (`nasa-apod`, `thunderforest-map`); the one that holds a vendor's key and kept answers is `<vendor>-api` (`openai-api`, `comicvine-api`, `open-meteo-api`), so a provider sorts with what uses it; its code folder is the id with `_` for `-`, and the main module has the folder's name (`openweathermap_api/openweathermap_api.py`); its `name` is for people (no "Data Source", no abbreviation). A folder in `python/datasources/` without a descriptor is shared code (`ai`, `contracts`), which the loader does not list.
- **A data source's folder is its id.** `create_datasource_context` opens its settings by `ds.id`, as the settings routes do; the display name ("RSS Feed") is for people. Opening them by name read a folder that did not exist, so every list kept in settings looked empty at run time; tests with a fake settings manager could not see it.
- **The Help drawer says how to use the app, and is kept true** (`app/src/components/HelpDrawer.vue`, opened by the toolbar's help button; a PrimeVue `Drawer` from the right, `help.spec.ts`): the first steps, the pages, how a picture reaches the panel (layers), play/stop/next, API keys, safety, what to do when something is wrong, and how to set up the data sources that need it (weather, calendars and their sign-ins, generated pictures). A change to a page, a toolbar command, a layer rule, a data source's settings or a Pi command that the drawer mentions changes the drawer in the same PR; it names only what exists. **How to use the app belongs in the drawer, not the readme** (a consumer never reads the readme): every plugin and data source has its entry there, and so does every setting a consumer chooses (the panel, buttons, kept downloads, strike-outs, backups, API usage). **The readme is not documentation** (#578): it says what the project is, its known limitations and how to install a Pi (which happens before the app exists), and links to `docs/`, where everything else about the code and the Pi's commands goes. Both say only what is so now: no "used to", "moved", "now", "from before" or issue numbers (those are in git and the issues).
- **The System page is the one place that shows how the device is** (`app/src/views/System.vue`, `GET /api/system`, `python/web/system_info.py`, #390): the parts' status, the machine, a Raspberry Pi's own readings (only when `/proc/device-tree/model` says Raspberry Pi), the storage by plugin and data source, and, in the right column, two panels of their own (Now showing, Activity). Its toolbar (as the playlist's) holds the playlist's transport and the commands that open a dialog: Back up, Restore, Device password. The app's toolbar has no status or activity button; the page is in the left menu. **The response is numbers and our own words**: no host name, address, user or path (`test_system` checks the body against the temp folder, machine and user names). The storage is counted by `ConfigurationManager.storage_usage()` (names from `_LEAF`-checked folders, sizes only), never by a caller walking folders; reads of the machine's own `/proc` and `/sys` are in `system_info.py`, which is listed in `test_storage_access` as not storage. A reading the machine cannot give (a container, Windows) is left out, never an error. The telemetry link starts after the page's first request is answered, so on a device that asks for a sign-in it is never refused first.
- **A build says which commit it is, and an update checks what it started** (#413 follow-up to a Pi that showed no front-end change after a rebuild): `deploy/eink-container.sh build` passes `--build-arg EINK_COMMIT=<short commit>`; the Dockerfile sets it after the dependency layers (web stage before `npm run build`, so a new commit always rebuilds the bundle and a cached bundle of another commit cannot be reused; app stage before `COPY python/`). The bundle carries it as `__APP_COMMIT__` (the header's `v0.1.0 (abc1234)`, `dev` outside an image), the server as `EINK_COMMIT` (`GET /api/system` `host.commit`, `unknown` unless it is a short alphanumeric), and the System page's Machine card warns when they differ (a tab opened before an update). `cmd_start` fails when the container's image is not the one just built, and prints `Running commit ...`. Anything else that must be known about a running build goes through the same build argument, never a file written at run time.
- **The browser stores nothing but the theme** (`localStorage`, key `theme-...`); everything else lives on the server, which is trusted. Never put a token, a session, or any other state in `localStorage`, `sessionStorage`, or a script-readable cookie (CodeQL flags it as clear-text storage of sensitive information, and it is not needed).
  The API token is the one case that looks like it needs storage: it is sent once to `POST /api/session`, and the server keeps the session (`python/web/sessions.py`) behind an `HttpOnly`, `SameSite=Strict` cookie. The e2e tests assert that only the theme is stored.
  The cookie is `Secure` only when the app itself sees `https`: behind a TLS-terminating proxy it sees plain `http`, so the cookie is not marked `Secure` (forwarded headers are deliberately not trusted). There is no rate limiting on `POST /api/session`; that is a documented tradeoff for a home-network device.
- **What only the device has stays in the `device` group, marked Linux** (`inky`, `gpiozero`, `lgpio` and what they pull: `spidev`, `smbus2`, `gpiod`, `gpiodevice`; `cysystemd` was dropped, nothing imported it): never in `dependencies`, no default group, and imported only inside the function that needs it (the Inky driver of #281, `python/display/inky_display.py`, when the display is initialized: `load_driver` turns a missing driver or a board that does not answer into a `PermanentError` in our words, which the telemetry hub's status shows as they are; a display that fails to start is **not** replaced by the mock one), so Windows and the container install and start without it. The Waveshare drivers (vendored: `python/display/waveshare_epd`, left out of `ruff`, `mypy` and `coverage`) are imported by name, from our list of the vendored files, in `python/display/waveshare_display.py` when the display is initialized. `test_pyproject` pins all three; `uv sync --frozen --all-groups --dry-run` on Windows makes no change.
- **After swapping a framework or library, check what it was installing for you.** Removing Flask silently removed `jinja2` (and `markupsafe`), which four modules still imported; only the tests noticed.
  Grep the imports against `pyproject.toml` and declare every third-party package you import directly.
  The same goes for the tests: **a test that patches the old name keeps passing without testing anything** once the code makes its object another way (the pool's client became a `MeteredClient`, and two robustness tests still patched `httpx.AsyncClient`: one failed, the other went on passing with no failing client in it). Grep the tests for the old name, and make such a test assert that its stand-in is the one in use.
- **A `DispatcherTask` handler is marked: `@handles(MessageType, ...)`** (`basic_task.py`, #579). Only a marked method is a handler, so a helper that takes a message is never one: when any one-parameter method annotated with a message type was a handler, a helper silently replaced the real one, twice (`Application._display_settings`; a setup-page helper that stopped the layers being configured). `handler_claims` reads the marks along the class's bases (a subclass's handler for a type replaces its base's; an override of a marked method keeps the mark) and makes a mistake a `TypeError` when the task is made: two methods of one class for the same type, a mark that disagrees with the parameter's annotation (resolved with `typing.get_type_hints`, so `from __future__ import annotations` is fine; one that cannot be resolved is not checked), more than one parameter, or `QuitMessage` (`quitMsg` handles it). A new handler gets its mark; a helper needs nothing. **A task's own names are taken too**: `CoreTask` has `stopped` (an `Event`), so a property of that name on `Application` failed in the base constructor (`Application.playback_stopped`).
- **HTML from outside is read with a parser, never searched with a regular expression** (#489). A feed's or an answer's markup goes through `html.parser`: `python/utils/html_text.py` (`html_text`: the text on one line, a block tag a space, scripts and styles not text; `html_images`: each `<img>`'s attributes) or a reader of its own on the same parser (the Comic's `strips.py` reads the text after a marker). The regular expressions they replaced ran paragraphs together, ate a `<` that opened no tag, kept a script's text and skipped an `alt=""`. A comic is a `Comic` record in `strips.py` (its feed, where the HTML is, how the title and caption are read), not code.
- **A text file is opened with `encoding="utf-8"`** (`test_storage_access` checks every `open` of ours that is not binary). The default is the platform's: UTF-8 on a Pi and in CI, cp1252 on Windows, so `load_json` wrote UTF-8 and read a schema's `°C` back as `Â°C` on Windows only. Anything that differs between the device and the development machine (encodings, line endings, paths, the shell) is fixed in the code, never left to the platform.
- **Test an object for `None`, not for truth.** A class with `__len__` is falsy while empty: `if self.sink:` dropped every message to a hub that had no events yet, including the first failure (found building `GET /api/status`). Use `is not None`.
- **A failure's cause is usually in what the change touched indirectly:** the watcher, the CI storage, a transitive dependency. Reproduce under CI conditions before concluding anything.

## Cutting a release

Only when the maintainer asks for one and names the version. **Before touching a version field or pushing a `v*` tag, read `RELEASING.md` in full**: it is the procedure (bump both version fields, verify, audit, merge, try the snapshot on a Pi, tag only on the maintainer's go-ahead for that version, watch `release.yml`, announce). It is kept out of this file because it is needed at one rare moment.

## Boundaries this repo has actually hit

- **A 403 on push means GitHub access is not connected for the session.** Stop and tell the maintainer; do not look for a way around it. Repository settings, secrets, and branch protection need the maintainer's explicit go-ahead for that specific change.
- **A PR's own CI can surface a real problem that passes locally** (the CI storage above). Fix it on the same branch; never skip, disable, or quarantine a test to get green.
- **A merged PR is finished.** Follow-up work goes on a fresh branch from the updated `master`, never on the merged branch.
