# Working on eInk Billboard

This file is for whoever (human or AI) is working **on** this repo. `CLAUDE.md` only imports it, so every agent reads the same rules.
The readme explains the architecture (layers, compositor, tasks, storage); this file is the working agreement.
Process lives in its own docs, indexed in `CONTRIBUTING.md`: **`WORKFLOW.md`** (idea to merged) and **`SESSION_SUMMARIES.md`** (how a piece of work is written up afterwards).

## What this is

An e-Ink "billboard" server for Raspberry Pi (and Windows/Linux development): a Python task-based backend (threads + `asyncio`),
a FastAPI web API, and a Vue 3 / PrimeVue settings app. It is developed on Windows and Linux; keep both working.

## Generalizing lessons in this file

Every rule below started as one specific bug in one specific place. Whoever adds the next one should write it up as the *underlying pattern*,
not just the file where it surfaced, and fold it into an existing entry when it has the same root cause rather than appending a disconnected one.
"After swapping a framework, check what it was installing for you" (below) is the model: it was found once with Flask and `jinja2`, but it applies to any dependency swap.

Before starting anything beyond a trivial change, read the last several posts of the Discussions category the session summaries go to (see `SESSION_SUMMARIES.md`)
and skim the most recent merged PRs for review comments nobody answered. A problem already found once should not be rediscovered from scratch.

## Layout

| Path | What |
|---|---|
| `python/eink-billboard.py` | Entry point (`main()`), starts the `Application` task and uvicorn |
| `python/web/` | FastAPI app: `app.py` (factory), `deps.py`, `errors.py`, `documents.py`, `routers/` |

| `python/model/` | Configuration manager/watcher, schedules, time of day, service container |

| `python/storage/` | NVE ("factory default") schemas copied into the storage root on reset |
| `python/tests/` | `unittest` tests; `fixtures/storage/` is the synthetic test storage (built into a temp folder per run) |
| `app/` | Vue web app (`npm`, Vite). Talks to the API through `src/components/ApiClient.ts` |

## Commands

```
uv sync --frozen --no-group device         # install (Python 3.13)
uv run python -m unittest discover .       # all tests (about 2.5 minutes)
uv run python -m unittest python.tests.test_web_api   # the API tests (about 1 second)

# run the app (storage root is created and seeded on first start)
uv run python -m python.eink-billboard --dev --cors http://localhost:5173 --host localhost --storage ./.storage
cd app && npm ci && npm run dev            # web app on :5173

cd app && npm run build                    # type-check (vue-tsc), then the production bundle -> app/dist (served with --app)
cd app && npm test                         # web unit tests (Vitest + jsdom), src/**/*.test.ts
cd app && npm run e2e                      # build, then the browser tests (Playwright) against two real servers
```

- `npm run build` runs `vue-tsc -b` first, which reports **zero** errors; keep it that way (a type error fails the build).
- The built app uses hash routes (`/#/settings`), and Vite's default layout: `index.html` and `public/` files at the root, bundles in `assets/`. The bundles are served `immutable` (their names carry a hash), everything else `no-cache` (`_mount_web_app`): an `index.html` with only a `Last-Modified` was kept by the browser, which ran the old app after an update. A tab that was open before an update still runs the old app until it is reloaded: the next page it opens asks for a chunk the update replaced, which is a **404** (a missing file under `assets/` is never the app's page, which a browser cannot run as a module: "Failed to fetch dynamically imported module"), and the app **reloads itself once** at that page (`StaleBuild.ts`, `router.onError`; the reload is marked in `history.state`, so a broken build does not reload for ever; not on `vite:preloadError`, which fires first and does not know the route). `stale-build.spec.ts` refuses the chunk until the tab reloads (Vite preloads it, then imports it).
- **Browser tests** (`app/e2e/`, Playwright Test): `playwright.config.ts` starts two real servers on a storage built by `scripts/e2e_storage.py` (the factory defaults plus the **synthetic** fixtures in `app/e2e/fixtures/storage`: schedules, a system settings file, a fake API key).
  No secret and none of the real test storage is involved, so they run on fork PRs. One server is open (port 8099), one requires a token (8098, `e2e-token`). They need `uv sync` and, once per Playwright version, `npx playwright install chromium` (CI does this itself). `@playwright/test` is no longer pinned to the cloud sandbox's preinstalled browser; a sandbox session installs the matching one the same way.
  `watchProblems()` in `e2e/support.ts` fails a test on any page error, console error, failed request, or HTTP error that the test did not declare, so a page that merely renders is not enough.
  Gotchas: the servers serve the **built** `app/dist`: `npx playwright test` alone runs the last build, so a build that failed (a `vue-tsc` error) leaves the old bundle under test; use `npm run e2e`, or build first. The app uses hash routes (`/#/settings`); PrimeVue option accessible names are not their text, so match options by visible text; the factory `location: null` leaves Save disabled, so the fixture sets one.
- CI: `.github/workflows/web.yaml` runs the `web` job (build, unit tests) and the `e2e` job (browser tests) on pull requests and pushes to `master`. They are not required checks until the maintainer adds them to the ruleset.
- **Logging:** production logs at INFO, `--dev` at DEBUG, `EINK_LOG_LEVEL` decides last; `watchdog`'s file events are WARNING everywhere. The setup code is a block of its own in the log (`setup_banner`), found with `grep "Setup code"`.
- Options: `--port` (default 8080 with `--dev`, else 80), `--token` or `EINK_API_TOKEN` (Bearer token on `/api`), `--app` (web bundle folder).
- Do not start the server with `pkill -f`/`pgrep -f` patterns that match your own shell command; start it in the background, record its PID, and signal that PID
  (`uv run` is a wrapper: signal the Python child, not the `uv` process).

## Test environment

- **No test needs a secret or a private storage.** `storage_path()` (`python/tests/utils.py`) builds one per test run in a temporary folder: the factory defaults (`hard_reset`) plus the synthetic schedules in `python/tests/fixtures/storage/` (nothing real, no keys). It is **read-only**: a test that writes copies it first (`WebApiTestBase` does), or builds its own with `temp_configuration_manager`. So the suite runs on a fork's pull request, in a cloud session and in the container with nothing to restore. The old `TEST_STORAGE_B64` secret and `prepare-test-data.ps1` are gone (#27).
  A fixture must stay valid for the data sources it names and use only ones the fake internet serves (a playlist track that fails strikes out and the layer tests then see an error). **Tests must not assume `datasources/` or `plugins/` content exists**: the factory storage makes a folder only for what has settings.
- The headless render tests need the headless browser: `chromium-headless-shell` on `PATH` (Linux), `chrome-headless-shell` on `PATH` (Windows), or whatever `EINK_CHROME` names (a path or a name on `PATH`, set in the environment or in a `.env` file at the repository root, see `.env.example`; no machine's path is in the code; `chrome_command()` in `image_utils.py`, read on every render). In the cloud sandbox:
  `ln -s /opt/pw-browsers/chromium_headless_shell-*/chrome-linux/headless_shell /usr/local/bin/chromium-headless-shell`.
- **No test needs the internet.** `python/tests/__init__.py` makes every `AsyncHttpWorkerPool` talk to `python/tests/fake_internet.py`, which answers the comic feeds, the Wikipedia API and the newspaper covers from text fixtures in `python/tests/fixtures/http/` and generated images (real ones are copyrighted); any other URL is a `ConnectError` naming it. A new download in the code under test needs a route there (and a fixture), not a real request.
  The text fixtures are hand-written in the sites' shapes; `uv run python -m scripts.record_http_fixtures` (needs the internet) replaces them with real answers, and `EINK_TEST_LIVE=1` runs the tests against the real network (the opt-in live check).
- `tkinter` is mocked in `python/tests/__init__.py`. In production it is imported only for the `tk` display, so a missing Tk fails that display and nothing else.
- **Never print, log, or commit the contents of storage files**: they can hold API keys. Inspect them with a command that cannot echo values (key names only), not `cat`.

  Before a PR, run `podman compose run --rm test` (below): it does what `.github/workflows/unittest.yaml` does (`ruff`, `mypy`, `coverage run -m unittest discover .`) on Linux with Chromium.
- **Containers** (`Dockerfile`, `compose.yaml`, `.dockerignore`):
  - `podman compose run --rm test` builds the `test` image (Python 3.13.7, `chromium-headless-shell`, `uv`, the locked dev dependencies) and runs the checks against the **bind-mounted checkout**. The virtual environment lives in `/opt/venv` (not `.venv`), so the container never touches the Windows one, and `PYTHONDONTWRITEBYTECODE` keeps `__pycache__` out of your tree.
    It needs nothing restored. Because it sees the working tree, an untracked file you have lying around is checked too (it once showed an unrelated `mypy` error that CI would never see).
  - `podman compose up --build app` serves the built web app and API on `http://localhost:8080` with the storage in a named volume (seeded on first start: a missing **or empty** folder is seeded, since a mounted volume always exists). `EINK_STORAGE=./.storage podman compose up --build -d app` mounts that folder of the checkout instead, used as it is (the app writes to it). The port is published on `127.0.0.1` only; set `EINK_API_TOKEN` before widening it (see the network-exposure issue, #36).

Check the log line "Watching ... by".
    The image has no display hardware (the `device` dependency group is left out), so it is for the API and web app, not the panel.
  - `podman compose --profile inky up --build -d app-inky` is the app with the **Inky driver installed** (the `device` group, which the other images leave out) on `http://localhost:8081`, to see what a device does when the driver loads and finds no board; `EINK_FAKE_INKY=ok|busy-stuck|spi-off|unknown-board` pretends there is one (`scripts/fake_inky.py` fakes only I2C, GPIO and SPI: the real driver runs on them), the last image it was given is `/tmp/fake-inky/fake-inky-last.png`. It has a storage of its own (`storage-inky`); set the Display Type to `inky` there and restart.
  - `podman compose --profile waveshare up --build -d app-waveshare` is the same for a Waveshare (`http://localhost:8082`, `storage-waveshare`): the vendored driver (`python/display/waveshare_epd`, VENDORED.md) really runs, `scripts/fake_waveshare.py` answers for the Pi's `/proc/cpuinfo`, `spidev` and the `gpiozero` pins (`EINK_FAKE_WAVESHARE=ok|busy-stuck|spi-off`). It found that a Waveshare driver's `init` waits on the busy line for good, so the display guards both starting and refreshing with a time. **The driver stage owns that guard** (`python/display/panel_guard.py`, used by the Inky and Waveshare displays): whatever talks to a vendor driver runs on a thread for a time, because six Inky models (`e640`, `e673`, `el133uf1`, `jd79661`, `jd79668`, `ssd2683`) and every Waveshare driver wait on the busy line with a loop that has no end; the Display task never waits on a panel, and a call that timed out blocks the next ones until it returns. A new display class wraps its panel calls in it.
  - **A consumer starts with `curl -fsSL .../deploy/bootstrap.sh | bash`.** Only what cannot be in the container is done on the Pi (apt: podman, git, curl, uidmap; SPI and I2C through `raspi-config nonint`; the spi, i2c and gpio groups; linger), each with sudo after one confirmation. Everything is in `main()`, called on the last line, so a cut download runs nothing; questions are read from `/dev/tty` (the script's own input is the download). The downloaded copy checks, plans, does the sudo steps and clones; then it `exec`s the clone's copy (`--from-clone`), so the steps always match the app being installed. It is idempotent: a re-run continues (after the restart it asks for when SPI, I2C or the groups changed: a group in the group list but not in this session needs a login, not another `usermod`) or updates. The display is asked and remembered (`~/.config/eink-billboard/display`); an Inky that does not answer is a warning (`detect`), never a stop. Port 8080; built on the Pi (prebuilt images later); `master` until releases are tagged (`EINK_REF`). Tested in a Debian container (a `uname` shim, a real tty through `script` and `su -P`), then **run start to finish on a Pi 5** (Bookworm, Podman 4.3, no panel): `check` all fine, every driver library loads on arm64 (`lgpio` included), and after a restart the systemd user unit with linger started the container again with the devices open.
  - **On a Pi, `deploy/eink-container.sh`** is the consumer's whole kit (update, build, start, logs, code, check, display, models, detect, autostart, reset-password, wipe): **the consumer needs no command but it** (`update` is git fetch, a fast-forward, build and start; `build` builds the clone as it is): plain `podman` (Bookworm has 4.3 and no compose), the devices that exist passed in with `--group-add keep-groups` (rootless: the user's spi, i2c and gpio groups; `/dev/gpiochip4` is a link and is left out), `EINK_PUBLIC_URL` from the Pi's address. It is written for someone who is not an expert: every failure says what to do, nothing destructive without a typed yes, never as root, settings changed only through the app's own code inside the container (`cob.save`), never printed. A heredoc of Python in it sets `sys.path` to `/work` first: importing `lgpio` moves the working directory to `LG_WD`. Check it with ShellCheck (`podman run --rm -v ./deploy:/mnt:ro docker.io/koalaman/shellcheck:stable -S warning /mnt/eink-container.sh`).
  - `podman compose` delegates to an installed compose provider: Docker Compose (the binary Docker runs as `docker compose`, found as `docker-compose.exe`) or `podman-compose`. With Docker the same commands are `docker compose ...`.
  - **Podman on Windows needs WSL 3.0+ and Podman 6.1+.** Each combination short of that broke containers differently (all found after one upgrade):
    an older WSL kernel (6.6) lacks nftables modules netavark 2.0 needs, so no container starts; WSL 3.0 with Podman 6.0 fails on cgroups (`controller pids is not available`);
    and Podman 6.0 publishes ports without a listening socket, which WSL does not forward to Windows `localhost`. Podman 6.1 fixes the last two **inside the machine image**,
    so after upgrading Podman, recreate the machine (`podman machine rm`, `podman machine init --rootful`, `podman machine start`; no Windows admin needed). Check with `wsl --version` (kernel 6.18+) and `podman version` (client and server 6.1+).
    Do not work around it by turning off the container firewall: containers then lose internet access too, and builds fail.
  - The Podman installer may move Podman (now `%LOCALAPPDATA%\Programs\Podman`, per user); `PATH` changes reach VS Code and its terminals only after a sign-out or reboot.
  - `podman machine ssh` from Git Bash leaves a file named `NUL` in the current folder (Podman passes `UserKnownHostsFile=NUL`); run it from PowerShell or delete the file.
  - The web stage keeps the repository layout (`/repo/app`, `/repo/python/tests`) because the type-check imports the shared rule cases from `python/tests`; copy any other cross-folder import it needs.
- **No secret goes into an image.** `.dockerignore` excludes `.storage` folders, `.env` files, and zips; test storage is only ever mounted.

## Core rules

- Python 3.13, **tabs** for indentation, type hints, `logging` (no `print`), config in JSON. Keep changes focused; do not reformat files you are not changing.
- **The web API.** Endpoints are plain `def` (they run in uvicorn's thread pool; the configuration code is blocking and lock-based), not `async def`.
  Errors are `ApiError(status, message, id)`, and every non-2xx body is `{ success: false, message, id }` (+ `rev` on 409, `errors` on 422). Never put exception text in a response.
- **Settings documents** carry `_id` and `_rev` (a content hash); a `PUT` must echo `_rev` or gets 409. Files are written atomically by `_internal_save`; never write settings files any other way.
  Anything that watches the files must therefore also handle a *move onto* the real file (the watcher reports the destination), not only modifications.
- **IDs from URLs are untrusted.** Plugin and datasource IDs must come from `cm.enum_plugins()` / `cm.enum_datasources()`; never build a path from a raw URL parameter.
  Validating is not enough for the analyser (or a reader): what builds the path must be **our own value** (the constant from our list, the ID declared in the descriptor), not the URL's string that passed a check. Files served for a URL are resolved with `realpath` and must start with the folder's prefix (see `_file_in_bundle`), which also stops symbolic links.
  Error bodies do not echo the URL's text back. CodeQL's `py/path-injection` alerts are about exactly this; fix the flow, do not dismiss the alert.
- **Secrets.** A schema property with `"writeOnly": true` is masked (`********`) in GET responses and kept when the mask, or nothing, is sent back. Mark any new key/token/password property that way.
- **Form field rules are written twice and must agree.** The form (`app/src/components/FormValidation.ts`) and the server (`validate_properties` in `python/web/documents.py`) apply the same rules to a descriptor's properties; the cases both must pass are in `python/tests/form_rules.json` (run by Vitest and by `test_web_api`). Change a rule in both places and add a case.

  | Property | Rule (message) |
  |---|---|
  | `required: true` | not null / not empty ("Required"). Optional properties may be `null` (unset) |
  | `string` | with `enum`, or an `items` lookup: one of the values ("Not one of the allowed values"); a URL lookup is not checked. `minLength` / `maxLength` ("At least N characters", "At most N characters") and `pattern` ("Not in the expected format") apply to a value that is there (`""` is unset); a `pattern` must read the same in JavaScript and Python `re` (no named groups, lookbehind or inline flags) |
  | `number`, `integer` | `minimum` / `maximum` inclusive, **including 0** ("Minimum N", "Maximum N"); `integer` has no fraction ("Whole numbers only") |
  | `string` with `format: "uri"` | an address: a scheme, `://`, a host, no spaces; the scheme is one of `schemes` (default `http`, `https`) ("Enter a valid URL"). The same expression is in `FormValidation.ts` and `documents.py`; shown as a URL input |
  | `string` with `format: "date"` | `YYYY-MM-DD`, a real day ("Expected a date (YYYY-MM-DD)"); shown as a date picker |
  | `string` with `format: "color"` | `#rgb` or `#rrggbb` ("Enter a color like #3366cc"); shown as a color picker beside the hex (`ColorField.vue`), in a row too. Our own `format` value (JSON Schema leaves unknown formats as annotations) |
  | `string` with `format: "multiline"` | text of several lines, shown as a text area (`Textarea`, grows as it is typed in; `rows`, 1 to 20, is its starting height, default 3). No rule of its own: `minLength`, `maxLength` and `pattern` apply as for any string. Our own `format` value; not for a `writeOnly` field (a secret is one line) |
| `location` | `{latitude -90..90, longitude -180..180}` |
  | `schema` | a string; the form also checks it is one of the available plugins/datasources |
  | `boolean` | optional booleans may be `null` (unset) |
  | `array` | a list of flat objects: `items: { type: "object", key, properties }`. `minItems` / `maxItems` ("At least N items", "At most N items"); each item follows the rules of its `properties`; the `key` field's values are unique ("Must be unique", on the later row); not a list: "Expected a list". A 422 path is `[name, "<row>", "<field>"]`; a row that is not an object: "Expected an object". Item fields are `string` (with `enum`, `pattern`, `format`, ...), `number`, `integer` or `boolean`, never a nested list (`test_web_api` checks). Inside a row: a `visibleIf` reads **that row's** fields (a hidden one is not checked and is saved as `null`, row by row); a `lookup` names one of the descriptor's lookups (shown as a `Select`); a `writeOnly` field is masked per row and restored from the stored row with the **same key** (so it needs `items.key`; a renamed row's mask cannot be matched: "Enter the key" at `[name, "<row>", "<field>"]`). A row with more than four fields is shown as a block of labelled fields |
  | `array` of `string` (multi-select) | `items: { type: "string", enum? }`: the values chosen from `items.enum` or the property's `lookup`, shown as a `MultiSelect`. Each value one of the choices ("Not one of the allowed values", path `[name, "<index>"]`; a `null` in the list: "Required"); `minItems` / `maxItems`; `[]` is none chosen. A settings lookup is closed on the server as for a string |
  | `string` with `tokens` | the fields a text may use: `[{ name, description }]`, shown under the field (a list of what each stands for). A `{name}` in the text that is not listed: "Unknown field {name}"; `{{` and `}}` are a literal brace and any other brace is plain text. An empty list: no field may be used |
  | `header` | no value, never validated |
  | `description` | shown under the field as help text (any property) |
  | `link` | `{ url, label }`: a button under the field that opens someone else's page in a new tab (where to get an API key); `url` is `https` (the form shows nothing for another scheme), `test_web_api` checks the descriptors |

  **Descriptors use JSON Schema keyword names** (`title`, `type`, `format`, `minimum`, `maximum`, `minLength`, `maxLength`, `pattern`, `enum`, `const`, `default`, `writeOnly`, `items`); the old names (`label`, `min`, `max`, `secret`, `int`, `date`, `eq`, `ne`, `in`) are gone, and `test_web_api` fails on them.
  Our own keywords keep bare names, which JSON Schema ignores: `required` (a boolean on the property, not the array of the standard), `lookup`, `visibleIf`, `step`, `minFractionDigits`, `maxFractionDigits`, `header` and `description` as help text. Never give a standard keyword a different meaning.
  A property of a type neither side knows is not checked. A `number` shows the digits its descriptor declares (`step`, `minFractionDigits`, `maxFractionDigits`); only `integer` forces whole numbers. **`step` is a hint, not a rule** (#89): it is the increment of the input's up/down buttons, and neither side checks it, so a stored `0.15` on a `step` of `0.1` is valid (a grid check would fail on float arithmetic and reject values typed into a file by hand); `minimum`, `maximum` and `integer` are the checks.
  A descriptor's `instanceSettings` has no `default` document: each property carries its own `default`, and `test_web_api` checks the defaults against the rules, the field names (no `.`, `[`, `]`: PrimeVue reads them as paths) and the types.
  A `schema` field's choices are the sources whose `features` match the lookup's (the form offers only those; the server rejects the others). A lookup that fails to load shows a message under the field, never an option.

  **A Test button** on a `string` field (or a field of a list row): `"test": { "url": "/api/..." }` names a route of ours that gets `{ "value": ... }` and answers `{ "ok": true|false, "message": "..." }`; the form shows the message beside the field and clears it when the value changes. The browser never fetches the address itself (CORS, and the server is where the data source runs): the route does, with the data source's own code. A route like this gets an address from whoever is signed in, so it must refuse what it should not reach and never put exception text or the address in its answer. `python/utils/url_guard.py` is the guard: only http(s); every address the host resolves to must not be loopback, link-local (the metadata address), unspecified, multicast or reserved; the home network is allowed; redirects are followed by `fetch_checked`, which checks each hop. Not caught: a name that answers differently when the client connects (DNS rebinding). The RSS Feed route (`python/datasources/rss/api.py`) is the model: a plain `def` that runs the check in `asyncio.run` with a client of its own (the web app has no HTTP pool; the layers each make theirs) and always answers 200 `{ ok, message }`.
  **A list kept in settings, one entry chosen per task.** A plugin or data source keeps an `array` in its own `settings` (a feed list) and its `instanceSettings` offer the entries through a `settings` lookup:
  `"lookups": { "feed": { "settings": "feeds", "value": "name", "label": "name" } }`, used by a `string` property with `"lookup": "feed"`. The task stores the entry's `value` (its `key`, so reordering the list is safe; a renamed or deleted entry shows as a stale value the user must choose again).
  The choices are served by `GET /api/datasources/{id}/lookups/{lookup}` (`/api/plugins/...` likewise), for a lookup the descriptor declares; the form reaches it through `BasicForm`'s `owner`. Unlike a URL lookup the server can check membership, so a value that is not an entry is a 422 (and nothing is allowed while the list is empty).
  A field of the **settings themselves** may use a `settings` lookup too (a calendar row naming an account of the same settings): the server checks it against the document being saved, so an entry added in the same save is a choice; the form's list (`SettingsForm`'s `owner`) is the stored one until then.
  The RSS Feed data source is a second: its `feeds` (`name`, `url`, http or https only) are in its settings, a task picks one by name, and it is a list source (`media-list`) with one story per slide for the Slide Show plugin; its page is `render/rss.html`. The Image Folder data source is the first user: its `folders` (`name`, `path`) are in its settings, and a task's `folder` is a name (an unknown name is a `PermanentError`). Tests that run it write its settings first (`save_datasource_settings`).

A master's code asks what the task chose, so a `schema` field stands for `uses`. An API data source chosen where a page source belongs (an `openai-image` track from before) is refused with where it went ("... is now chosen inside Generated Image"). **A settings document serves masked any value its schema does not declare** (`get_document(declared=)`): a key left by a setting that moved away is not sent as it is. The browser tests answer the provider's lookups in the browser (`page.route`), never OpenAI.
  **OpenAI asks OpenAI what the key may use** (`python/datasources/openai_api/`): the image and text model fields are URL lookups served by the provider's router (`/api/datasource/openai/lookups/image-models`, `/text-models`, `/qualities`; `/models` says what each image model takes; `/test` checks a key), from OpenAI's model list with the **saved** key (read on the server). The list gives only ids, so what a model takes comes from its family in `models.py`, found by the id's prefix (a dated snapshot or a new `gpt-image-*` needs no change): every GPT image model takes three fixed sizes, `gpt-image-2` and later any `WxH` (multiples of 16, 1:3 to 3:1), so the picture is asked in the panel's own shape; a quality the model lacks is the nearest one below. DALL·E is retired (a stored task says so, a `PermanentError`). Model names change every few months: never put one in a list in the descriptor, only a `default`. The SDK gets an HTTP client of ours (`openai_client`: `tls_context`, and the tests' fake internet, which answers `api.openai.com` by the key: `sk-good`, `sk-busy`, `sk-broke`, any other a 401); a failure is our words and OpenAI's error code, never its text (a 401's text quotes the key).
  **Google AI is a second provider, with the same parts** (`python/datasources/google_api/`, `google-text`, `google-image`): REST through our own client (`tls_context`, the tests' fake internet), no SDK. **The key is an AI Studio authorization key, `AQ.`** (the older `AIza` standard keys are refused: the settings field has the pattern, and the provider refuses any other before asking Google), sent **only in the `x-goog-api-key` header**: never in the address (where `AQ.` keys are refused, and logs show addresses) and never as a Bearer token. Google's errors are its status word and our sentence, never its message. **Google describes its API itself**: the discovery document (`https://generativelanguage.googleapis.com/$discovery/rest?version=v1beta`, public, no key; kept for `discoveryCacheHours`) lists the `ImageConfig` aspect ratios and sizes and the `responseModalities`; `models.read_discovery` takes an enum where the schema has one, else the values in backticks in the description, and falls back to today's values (logged) when it cannot be had, so a new ratio needs no change here. Its model list has **no output modality**, so which models draw is a rule by id (`-image`, `nano-banana`), with the limits Google documents outside the schema as exceptions (Flash Lite Image takes only `1K`, Nano Banana no `512`). The picture is asked at the discovered ratio nearest the panel's, at the size the quality asks (Auto/Low/Medium 1K, High 2K, Xhigh/Max 4K, clamped to the model). `imageModel` and `textModel` are one name for each provider's own list (`SAME_NAME_DIFFERENT`); the **fake Google** (`fake_internet.py`) keys on the header (`AQ.good`; `AQ.busy` 429; `AQ.broke` the unsupported key type), refuses a key in the address, serves the model list in two pages, and checks the ratio and size against the discovery fixture. **A write-only field's mask passes the length and pattern rules** (the stored value is checked once restored): on the form and the server alike, with a shared case in `form_rules.json`.
  After a save, `SettingsForm` reloads the document: the saved values are the form's new baseline, so it is not "changed" and leaving the page does not ask to discard.
  **A row action** (`items.action: { url, label }` on a list of objects with a `key`): a button on each row that runs steps of ours for the **saved** row, found by its key (`RowAction.vue`). The steps are:
  - `POST {url}/start { key }` answers what to show (`message`, `link`, `code`, `input`, `poll` seconds) and a `session`;
  - then `{url}/continue { session, value }` or `{url}/poll { session }`, until `{ done, ok, message }`.

A refused refresh is a `PermanentError` ("Sign in ... again"). A provider's error reaches a message only as its error code, never its description.

  **Conditional visibility.** A property may carry `visibleIf`, a predicate over the other fields' values (`app/src/components/FormVisibility.ts`, `python/web/visibility.py`, cases in `python/tests/form_visibility.json`):
  `{ "field": "x", "const" | "enum" | "set" | "contains": ... }` (`contains`: a list value, a multi-select, holds it), combined with `all` / `any` / `not`. Names are the form's field names (children of a `schema` field share them); unset (missing, `null`, `""`) reads as `null`.
  A hidden field is not applicable: it is not validated (a hidden `required` does not block) and is **saved as `null`**, by the form and again by the server.
  **A setting that only fits one kind of data source reads what the source says.** A `schema` field (a plugin's data source) also has values derived from the source it chose, which a predicate may read: `<field>.features` (its features: `contains`) and `<field>.keepsList` (true when its list outlasts a visit); the form derives them from the choices it offers (`derivedValues` in `FormVisibility.ts`) and the server from the descriptors (`derive` in `visibility.py`), nothing chosen reads as no features and not kept. The Slide Show's *Slides in a List* and *Fetch Again After* are shown only for a source that keeps a list (`dataSource.keepsList`); a picture of the day has none, so they are hidden, not validated and not defaulted for it (a stored value stays harmless). **A source of one picture** (`media-image` without `media-list`: a picture of the day, a generated image) is one slide: *Max Slides* is shown only for a source with `media-list` (`dataSource.features` contains it) and the plugin ignores a stored count for the other (`is_single_picture`). `test_web_api` checks every descriptor's `visibleIf` for unknown fields and cycles.

- **The form reads the schema, not only what is mounted** (`BasicForm.vue`, #257). A field of a data source mounts only after the field it depends on (`visibleIf`) is set, so for a moment it is in the schema and not in the form's values: validating only the mounted fields reported `Required` on a field that then showed its value (a calendar track after a weather track: both have `views`). So the rules and the save read `withSchemaValues` (the values the form opened with, defaults included, for a schema field not mounted yet); a new track's defaults are those of **its** data source (`localValues` is taken before the fields are built); and a field that is shown with no value takes its default (`takeDefault`: stored as `null` while hidden, or older than the field).
  **A stored item is compared with the schema** (`showChanges`, on in the settings, playlist and task forms): a property the schema defines and the item lacks is tagged *new* (it starts at its default), one the item has and the schema no longer defines is listed dimmed under *No longer used* **by name only** (a value can be a secret) and is left out when saved (every editor sends only the validated fields). A document with no properties yet is new, and nothing in it is marked.
  **`test_item_audit` pins the descriptors' conventions** (every property has `title`, `description` and a `default` key, null where the user supplies it; a required property without a default is listed on purpose; one name means one thing, or is listed with the reason; a plugin and its data sources share no name) **and checks every stored fixture item** (no property the schema does not define, none required missing, the declared types).
- **An item runs at the descriptors' defaults, not at each plugin's own fallback.** The layers fill what a track or task lacks from its plugin's and chosen data source's `default` before the plugin runs (`content_with_defaults`, `python/web/documents.py`; a null default and a hidden field are left), so an item never saved again (older than a property, or written by hand) behaves as the form shows it. The stored file is not changed. A plugin's `settings.get(name, fallback)` is only a last resort; when you add a property, its descriptor `default` is the value (`test_item_audit`).
- **A picture whose shape is not the panel's gets a blurred margin, not white bars** (`blurred_margin` in `python/utils/image_utils.py`): the whole picture, uncropped, centred on a blurred enlarged copy of itself (the blur grows with the canvas). The Image Folder, Wikipedia Picture of the Day, Newspaper and Generated Image sources use it (`enlarge=False` keeps a small picture at its size); a new image source does too. The Comic keeps its white page on purpose (a panel and its caption on paper).
- **A plugin and its data sources agree on features** (`test_layer_features`). A data source declares the layers it can serve (`layer-background`, `layer-foreground`, `layer-priority`, `layer-overlay`) and the media it makes (`media-image`, `media-list`). A plugin advertises its layer and the media it handles, and its `dataSource` lookup asks for **its layer**: Slide Show `layer-background` + `layer-foreground`, Priority Update (`interstitial`) `layer-priority`, Overlay `layer-overlay`. So a source that is only `layer-background` is never offered to a timer task, and a plugin is never offered media it cannot handle. A new source or plugin keeps the test green.
- **The feature lists say the same thing the same way** (`TestFeatureVocabulary` in `test_layer_features.py`; the words and their tooltips are in `ItemInfo.vue`). Listed in this order: what it needs (`internet`: it downloads itself; `filesystem`; `api-key`; `paid-service`), what it is (`api`: a data-only provider; `api-client`: it asks an API data source, by `uses` or by choosing AI parts, and so does not also claim `internet`, the provider downloads; `ai-provider`, `ai-text`, `ai-image`), where it can be shown (`layer-*`), what it makes (`media-*`). **Background or foreground**: a picture that overlays may draw on (a photograph, a generated or folder image) is `layer-background`; a page with text that must not be covered (a comic, a cover, a newspaper, a calendar) is `layer-foreground`, because overlays are drawn only over a background page. The Plugins and Data Sources settings tabs show a descriptor in one table (`ItemInfo.vue`: name, id, version, enabled, description, features, and for a data source what it uses and whether it keeps its list), one attribute to a row.
- **A descriptor says how a use of it reads.** `describe` (a plugin's or a data source's, beside `name`) is a line with `{field}` placeholders over its `instanceSettings`; the playlist editor fills it from a track's content (`app/src/components/Describe.ts`: unset values drop out, a `schema` field reads as the chosen source's own line, "Comic XKCD"). `test_web_api` checks the placeholders are fields. A new plugin or data source gets one.
- **Timer tasks are changed one at a time** (`python/model/schedule_store.py`, routes under `/api/schedule/timer`): `POST` a document or a task, `PUT`/`PATCH`/`DELETE` a document (`/{doc}`) or a task (`/{doc}/items/{item}`).
  The server generates ids (document `tasks-<uuid>`, which is also its file name; task uuid); a URL id only selects among the ids found in the stored files. `_rev` is the hash of the parsed form, per task and per document, so changing task A never conflicts with a change to task B; a stale `_rev` is a 409 with the current `rev`.
  `PATCH` of a task is a JSON Merge Patch (`null` removes a key, `trigger` is replaced whole). A 422's `errors[].path` is relative to the task (`["task","content","slideMinutes"]`, `["trigger"]`); unknown keys are rejected, not dropped. Always read-modify-write through the store (a lock per file, then `_internal_save`); never write a schedule file any other way.
  **A timer task in a file that did not come through these routes** (edited by hand, seeded) is checked when the timer layer loads or reloads (`TimerLayer._check_tasks`): the trigger and the plugin's settings, by the same rules as the routes. A task that fails is skipped (the others run) and reported once as a `task-failed` event with the first problem in our words; a disabled task is not checked, and a plugin that is not there is left to its error page when the task fires. A file that does not parse (a missing `task` or `trigger`) still fails the whole load, and the schedule in use is kept.
- **A playlist is a self-contained document**, saved whole: `/api/schedule/playlist` has `POST` (create), `GET`/`PUT`/`PATCH` (rename)/`DELETE` per document, no single-track routes. The editor keeps a working copy (apply a track, add, move, remove) and one Save sends all of it; **a new track is a draft** (`draft` in `PlaylistEditor.vue`): edited like the others and shown dashed at the end of the list, but not in the working copy, and not an unsaved change, until it is applied; cancel, or choosing another track or playlist, drops it, so nothing invalid is left behind; a user may have many playlists. The same store, rev and 422/409 conventions as the timer tasks; a 422 path is `["items", "<index>", "content", "<field>"]`.
- **Configuration changes reach every task.** The watcher's debounced file events go through a `FanoutSink` (evict the cache first, then the `Application`), which broadcasts `ConfigurationChanged(area, type, path)` (`area` from `ConfigurationManager.area_of`) on the `configuration` route to the display and both layers; a task that cares handles that message. The timer and playlist layers coalesce a burst of `schedules` changes (2 s) and re-plan when their part changed; a schedule that does not load keeps the one in use; startup tasks do not run again. The display only logs it (live reconfiguration is not built).
- **Dates crossing the API name their zone.** Every instant the server sends carries an offset (`start_ts`, `end_ts`, `scheduled_time`), and the response names the device zone (`timezone`); the browser reads days and minutes in that zone, not its own. An instant the server receives must carry an offset or `Z` too (`start` of `/tasks/render`: a time without one is a 422); a bare `YYYY-MM-DD` is allowed because it names a calendar day, which has no zone. The wall clock is `ConfiguredTimeOfDay` (system settings `timezoneName`, read on every call).
- **A new device has nothing scheduled, and that is a state, not a failure.** The web app's landing page (`/`) opens the playlist page when there is no playlist (`router/index.ts`: only the landing page, any other address is the user's choice). The factory storage has no playlist and no timer task (and git keeps no empty folder, so seeding makes the `schedules` folder itself, and every start puts it back in `ensure_folders`, for a storage seeded before): `ScheduleManager.validate` warns and lets both layers start, the playlist layer shows the "Nothing to show" page ("Create one in the web app and schedule it"), and a user may delete the last playlist. `NewDeviceHasNothingScheduled` runs both layers on a bare `hard_reset` storage. An emptiness that a layer can say on the panel never raises.
- **Play, stop and next belong to the playlist layer, and every plugin handles `resumed`** (#354, the readme's "Transport"). A command goes to `Application.transport(command)` first, which forwards on the `playlist-layer` route (the timer layer is not on it). **Stop** cancels the track and sets `halted`: anything that would start the layer (`StartPlayback` from a reload, the restart timer, the end of a pass) must check it. **Play** and a schedule reload re-enter the interrupted track with `PluginExecutionContext.resumed`; the layer decides nothing about what that means, **the plugin does** (the Slide Show continues a kept list and passes on, returning at once, for a single picture, an unkept list or a used-up one). A plugin class says `resume_contract = "honours"` (the playlist layer runs it) or `"ignores"` (the timer layer does, and never sets the flag); `test_transport` fails for a plugin that says neither, so a new plugin cannot forget it. The track the layer is on is `Position` (ids and indexes: an edit moves the indexes), and a pass starts at `Start(playlist, track, resume)`. **"Did the schedules change" compares the files as loaded** (`_snapshot`, `_loaded`), never the tracks the layer ran: running a track fills its defaults into the object, so comparing those reported a change on every save (a timer task's included).
- **A failing track strikes out, it does not spin.** The playlist layer counts consecutive failures per track: a transient one is a strike (three, the system setting `maxStrikes`, and the track is struck out: it is **not run, its slot shows its error page** instead), a permanent one (`PermanentError`, `ImportError`, `TypeError`, `AttributeError`, a plugin that is not there, settings that fail `plugin_content_errors`) strikes out at once; a success clears the strikes. A pass where nothing succeeded waits (1 s doubling to 60 s). **A strike-out is not for ever** (found when a comic that timed out stayed on its error page until the device restarted): a struck-out track is tried again after `strikeRetrySeconds` (60 by default; one attempt, a probe, struck out again if it fails with the wait doubled up to `strikeRetryMaxSeconds`, 900), and a success clears it; all three are system settings, read at each use (`_policy`), with the class constants as the fallback. When every track has struck out the layer is `faulted` (one telemetry message) and a timer tries again when the first is due (`RetryStruckOut`); a `ConfigurationChanged` of any area also does, and clears the strikes. Anything that gives up on something that may recover needs a way back (a retry time, a probe), not only a person's edit. A plugin that cannot be fixed by trying again should raise `PermanentError`.
- **A rendered page is one template.** An HTML-rendered page (`render/<name>.html`, extending `static/render/plugin.html`) carries its own CSS in its `{% block style %}`; there is no per-page stylesheet and `RenderSession` takes no CSS file. Only `plugin.css` (the base) and `themes.css` (the theme roles) are shared files, linked by `RenderSession`. Page CSS cannot contain `{{`, `{%` or `{#` (Jinja reads them). `plugin.html` carries a Content-Security-Policy (no script, no network: styles, fonts and stylesheets are our files, pictures are embedded as `data:`), because Chromium runs with `--no-sandbox`; a page that needs a remote resource embeds it first (as the RSS pictures are), it does not link to it. `test_error_image` renders a page with a script to prove it does not run.
- **The theme is computed in Python and cascades into CSS** (`python/model/theme.py`). The device theme (`theme-settings.json`: scheme, hue, saturation, lightness) becomes a few HSL inputs; `RenderSession` writes them into `:root` (`plugin.html`), and `themes.css` derives every role class (`text-primary`, `bg-secondary-1-accent`, ...) from them with relative color syntax, `hsl()` only. PIL code takes the same colors from `Palette` (`current_palette(scm)`, read on every render), so it is in theme too. Pages do not pick a scheme; every page wears the device theme. A new role is added in both places (a `Palette` field and a class); `test_theme` checks the class list and renders a swatch per role in Chromium against `Palette`. Design pages so they still read when both secondaries are the same hue (complementary, monochrome): tell parts apart by tone (light, accent, dark), not only by hue.
- **Typography is part of the theme.** `fontBody`, `fontHeading` (unset: the body font), `fontOverlay` (the overlays' text; unset: the heading font) and `fontScale` (0.8-1.4) are in the theme settings and in `ThemeInputs`; `css_vars` writes `--font-body`, `--font-heading`, `--font-overlay` and `--font-scale` into `:root` (family names unquoted: the page escapes quotes), `plugin.css` sets the body font, and PIL code reads `current_typography(scm)`. **A page sets no `font-family` of its own** (`test_theme` checks): headings use `var(--font-heading)`, overlay text `var(--font-overlay)`, text sizes are multiplied by `var(--font-scale)` (the calendar multiplies in `Layout`, which counts events from the text size). A figure that is sized to fill its page (the countdown's number, the year, the error page) is not scaled, so it still fits. Only families in `FONT_FAMILIES` are accepted, and `/api/fonts/{family}` serves a file from that table, never a path from the URL. **The page background** is a theme setting (`background`: `white` by default, `tinted` = the theme's light tone, `black` = dark mode); every page's container is `bg-page` (`--page-bg`), and the compositor's fill is `Palette.bg_page`. White is the default because a color e-ink panel has only a few pure colors and dithers a tint. Black swaps the light and dark tones (`l_text_dark`/`l_text_light`, `l_bg_light`/`l_bg_dark`) so every `text-*` and `bg-*` role stays readable on it; a page never hard-codes white or black. The Theme tab shows a sample in the real fonts. It also shows every role of the palette, computed by the server for the form's values (`POST /api/theme/palette`, the same `palette_of` as PIL), never re-derived in the browser.
- **Deployment is the container** (the readme's "Set up a Raspberry Pi", `deploy/bootstrap.sh` and `deploy/eink-container.sh`, below under Containers): a non-root user's rootless Podman, port 8080, the token passed to the container by name (never on a command line, which the process list shows). The old systemd unit for an install without a container is gone.
- **Who may use the device** (`python/web/access.py`, #36): there is no default credential. A device on the network starts *unclaimed*, logs a one-time **setup code** (and draws it on the panel through `Application.setup_notice`: a page with no expiry, so it holds the panel until the device is claimed, and the **layers are not configured until then**: `Application` keeps their `ConfigureEvent`s and sends them on `SetupDone`, so no track or timer task goes into play mode on a device nobody owns; a replaced code is redrawn, `SetupCodeChanged`), and whoever enters it at `POST /api/access/setup` chooses the password (kept as a salted scrypt hash in the `access` settings, which is not in `DEVICE_SETTINGS`, so no route serves it). `--token` / `EINK_API_TOKEN` stays the script credential and counts as claiming; `--no-auth` keeps a network device open on purpose; `--require-auth` applies the rules on a local bind (the browser tests); `--reset-password` forgets the password. A device bound to `localhost` is open until a password is set. Routes use `require_auth`; `EINK_SETUP_CODE` fixes the code for tests.
- **The server answers only to names it expects** (`python/web/hosts.py`, DNS rebinding): `localhost`, any IP address, this machine's name and `<name>.local`, and `--allow-host` / `EINK_ALLOW_HOSTS`; any other `Host` gets 421 in the error shape, on HTTP and on the telemetry WebSocket. The tests allow `testserver` through the environment (`python/tests/__init__.py`). A failed `POST /api/session` is logged (address and count, never the token) and the client waits longer after each one past three (`SignInThrottle`: 429 with `Retry-After`, no wait on a server thread).
- **An HTTP client of ours is made with `verify=tls_context()`** (`python/task/async_http_worker_pool.py`; `test_tls_context` scans for the rest). The container's OpenSSL 3.5 puts a post-quantum hybrid key exchange group first in the TLS 1.3 handshake, and some hosts (webcomicname.com on Tumblr) answer by dropping the connection: `RemoteProtocolError: Server disconnected without sending a response`, only from the container (the Windows host's older OpenSSL, `curl` and a browser were fine, and TLS 1.2 worked in the container too). The shared context offers P-256 only, which every TLS 1.3 server accepts. A failure that is the same address in one place and not in another is the stack, not the address: compare the TLS version and groups before the headers. **A client names its timeouts**: httpx's default is 5 s for connecting and for each read, which a small board on a slow link or a slow site (Dinosaur Comics, whose picture redirects to another host) does not meet; the shared pool's client is `REQUEST_TIMEOUT` (30 s, connect 15 s), and a client of our own sets one.
- **Every download of an address that is not our own constant goes through the URL guard.** `stream_to_buffer` (images and feeds) is guarded by default and `stream_checked` (`python/utils/url_guard.py`) is the same for any method: the address and every redirect are checked (not this device, not link-local, ...), because the address is typed in a settings page or taken from a feed, an answer or a redirect (found by the OWASP pass, #189). A new download uses one of them; `guarded=False` is for a constant only. The tests' fake internet makes every fake host resolve to a public address; a test of a refusal patches `url_guard._resolve` or uses an address literal.
- **Every file of the storage goes through the configuration manager, by name.** `ConfigurationManager` is the only holder of the storage root; it builds the sub-managers (settings, schedules, plugin, data source) and each gets a **local root** from it: the chain of trust on paths. A caller names a file (`dsm.file("tokens")`, `schedule_manager().read("tasks-x.json")`, `cm.read_schema("theme")`), never a path, and a name is checked to be a leaf (`leaf_name`), so nothing outside a sub-manager's root can be reached. Only `model/storage_files.py` (`save_json`: atomic; `load_json`), `configuration_manager.py` and `schedule_manager.py` open, write or delete files; `test_storage_access` fails on any other module that does (the few non-storage uses are listed in it: render scratch files, `/etc/timezone`, the log configuration, the mock display's output in the system temp folder). **A folder exists because something was written to it:** `save_json` makes the parent folder, a lookup or a read makes none, so a plugin or data source without settings or files has no folder. Folders the **user supplies** (the Image Folder's) are read in place, read-only, and are not storage. The calendar's `tokens.json` was the case that broke the rule (its own `open`, `makedirs`, private save); a new data source that needs a file of its own asks its `DatasourceConfigurationManager`.
- **A media list can outlast a visit, and the plugin that shows it keeps it** (`python/plugins/kept_list.py`, #222). The Slide Show opens the data source's list (`open_async`), shows the head, drops it and saves the rest in `plugins/slide-show/list-<hash of the slot>.json` (through its `PluginConfigurationManager`); only when nothing is left, or the list is older than the task's `refreshHours`, does it open the data source again. The **slot** is `PluginExecutionContext.slot`, the playlist's id and the track's (track ids repeat across playlists, so a track id alone is not an identity), and a slot runs one visit at a time, so there is nothing to share, lock or retry: two slots on one feed each have a list. A file carries a fingerprint (the data source, the task's settings that choose the list, the data source's settings revision), so a slot pointed at another feed starts anew. The **task** chooses `listMode` (`continue`, the default, or `restart`: a new list every visit) and `refreshHours`; the plugin's settings choose `staleDays` (a list unused that long, a deleted track's, is removed; 0 never; every file records `last_used`). The **data source** only says `"keepsList": true` in its descriptor (RSS Feed, Image Folder, Comic: every feed or folder is shown item by item until it is used up, then fetched again and started over, so new items turn up in time; no tracking of what was seen, `refreshHours` defaults to 0 = only when used up; `test_item_audit` lists the sources that are not kept): a source whose list is made fresh every time (the calendar's and the weather's pages are views of now) never is. An item is dropped once it has been shown (or failed), so a restart or cancel does not show it twice; an old list is used when the origin does not answer; a list that cannot be kept (too big, not JSON, an unwritable disk) is used from memory, so a slide is never lost to the disk. Another plugin that shows a list uses `open_list`. **A data source is called from several threads at once** (`open_async` and `render_async` run on the playlist layer's loop and the timer layer's, and for the settings routes' tests): it keeps no mutable state on the instance, or guards it; its files go through the configuration manager, whose objects lock and check the revision.
- **The generators' system prompts are the Master Prompts, a device-wide settings document** (`master-prompts`, its own Settings tab; #271): `inventInstructions`, `inventRequest`, `rewriteInstructions`, `rewriteRequest` and `canvas`, read by `python/datasources/ai/prompt.py` (`master_prompts`, `rewrite_request`, `with_canvas`) for the Generated Image and its image parts; nothing is hard-coded in Python. **The factory text is the `default` of the schema shipped in the NVE** (`python/storage/schemas/master-prompts.json`): a new storage is seeded with it, `GET /api/settings/{name}/defaults` serves it (`ConfigurationManager.shipped_settings`, from the NVE and not the stored schema or document), and the form's "Restore default" (a field) and "Restore defaults" (the tab) put it into the form for the user to save or not; a value missing or empty reads as the factory text. A new prompt is a new property in that schema (and its default). **A text's fields** (`{name}`, `{{` and `}}` for a brace; `python/utils/prompt_tokens.py`, `PromptTokens.ts`): a string property with `tokens: [{ name, description }]` may use only those names (any other is "Unknown field {name}" on the form and from the server, a shared case in `form_rules.json`), and the form lists them under the field. **Whatever supplies the values supplies that list**: a data-only source says its `tokens` (names with descriptions) and fills them, so a field is never a guess. A field with no value drops out of the text.
- **The Weather Visualizer** (`python/datasources/weather_image/`, #271) is the Generated Image with a prompt that talks about the weather, and the model of a prompt whose fields are **supplied by a data-only source**: OpenWeatherMap's descriptor lists `tokens` (names with descriptions) and its class implements `DataSourcePromptFields.prompt_fields(report)` (only what is known; a field with no value is left out; `test_weather_image` checks the two agree). - **Comic Vine is the second API data source with a key in the address** (`python/datasources/comicvine/`, asked by Comic Vine Covers, `comic_vine/`, #237): the same shape as the weather (a page source `uses` an `api` source). `api_key` is hidden in the `httpx` log lines (`HideKey`), its failures are our words with the site's status code at most, and it sends a browser-like `User-Agent` (the site refuses the HTTP library's). - **An origin's answers are kept by the data source, for all its tasks** (`python/datasources/response_cache.py`). The OpenWeatherMap API data source keeps what OpenWeatherMap answered in `datasources/openweathermap/cache-<hash of the question>.json` for **the time its settings give that kind of answer: one setting per kind of response** (`currentCacheHours`, default 0.5, and `forecastCacheHours`, default 6; 0 asks every time; neither cuts the other; `cached(..., setting=)`; a data source with another kind of answer gets another setting; `staleDays` removes an answer nobody used, default 30), through `cached(...)`: one task at a time asks the origin and the others wait for its answer, the old answer is used when the origin does not answer (never a `PermanentError`, so a refused key is not hidden), and a cache that cannot be read or written is no cache. The Reminder Overlay (#158) asks it, on demand, from the overlay task's own trigger: nothing runs between runs. So the settings, the cache and its lock are shared, not copied, and a page and an overlay of the same hours make one call.

Its descriptor has the `api` feature and no `layer-*` or `media-*` one, so no plugin offers it; it holds the origin's settings (key, kept times) and another source `uses` it (`test_layer_features`). **OpenWeatherMap is the model**: `open_async(dsec, { "needs": ["current", "forecast"] })` answers a `Report`; the Weather pages and the Weather Overlay only draw it, and its settings problems reach them in its words. The Calendar's `events_async` is the older shape of the same idea (a data-level method beside the pages). **Settings that move to another data source** go through `SETTINGS_MOVES` in `configuration_manager.py` (once, in `upgrade_settings`, logged by key name): the values are copied and **removed from the old document**, whose schema no longer marks a key write-only, so the settings route would otherwise send it as it is.
- **A schema belongs to the code, not to the storage.** `ConfigurationManager.refresh_schemas()` (at every start) copies the shipped `schemas/*.json` over the storage's, since a device seeded before a setting existed would otherwise never show it (found when the theme's fonts had no selector). Settings documents and schedules are never touched (`EINK_KEEP_SCHEMAS=1` skips it: the browser tests patch the schemas); the same start then runs `upgrade_settings()`, which adds the keys a stored settings document lacks from its schema's `default` (the device's) or its descriptor's `settings.default` (a plugin's or data source's), keeping every value the user set. Give every new setting a `default` there, or its form field will not appear on a storage seeded before it (found with the theme's fonts).
- **The panel's rest after a refresh is held by the driver stage, and no image reaches a driver during it** (`python/display/refresh_gate.py`, the readme's "Blanking Period", #364). Every display class asks its `gate` (`begin()` before a send, `finish()` in a `finally`: a failed or timed-out send starts the rest too) and a call that is too early is refused with `TooSoon`; the Display task waits `ready_in()` **before** it takes the next image (so what arrives meanwhile is one net image), and never sleeps a constant. A new display class calls `start_gate(settings)` in `initialize` and wraps its panel call in the gate, next to the `PanelGuard`. The last refresh is kept in `state/refresh.json` (`cm.state_file`; the `state` area is the device's own bookkeeping, so the Application does not announce changes to it); a stored time is clamped to one rest (a Pi with no clock set reads any date at boot) and an unreadable file is no state. A test that renders again and again gives its display `refreshInterval: 0`; the rest itself is tested in `test_refresh_gate`.
- **Chromium renders are capped per process** (`render_chrome_headless_arglist`, `RENDER_SLOTS_ENV`, #360): the two layers render on their own threads, so two browsers could run at once; a semaphore holds them to `render_slot_count()` (1 on a board with less than about 800 MB, else 2; `EINK_RENDER_SLOTS` decides first), measured at about 75 to 110 MB each. Anything new that starts a browser goes through that function, never `subprocess` of its own.
- **One task owns every GPIO, I2C and SPI line that is not the panel's** (`python/task/device_io.py`, `python/device/`, the readme's "Device I/O Task", #365). The display's driver stage owns the panel's lines (and its rest and guard); `DeviceIO` opens, listens to and closes the rest, and knows hardware but not meaning: a device reports `InputEvent(source, name, gesture)` (its library's callback only puts it on the task's queue), the task forwards it on the `device-input` route, and the Application maps it to an action in `python/device/bindings.py` (the same transport commands the web app sends, dropped while unclaimed). A device is an `InputDevice` (`pins`, `open`, `close`) listed in `python/device/registry.py`; its library is imported only inside `open` (device group rule), a pin is never opened before `check_pins` has compared it with the panel's lines (`python/device/pins.py`: add the lines of a new display type there), and a blocking bus call goes through `PanelGuard`. Its settings are the `devices` document (a Settings tab; one pin per input, empty = none). A changed document is applied live and a refused or failing one leaves the working devices open. **`test_device_io.TestEveryHandlerIsRegistered` fails when two methods of a task are handlers of the same message type**: a helper whose only parameter is a message type silently replaces the real handler (it happened to `Application._display_settings` twice); give helpers plain parameters.
- **A script may push a message or a picture to the panel** (`python/web/routers/display.py`, `Application.push_image` / `revoke_pushed`, the readme's Web API, #366). It is a priority image marked `origin.kind = api`: the route renders the text (`message.html` through `render_message_image`, themed, escaped by Jinja, a plain page when the browser fails) or decodes the picture (`utils/upload_image.py`: size, formats and pixel count are checked before decoding, by content, never by name; every refusal is a `ValueError` in our words) in its own thread, and the Application's own thread does the sending (`PushedImage`). A body is read by an `async` dependency with a size cap (the endpoints stay plain `def`); nothing is a path (`message_id` is looked up in the Application's own table, never built into one). The Application keeps the pushed messages that are still about (at most 20, 429 beyond), makes their titles unique (a title is what `PriorityRevoke` takes down) and refuses before the device is claimed. A route gets the Application from `application_of(request)`.
- **Say a thing with the time it happens, not the stamp of the message that caused it** (`PlaylistLayer._now`). A message carries the time it was made; a chain of messages (the end of a pass starts the next pass with the stamp it was given) passes the first stamp on for ever, so an event sent late in the chain showed a time long gone (the gutter said "The playlist stopped" after every pass, with the stamp of the pass the layer first started, hours or days before; found on a Pi). Telemetry and logs use `timebase.current_time()` when they are sent. And an ordinary transition is not an event: the end of a pass is not "stopped" (a stop is a transport command), so it is not announced; the next track's start says what is on the panel.
- **The layers decide what shows** (`python/utils/image_compositor.py`, the readme's "Display Architecture"). Back to front: the playlist's background page (or the theme's background color); the playlist's foreground page, `override` (covers everything below, a timer blend included) or `blend` (alpha-composited over the background); a timer `BlendImage` (Priority Update with Show As `blend`, for its minutes, queued like priority images); `priority`. **The overlays are drawn only in lock screen mode**: a background page and nothing above it; any other layer takes them off until that holds again (they are kept). A playlist background page ends the playlist's foreground page; it does not end a timer blend. The Slide Show's Show As picks a page's layer; `auto` reads the data source's `layer-foreground` feature (override) or not (background). `test_display_layers.py` pins this down.
- **Overlay text is outlined in the page, not washed in PIL** (#239; `python/datasources/overlay_text.py`, `static/render/overlay-text.html`). This is **the** way an overlay data source draws text: `render_overlay` renders a block of lines (each of runs in text roles) as SVG text, with an optional line drawing before it (`OverlayIcon`: the Weather's icons, stroked twice like the letters), `render_overlay_text` one line, on a **transparent** page (`RenderSession.render(..., transparent=True)` starts Chromium with `--default-background-color=00000000`, without which it paints white under every page; the page sets `--page-bg: transparent`). Under the letters the same line is stroked in the theme's outline color (`text-outline`, `--outline-color`: white, black on a black page): a hard edge, no blur and no gradient, which a color e-ink panel dithers into dots. Its width is the task's `outline` (the Overlay plugin's setting, 0 to 1, unset reads as 1) times a fraction of the text size, **a factor, not pixels**. The family is the theme's `fontOverlay` (unset: the heading font), one for every overlay, so they look alike; an overlay source has no font setting of its own. The page cannot run a script, so the size and the baseline are chosen in Python by measuring the line with PIL in the same font file (`fit_line`, with `font-synthesis: none` so Chromium draws that face and no made-up bold). Returning `None` means "nothing to show" and revokes. The timer layer revokes the overlays of tasks that a reload removed or disabled.

The layer, not the plugin, sends it as the message the plugin would have sent: an overlay task an `OverlayImage` in its zone (the compact layout of the page), a playlist track a `DisplayImage` on the `override` (foreground) layer so the overlays, which are drawn only on a background page, do not compete with its text (as "Playback stopped" and "Nothing to show" are), held for the track's `slideMinutes` (a struck-out track is not run again but still shows its page; all struck out shows one "Playback stopped" page), a timer task a `PriorityImage` for its `slideMinutes`. The page names the title and a reason that is our own message or only the exception's type name, never the exception's text (it can hold a URL with a key). The display does not redraw an image identical to the one on the panel, so a repeated error costs no refresh. Anything new that fails in a slot goes through the same page; do not log-and-skip.
- **Plugins and datasources can add API routes:** export an `APIRouter` and name it in the `"router"` entry of the `*-info.json`.

A panel paints its own surface (`--p-content-background`), or it shows the page through it (the Activity gutter did). A test that reads a computed color catches it; layout tests do not. - **The sign-in is a dialog, not a browser prompt** (`AuthPrompt.ts`, `AuthDialog.vue`; `ApiClient.signIn` opens it on a 401). It asks what `GET /api/access` says the device needs: the setup code and a new password (`setup`), the password, or the API token. - **Glyphs: PrimeIcons first, Material Symbols for what it lacks.** PrimeVue's widgets and most of the app use PrimeIcons (`pi pi-*`); for a glyph it does not have, use the same way a Material Symbol (Apache-2.0, `@material-symbols/svg-400`, outlined): `<i class="mi mi-skip-next">`, or `icon="mi mi-stop"` in any PrimeVue icon slot (the class is the name with hyphens). `.mi` is built like `.pi` (inline-block, the text color) with the glyph as a CSS mask, 1rem square whatever the font size around it (`--mi-size` changes it: `style="--mi-size: 1.5rem"`), and is injected by `installMaterialIcons()` in `main.ts`. An `em` follows the font size of whatever holds the element, so the same glyph or margin comes out a different size in each place (the gutter's glyph shrank with every nested `em`); `rem` is the same everywhere. A rendered page puts its computed size on `html { font-size: ... }` (the weather page's, the calendar's `font_px`), so `1rem` is the page's size, and where an element's own size varies a custom property holds it (`--fs`, the weather table's `--u` and `--p`) and its lengths are `calc(k * var(--fs))`. - **A task that swallows a failure reports it** (`DispatcherTask.report_failure`, `MessageRouter.failure_sink`): `except Exception` in a task thread exists to keep the thread alive, not to hide the failure. - **Telemetry is a response** (`python/task/telemetry_hub.py`, `python/web/routers/telemetry.py`, the readme's "Telemetry"). What a task sends on the `telemetry` route reaches the web app over a WebSocket:
  - Never raw exception text: send our sentence and `safe_reason(e)` (an actionable reason: the HTTP status and what to check, or the type's name with the text cleaned of addresses and secrets; the user must be able to tell what to fix), and log the rest.
  - **The exception in full** (`detail`, from `error_detail(e)`) is on a failure's event, but the telemetry routes and the WebSocket send it only when the connection comes from a loopback address (`_on_device`); anyone else gets the cleaned `message`. Forwarded headers are not trusted, so a proxy on the same machine (or a container's published port, which arrives from the gateway) makes viewers remote. The gutter shows it under the message.
  - The hub keeps only JSON scalars, short lists and small objects; any other object becomes its title or its type's name.
  - A shown image goes to the hub with the `shown` event and is served by its digest, never through the link and never by a path.
  - The WebSocket checks the session itself (it is outside the `/api` token dependency) and the `Origin`, since CORS does not cover a WebSocket.
  - A new event kind goes in the readme's table.
  - **`seq` starts again at every start of the device**: the WebSocket opens with `hello { run }` (`TelemetryHub.run`, random per start), and a page that names another `run` gets everything kept; the link then starts over. Without it a page open across a restart asked `since` an old number and showed nothing new (found after a container rebuild).
  - **Every image says who made it** (`DisplayImage.origin`, `OverlayImage.origin`, `python/task/source_router.py`): the layers hand each track and timer task a router that marks the images sent through it, the compositor's `layers()` carries the mark into the `shown` event, and the gutter lists it under "Now showing". A plugin sends through `context.provider.required(MessageRouter)` and gets the mark for free; code that sends an image on its own (an error page, the setup page) marks it itself or leaves it blank.
- **A data source's folder is its id.** `create_datasource_context` opens its settings by `ds.id`, as the settings routes do; the display name ("RSS Feed") is for people. Opening them by name read a folder that did not exist, so every list kept in settings looked empty at run time; tests with a fake settings manager could not see it.
- **The browser stores nothing but the theme** (`localStorage`, key `theme-...`); everything else lives on the server, which is trusted. Never put a token, a session, or any other state in `localStorage`, `sessionStorage`, or a script-readable cookie (CodeQL flags it as clear-text storage of sensitive information, and it is not needed).
  The API token is the one case that looks like it needs storage: it is sent once to `POST /api/session`, and the server keeps the session (`python/web/sessions.py`) behind an `HttpOnly`, `SameSite=Strict` cookie. The e2e tests assert that only the theme is stored.
  The cookie is `Secure` only when the app itself sees `https`: behind a TLS-terminating proxy it sees plain `http`, so the cookie is not marked `Secure` (forwarded headers are deliberately not trusted). There is no rate limiting on `POST /api/session`; that is a documented tradeoff for a home-network device.
- **What only the device has stays in the `device` group, marked Linux** (`inky`, `gpiozero`, `lgpio` and what they pull: `spidev`, `smbus2`, `gpiod`, `gpiodevice`; `cysystemd` was dropped, nothing imported it): never in `dependencies`, no default group, and imported only inside the function that needs it (the Inky driver of #281, `python/display/inky_display.py`, when the display is initialized: `load_driver` turns a missing driver or a board that does not answer into a `PermanentError` in our words, which the telemetry hub's status shows as they are; a display that fails to start is **not** replaced by the mock one), so Windows and the container install and start without it. The Waveshare drivers (vendored: `python/display/waveshare_epd`, left out of `ruff`, `mypy` and `coverage`) are imported by name, from our list of the vendored files, in `python/display/waveshare_display.py` when the display is initialized. `test_pyproject` pins all three; `uv sync --frozen --all-groups --dry-run` on Windows makes no change.
- **After swapping a framework or library, check what it was installing for you.** Removing Flask silently removed `jinja2` (and `markupsafe`), which four modules still imported; only the tests noticed.
  Grep the imports against `pyproject.toml` and declare every third-party package you import directly.
- **A `DispatcherTask` method whose only parameter is annotated with a message type is that message's handler** (`basic_task.py` reads the signature). A helper that takes such a parameter silently replaces the real handler for the type; give helpers plain parameters (found when a setup-page helper took a `DisplaySettings` and the application stopped configuring its layers) **A task's own names are taken too**: `CoreTask` has `stopped` (an `Event`), so a property of that name on `Application` failed in the base constructor (`Application.playback_stopped`).
- **Test an object for `None`, not for truth.** A class with `__len__` is falsy while empty: `if self.sink:` dropped every message to a hub that had no events yet, including the first failure (found building `GET /api/status`). Use `is not None`.
- **A failure's cause is usually in what the change touched indirectly:** the watcher, the CI storage, a transitive dependency. Reproduce under CI conditions before concluding anything.

## Boundaries this repo has actually hit

- **A 403 on push means GitHub access is not connected for the session.** Stop and tell the maintainer; do not look for a way around it. Repository settings, secrets, and branch protection need the maintainer's explicit go-ahead for that specific change.
- **A PR's own CI can surface a real problem that passes locally** (the CI storage above). Fix it on the same branch; never skip, disable, or quarantine a test to get green.
- **A merged PR is finished.** Follow-up work goes on a fresh branch from the updated `master`, never on the merged branch.
