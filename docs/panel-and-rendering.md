# The panel and rendering

Read before touching what is drawn on the panel: rendered pages, the theme's inks and typography, the layers and overlays, the error page, the display devices, the driver stage's guard and rest, GPIO and I2C, and pushing a picture from a script. These rules were moved out of `AGENTS.md` unchanged; `AGENTS.md` keeps the rules that apply to every change.

- **A rendered page is one template.** An HTML-rendered page (`render/<name>.html`, extending `static/render/plugin.html`) carries its own CSS in its `{% block style %}`; there is no per-page stylesheet and `RenderSession` takes no CSS file. Only `plugin.css` (the base) and `themes.css` (the theme roles) are shared files, linked by `RenderSession`. Page CSS cannot contain `{{`, `{%` or `{#` (Jinja reads them). `plugin.html` carries a Content-Security-Policy (no script, no network: styles, fonts and stylesheets are our files, pictures are embedded as `data:`), because Chromium runs with `--no-sandbox`; a page that needs a remote resource embeds it first (as the RSS pictures are), it does not link to it. `test_error_image` renders a page with a script to prove it does not run. **Text is drawn without antialiasing, and CSS cannot do that on Linux** (#684): `font-smooth` and `-webkit-font-smoothing` do nothing there (Chromium takes its text rendering from fontconfig), and a grey or coloured fringe on a letter is dithered into dots on a panel with a few solid inks (measured: 741 colours and about 10,000 fringe pixels on a test page). The renderer starts with `FONTCONFIG_FILE` set to `python/static/render/fonts.conf` (antialias off, no subpixel colour, full hinting) and `--disable-lcd-text` (`FONTS_CONF` in `image_utils.py`); PIL text sets `draw.fontmode = "1"`; **An SVG shape is not text** and fontconfig does not cover it: the overlay's line icon has `shape-rendering: crispEdges` (without it an overlay had 626 partial-alpha pixels in the test, which the compositor blends with the picture and the quantizer dithers). `test_text_rendering` renders black, red and blue text and asserts every pixel is one of the page's inks, and renders an overlay (text, outline, icon) and asserts every pixel is transparent or opaque (Linux only: fontconfig is not Windows'). A new way of starting Chromium keeps that environment, and a new page sets no `font-smooth` of its own.
- **The theme is a choice of inks, resolved in Python for the attached panel** (`python/model/theme.py`, `python/model/inks.py`, `docs/architecture.md`'s "Color"). The device theme (`theme-settings.json`: `preset`, `background`, the five custom inks) is resolved against the panel's ink set (`resolve`; the Display task publishes the set, `panel_ink_set()`) into one ink per role; `RenderSession` writes each role's **drive color** (the exact `#rrggbb`) into `:root` (`plugin.html`), and `themes.css` is a plain class per role (`text-primary`, `bg-fill`, `text-on-fill`, `bg-strong`, ...) over its variable: no HSL, no tint. PIL code takes the same inks from `Palette` (`current_palette(scm)`, read on every render). Pages do not pick a scheme; every page wears the device theme. A new role is added in both places (a `Palette` field and a class); `test_theme` checks the class list and renders a swatch per role in Chromium against `Palette`, exactly. **A page is made of inks only**: no `opacity`, `rgba(`, `hsla(`, gradient, shadow or `color-mix` in a template or stylesheet (`TestNoTranslucency`; a panel dithers any other color into dots; fade with a rule, a dotted outline, italics or a strike instead). Design pages so they still read when two roles resolve to the same ink (a black-and-white panel, `mono`): tell parts apart by shape, weight and position, not only by color; a highlight may resolve to **none** (the page's own color), so never draw something that must be seen only in the highlight ink.
- **Typography is part of the theme.** `fontBody`, `fontHeading` (unset: the body font), `fontOverlay` (the overlays' text; unset: the heading font) and `fontScale` (0.8-1.4) are in the theme settings and in `ThemeInputs`; `css_vars` writes `--font-body`, `--font-heading`, `--font-overlay` and `--font-scale` into `:root` (family names unquoted: the page escapes quotes), `plugin.css` sets the body font, and PIL code reads `current_typography(scm)`. **A page sets no `font-family` of its own** (`test_theme` checks): headings use `var(--font-heading)`, overlay text `var(--font-overlay)`, text sizes are multiplied by `var(--font-scale)` (the calendar multiplies in `Layout`, which counts events from the text size). A figure that is sized to fill its page (the countdown's number, the year, the error page) is not scaled, so it still fits. Only families in `FONT_FAMILIES` are accepted, and `/api/fonts/{family}` serves a file from that table, never a path from the URL. **A font we ship is under the SIL Open Font License, unmodified, in a folder of its own with its `OFL.txt`** (and a line in `NOTICE`): read its licence in its name table before adding it (`fontTools`, name IDs 0, 13, 14), since a file's name and the text beside it can be wrong (the old `DS-DIGI.TTF` was Digital-7, "personal use", next to another font's shareware notice; Napoli was "all rights reserved"). A **variable font** (one file for every weight) is listed once per weight with its `wght`: PIL sets that axis (`get_font`), and Chromium sets it from the page's `font-weight`. **The page's face declares that number** (`enum_fonts`: `font-weight: 500`, not `normal`), or Chromium draws the 400 that PIL does not. **Shipped is not offered** (`OFFERED_FONTS`): the theme's `font` lookup lists exactly the offered families (`test_theme`), and DSEG7 is shipped for the clock's digits only. **A font earns its place by its strokes**: with antialiasing off a one-pixel stroke is wispy, so `TestStrokeSolidity` (Linux, measured in the test container) holds each offered font to a share of ink in solid 2×2 blocks at its floor size and weight; a serif is for headings, 22 px and up. **The page background** is a theme setting (`background`: `white` by default, or `black` = dark mode); every page's container is `bg-page` (`--page-bg`), and the compositor's fill is the page's ink (`Palette.rgb("bg_page")`). On a black page every preset swaps to the inks that read on it (white text, yellow and red accents), so a page never hard-codes white or black. The Theme tab shows a sample in the real fonts. It also shows every role of the palette resolved by the server for the form's values and the attached panel (`POST /api/theme/palette`, the same `resolve` as the pages and PIL, in the inks' appearance colors, with the ink set it is shown for), never re-derived in the browser.

- **A display device is a descriptor, chosen by the `display_type` schema field** (`python/displays/<id>/display-info.json`, `enum_displays` / `create_display`, `docs/architecture.md`'s "Display Task", #397). The Display task makes the class the descriptor names, found by **declared id**; a device's own settings are its descriptor's `instanceSettings`, stored flat in the `display` settings document (never prefixed keys such as `inky-saturation` in `schemas/display.json`) and checked like a task's content by `settings_choices` (only the chosen device's), with defaults filled in at seeding and start (`_chosen_defaults`). Their names do not repeat the display schema's own (`test_item_audit`). A display class reads its keys with the descriptor's default as the fallback (`picture_size`), and the `display` family in `fixtures/schema_shapes.json` is the schema together with every device's properties, so a device's property that changes shape asks for the number to be raised. The GPIO buttons are hardware config of their own (the Devices tab), not displays.

- **The panel's rest after a refresh is held by the driver stage, and no image reaches a driver during it** (`python/display/refresh_gate.py`, `docs/architecture.md`'s "Blanking Period", #364). Every display class asks its `gate` (`begin()` before a send, `finish()` in a `finally`: a failed or timed-out send starts the rest too) and a call that is too early is refused with `TooSoon`; the Display task waits `ready_in()` **before** it takes the next image (so what arrives meanwhile is one net image), and never sleeps a constant. A new display class calls `start_gate(settings)` in `initialize` and wraps its panel call in the gate, next to the `PanelGuard`. The last refresh is kept in `state/refresh.json` (`cm.state_file`; the `state` area is the device's own bookkeeping, so the Application does not announce changes to it); a stored time is clamped to one rest (a Pi with no clock set reads any date at boot) and an unreadable file is no state. A test that renders again and again gives its display `refreshInterval: 0`; the rest itself is tested in `test_refresh_gate`.
- **Chromium renders are capped per process** (`render_chrome_headless_arglist`, `RENDER_SLOTS_ENV`, #360): the two layers render on their own threads, so two browsers could run at once; a semaphore holds them to `render_slot_count()` (1 on a board with less than about 800 MB, else 2; `EINK_RENDER_SLOTS` decides first), measured at about 75 to 110 MB each. Anything new that starts a browser goes through that function, never `subprocess` of its own.
- **One task owns every GPIO, I2C and SPI line that is not the panel's** (`python/task/device_io.py`, `python/device/`, `docs/architecture.md`'s "Device I/O Task", #365). The display's driver stage owns the panel's lines (and its rest and guard); `DeviceIO` opens, listens to and closes the rest, and knows hardware but not meaning: a device reports `InputEvent(source, name, gesture)` (its library's callback only puts it on the task's queue), the task forwards it on the `device-input` route, and the Application maps it to an action in `python/device/bindings.py` (the same transport commands the web app sends, dropped while unclaimed). A device is an `InputDevice` (`pins`, `open`, `close`) listed in `python/device/registry.py`; its library is imported only inside `open` (device group rule), a pin is never opened before `check_pins` has compared it with the panel's lines (`python/device/pins.py`: add the lines of a new display type there), and a blocking bus call goes through `PanelGuard`. Its settings are the `devices` document (a Settings tab): `triggers`, a row for each button (its `pin` and its `action`: `play`, `stop`, `toggle` or `next`, each on one button only), and what a press does is the row's action, read at each press by the Application. **A button may run a task** (`action: "task"`, #671): the row carries the settings of a Priority Update (`content`, set in the plugin's own form in a dialog, `RowPluginDialog.vue`), the server checks them by the plugin's rules (`row_plugin_errors`, hooked into the devices document's save, paths `[triggers, row, content, setting]`) and drops them from a row that is not a task; a press sends `RunTrigger` to the timer layer (`Application.run_trigger`, also the Run now of a saved row, `POST /api/devices/triggers/{pin}/run`), which runs it like a timer task that is in no schedule file. There is no timer task without a time: a task that a button starts belongs to the button. A changed document is applied live and a refused or failing one leaves the working devices open. **A handler is a method marked `@handles(MessageType)`** (in `docs/tasks-and-storage.md`); `test_device_io.TestEveryHandlerIsRegistered` checks every task class's marks without making the task.

- **A script may push a message or a picture to the panel** (`python/web/routers/display.py`, `Application.push_image` / `revoke_pushed`, `docs/development.md`'s "Web API", #366). It is a priority image marked `origin.kind = api`: the route renders the text (`message.html` through `render_message_image`, themed, escaped by Jinja, a plain page when the browser fails) or decodes the picture (`utils/upload_image.py`: size, formats and pixel count are checked before decoding, by content, never by name; every refusal is a `ValueError` in our words) in its own thread, and the Application's own thread does the sending (`PushedImage`). A body is read by an `async` dependency with a size cap (the endpoints stay plain `def`); nothing is a path (`message_id` is looked up in the Application's own table, never built into one). The Application keeps the pushed messages that are still about (at most 20, 429 beyond), makes their titles unique (a title is what `PriorityRevoke` takes down) and refuses before the device is claimed. A route gets the Application from `application_of(request)`.

- **The layers decide what shows** (`python/utils/image_compositor.py`, `docs/architecture.md`'s "Display Architecture"). Back to front: the playlist's background page (or the theme's background color); the playlist's foreground page, `override` (covers everything below, a timer blend included) or `blend` (alpha-composited over the background); a timer `BlendImage` (Priority Update with Show As `blend`, for its minutes, queued like priority images); `priority`. **The overlays are drawn only in lock screen mode**: a background page and nothing above it; any other layer takes them off until that holds again (they are kept). A playlist background page ends the playlist's foreground page; it does not end a timer blend. The Slide Show's Show As picks a page's layer; with `auto` **a page that says what it is decides** (`MediaRenderResult.layer`, `foreground` or `background`: Museum Art's work with its caption is foreground, without it background, and it declares both layers), else the data source's `layer-foreground` feature (override) or not (background). `test_display_layers.py` pins this down.
- **Overlay text is outlined in the page, not washed in PIL** (#239; `python/datasources/overlay_text.py`, `static/render/overlay-text.html`). This is **the** way an overlay data source draws text: `render_overlay` renders a block of lines (each of runs in text roles) as SVG text, with an optional line drawing before it (`OverlayIcon`: the Weather's icons, stroked twice like the letters), `render_overlay_text` one line, on a **transparent** page (`RenderSession.render(..., transparent=True)` starts Chromium with `--default-background-color=00000000`, without which it paints white under every page; the page sets `--page-bg: transparent`). Under the letters the same line is stroked in the theme's outline color (`text-outline`, `--outline-color`: white, black on a black page): a hard edge, no blur and no gradient, which a color e-ink panel dithers into dots. Its width is the task's `outline` (the Overlay plugin's setting, 0 to 1, unset reads as 1) times a fraction of the text size, **a factor, not pixels**. The family is the theme's `fontOverlay` (unset: the heading font), one for every overlay, so they look alike; an overlay source has no font setting of its own. The page cannot run a script, so the size and the baseline are chosen in Python by measuring the line with PIL in the same font file (`fit_line`, with `font-synthesis: none` so Chromium draws that face and no made-up bold). The compositor only pastes the overlay's image; the PIL wash (`wash_mask`, `wash_rgb`) and `text_overlay` are gone. A stored task that still carries `wash`, `washColor`, `washStyle` or Today's `font` keeps working (unknown content properties are kept, not checked).
- **Overlays belong to a task and live in a zone.** The display's six zones (`python/task/overlay_zones.py`) are announced in `DisplaySettings.overlays`; a plugin sends `OverlayImage(key, zone, ...)` (the key is the timer task's id) and `OverlayRevoke(key)`, and the display keeps one overlay per zone and one zone per key, with no timer.
  An overlay data source renders at `dsec.dimensions` as given (the zone, as the viewer sees it): never through `target_dimensions`, which would turn it again for portrait. Returning `None` means "nothing to show" and revokes. The timer layer revokes the overlays of tasks that a reload removed or disabled.
- **A failed slot shows an error page** (`python/utils/error_image.py`, template `python/static/render/error.html` extending `plugin.html`, so it wears the theme classes and fonts of the other pages; a plain PIL page is the fallback when the browser is what failed). The layer, not the plugin, sends it as the message the plugin would have sent: an overlay task an `OverlayImage` in its zone (the compact layout of the page), a playlist track a `DisplayImage` on the `override` (foreground) layer so the overlays, which are drawn only on a background page, do not compete with its text (as "Playback stopped" and "Nothing to show" are), held for the track's `slideMinutes` (a struck-out track is not run again but still shows its page; all struck out shows one "Playback stopped" page), a timer task a `PriorityImage` for its `slideMinutes`. The page carries the logo (`static/images/logo.svg`, the same file as the web app's `app/src/assets/logo.svg` (keep them equal), embedded as `data:` by `StaticConfigurationManager.image_data_url`, from a list of our own names) and says where the web app is (`WebAddress`, the setup address, a service `Application` hands the layers); the setup page uses the same template with its own heading and no hint. The page names the title and a reason that is our own message or only the exception's type name, never the exception's text (it can hold a URL with a key). The display does not redraw an image identical to the one on the panel, so a repeated error costs no refresh. Anything new that fails in a slot goes through the same page; do not log-and-skip.

- **A board is given the frame in the form that reaches its buffer unchanged** (`inky_display.py`, #723). The frame is on the panel's inks (`to_inks`), and a board that quantizes it again with its own palette adds error when that palette is not our drive colours: the 7-colour Inky boards' orange is (255, 140, 0), ours (255, 128, 0), and a solid orange area came out 8% red. So those boards (`BOARD_ORDER`) are given a `P` image of indexes in their own order, which their driver copies into the buffer as it is; the Spectra boards' palette is exactly our drive colours and take RGB. `test_inky_boards` runs each board's `set_image` (copied from `inky` 2.6.0, the pinned version) on a block of every ink: 100% of each block must reach the buffer as its ink.
