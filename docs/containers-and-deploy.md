# Containers, the Pi kit and the build

Read before changing the Dockerfile, `compose.yaml`, `deploy/`, HTTPS, the device dependency group or how a build says which commit it is. These rules were moved out of `AGENTS.md` unchanged; `AGENTS.md` keeps the rules that apply to every change.

- **HTTPS is uvicorn's own, never a proxy's** (`python/web/https.py`, `python/utils/tls_certificate.py`): with no certificate of one's own the device makes a self-signed one for the names it answers to, keeps it in the storage's `tls/` folder through the configuration manager (`tls_paths`, `read_tls`, `write_tls`: never in a backup, not announced, like `state/`) and makes it again when a name is missing or it nears its end. A certificate that cannot be used stops the start in our words; HTTPS asked for never falls back to HTTP. On a Pi, `deploy/eink-container.sh ssl on [CERT KEY]` (remembered in `~/.config/eink-billboard/ssl`) passes `--ssl` and mounts a certificate of one's own as **Podman secrets** (`--secret NAME,uid=,gid=,mode=0400`: the app's user in the image, asked with `id`; Podman 4.3 mounts a secret world-readable and root's without them, and refuses to create a name that exists or remove one in use, so the container goes first); the kit's own probe of loopback uses `curl -k`. `deploy/test/ssl.sh` tests it in a Bookworm container; run it after a change to `ssl` or `start`.

- **Containers** (`Dockerfile`, `compose.yaml`, `.dockerignore`):
  - `podman compose run --rm test` builds the `test` image (Python 3.13.7, `chromium-headless-shell`, `uv`, the locked dev dependencies) and runs the checks against the **bind-mounted checkout**. The virtual environment lives in `/opt/venv` (not `.venv`), so the container never touches the Windows one, and `PYTHONDONTWRITEBYTECODE` keeps `__pycache__` out of your tree.
    It needs nothing restored. Because it sees the working tree, an untracked file you have lying around is checked too (it once showed an unrelated `mypy` error that CI would never see).
  - `podman compose up --build app` serves the built web app and API on `http://localhost:8080` with the storage in a named volume (seeded on first start: a missing **or empty** folder is seeded, since a mounted volume always exists). `EINK_STORAGE=./.storage podman compose up --build -d app` mounts that folder of the checkout instead, used as it is (the app writes to it). The port is published on `127.0.0.1` only; set `EINK_API_TOKEN` before widening it (see the network-exposure issue, #36).
    A Windows folder mounted into the container (9p) sends **no file change events**, so a save was written but no task heard of it: compose sets `EINK_WATCH_POLL=2` (seconds; `ConfigurationWatcher` then compares the folder on that interval instead of using inotify; empty turns it off). Check the log line "Watching ... by".
    The image has no display hardware (the `device` dependency group is left out), so it is for the API and web app, not the panel.
  - `podman compose --profile inky up --build -d app-inky` is the app with the **Inky driver installed** (the `device` group, which the other images leave out) on `http://localhost:8081`, to see what a device does when the driver loads and finds no board; `EINK_FAKE_INKY=ok|busy-stuck|spi-off|unknown-board` pretends there is one (`scripts/fake_inky.py` fakes only I2C, GPIO and SPI: the real driver runs on them), the last image it was given is `/tmp/fake-inky/fake-inky-last.png`. It has a storage of its own (`storage-inky`); set the Display Type to `inky` there and restart.
  - `podman compose --profile waveshare up --build -d app-waveshare` is the same for a Waveshare (`http://localhost:8082`, `storage-waveshare`): the vendored driver (`python/display/waveshare_epd`, VENDORED.md) really runs, `scripts/fake_waveshare.py` answers for the Pi's `/proc/cpuinfo`, `spidev` and the `gpiozero` pins (`EINK_FAKE_WAVESHARE=ok|busy-stuck|spi-off`). It found that a Waveshare driver's `init` waits on the busy line for good, so the display guards both starting and refreshing with a time. **The driver stage owns that guard** (`python/display/panel_guard.py`, used by the Inky and Waveshare displays): whatever talks to a vendor driver runs on a thread for a time, because six Inky models (`e640`, `e673`, `el133uf1`, `jd79661`, `jd79668`, `ssd2683`) and every Waveshare driver wait on the busy line with a loop that has no end; the Display task never waits on a panel, and a call that timed out blocks the next ones until it returns. A new display class wraps its panel calls in it.
  - **A consumer starts with `curl -fsSL .../deploy/bootstrap.sh | bash`.** Only what cannot be in the container is done on the Pi (apt: podman, fuse-overlayfs, git, curl, uidmap; SPI and I2C through `raspi-config nonint`; the spi, i2c and gpio groups; linger), each with sudo after one confirmation. Everything is in `main()`, called on the last line, so a cut download runs nothing; questions are read from `/dev/tty` (the script's own input is the download). The downloaded copy checks, plans, does the sudo steps and clones; then it `exec`s the clone's copy (`--from-clone`), so the steps always match the app being installed. It is idempotent: a re-run continues (after the restart it asks for when SPI, I2C or the groups changed: a group in the group list but not in this session needs a login, not another `usermod`) or updates. The display is `EINK_DISPLAY`, or remembered (`~/.config/eink-billboard/display`, asked as before), or, when neither, **found out (#836)**: once the app is running (only its image can ask the I2C bus, and I2C works after the restart the first run asks for) the bootstrap runs `detect`, and an Inky that answers is chosen without a question, `--yes` included; one that does not leaves the question (`--yes`: mock). An Inky that was chosen and does not answer is a warning (`detect`), never a stop. Port 8080; **downloaded, never built unasked** (#310, #504: `get` pulls `ghcr.io/escape-llc/eink-billboard:sha-<the clone's full commit>` (a release's too), checks its `eink.commit` label against the clone and **verifies its signature** (#555: `image.yaml` attests every image with `actions/attest-build-provenance`; `verify_image` runs cosign from an image pinned by digest, `COSIGN_IMAGE`, on each digest Podman recorded for the pull, the index being what is attested, and accepts only `image.yaml@refs/heads/master` of `EINK_SIGNER` at the clone's full commit; anything else, Sigstore unreachable included, is refused and the app keeps its image; `EINK_VERIFY=0` is for tests, whose images are unsigned), and when there is none says what to do and changes nothing: only `build` or `EINK_PULL=0` builds on the Pi; **`update` follows a channel**, remembered in `~/.config/eink-billboard/channel`: `stable` the newest `v*` release (the newest snapshot while there is none), `insider` (`--insider`, `--master`) the newest snapshot, `pinned` a tag named, `branch` for development; a Pi with no file follows what its clone follows, and going back to an older version asks for a typed yes; the bootstrap's downloaded copy chooses the version (`--stable`, `--insider`, `EINK_CHANNEL`) before handing over to the clone's; `.github/workflows/image.yaml` builds `app-device` on GitHub's arm64 runners for every push to `master`, attests it, and on a pull request that touches the image builds without publishing; **every image published from `master` is a snapshot** (#504, `scripts/snapshots.py`, `test_snapshots`): a git tag of the commit's committer time in UTC (`20261022143005`, no `v`) and the same name on the very manifest, and the cleanup after it keeps the newest always and at most 5, the others for 7 days, never a release; it removes an image by what it reaches (the index, its untagged image and build attestation, the `sha256-<hex>` provenance), never an untagged version a kept tag reaches; **a release is promoted, never built** (`release.yml`, when a person pushes `vX.Y.Z` as `RELEASING.md` says: the tag must be on `master` and agree with `pyproject.toml` and `app/package.json`, which `test_snapshots` keeps equal, and the commit's snapshot image gets the release's name and `latest`); the image that ran before is kept as `localhost/eink-device-previous` for `rollback`, and `podman untag IMAGE NAME` names the one name to remove: `untag IMAGE` alone removes them all, the app's too); **`deploy/test/pull-path.sh`** tests the pull path end to end in a Debian Bookworm container (a registry of its own standing in for ghcr.io, a `podman build` shim), run it after a change to `get`, `update`, `rollback` or the image names. **Podman's storage driver is overlay, never vfs** (#552): rootless Podman without the kernel's overlay for a user and without `fuse-overlayfs` falls back to `vfs` and keeps it, every layer a full copy of all under it (a Pi wrote 5.7 GB and took 9 minutes to unpack one 1.3 GB image; overlay: 1.4 GB, 2 min 30 s). The bootstrap installs `fuse-overlayfs`; `get` and `build` switch an empty vfs store; `storage` switches one that holds the app (export, check, `podman system reset`, `storage.conf`, import, download) after trying overlay in a scratch store with `--root`/`--runroot` (a storage.conf alone is overridden by the driver Podman's database remembers; a runroot is at most 50 characters); `check` reports the driver. **`deploy/test/storage-driver.sh`** tests it in a Bookworm container (`EINK_TEST_STORE=disk` for the store on the container's own file system); run it after a change to those; `EINK_REF` installs a branch or tag instead of a channel. Tested in a Debian container (a `uname` shim, a real tty through `script` and `su -P`), then **run start to finish on a Pi 5** (Bookworm, Podman 4.3, no panel): `check` all fine, every driver library loads on arm64 (`lgpio` included), and after a restart the systemd user unit with linger started the container again with the devices open.
  - **On a Pi, `deploy/eink-container.sh`** is the consumer's whole kit (update, build, start, logs, code, check, storage, display, models, detect, autostart, reset-password, wipe): **the consumer needs no command but it** (`update` is git fetch, a fast-forward, build and start; `build` builds the clone as it is). **`update` hands over to the new copy of itself** (#561): once it has moved the clone it `exec`s the clone's script with `EINK_UPDATE_HANDOVER`=the commit, which does only the download, its check and the start; the copy already running is the old one (bash keeps the file it started with), so without it a change to the script worked one update late (the image check of #555 did not run in its own update). **On a small board `update` stops the app while it downloads** (#568: `small_board`, less than 800 MB of `MemTotal`, the line the render slots use; `EINK_MEM_KB` is a test's): the download, the unpacking and cosign would compete with the app and a render for memory, and an e-ink panel keeps its picture. It is `podman stop`ped, not removed, so a failed download, a refused image or Ctrl+C `podman start`s the same container again; `pull-path.sh` fakes the container in its `podman` shim (`FAKE_APP`) and checks the order (stop, pull, start). `pull-path.sh` checks the hand-over with a snapshot that changes the script: plain `podman` (Bookworm has 4.3 and no compose), timesyncd's `/run/systemd/timesync` mounted read-only when it exists (the app waits for its `synchronized` flag, #785), the devices that exist passed in with `--group-add keep-groups` (rootless: the user's spi, i2c and gpio groups; `/dev/gpiochip4` is a link and is left out), `EINK_PUBLIC_URL` from the Pi's address. It is written for someone who is not an expert: every failure says what to do, nothing destructive without a typed yes, never as root, settings changed only through the app's own code inside the container (`cob.save`), never printed. **It promises no size and no duration** (#564), and neither do the bootstrap, the readme's setup or the Help drawer: a Pi Zero 2 W on an SD card and a Pi 5 on an SSD differ many times over, and an image's size changes with its contents, so "about 350 MB" or "15 to 20 minutes" was wrong on most devices and stale after the next image; say what happens ("downloading, then unpacking", "much longer than a download") and show what is measured as it runs (the download's progress line). What the code enforces (a limit, a time-out, the build's free-space check) is stated as it is. A heredoc of Python in it sets `sys.path` to `/work` first: importing `lgpio` moves the working directory to `LG_WD`. Check it with ShellCheck (`podman run --rm -v ./deploy:/mnt:ro docker.io/koalaman/shellcheck:stable -S warning /mnt/eink-container.sh`).
  - `podman compose` delegates to an installed compose provider: Docker Compose (the binary Docker runs as `docker compose`, found as `docker-compose.exe`) or `podman-compose`. With Docker the same commands are `docker compose ...`.
  - **Podman on Windows needs WSL 3.0+ and Podman 6.1+.** Each combination short of that broke containers differently (all found after one upgrade):
    an older WSL kernel (6.6) lacks nftables modules netavark 2.0 needs, so no container starts; WSL 3.0 with Podman 6.0 fails on cgroups (`controller pids is not available`);
    and Podman 6.0 publishes ports without a listening socket, which WSL does not forward to Windows `localhost`. Podman 6.1 fixes the last two **inside the machine image**,
    so after upgrading Podman, recreate the machine (`podman machine rm`, `podman machine init --rootful`, `podman machine start`; no Windows admin needed). Check with `wsl --version` (kernel 6.18+) and `podman version` (client and server 6.1+).
    Do not work around it by turning off the container firewall: containers then lose internet access too, and builds fail.
  - The Podman installer may move Podman (now `%LOCALAPPDATA%\Programs\Podman`, per user); `PATH` changes reach VS Code and its terminals only after a sign-out or reboot.
  - `podman machine ssh` from Git Bash leaves a file named `NUL` in the current folder (Podman passes `UserKnownHostsFile=NUL`); run it from PowerShell or delete the file.
  - **What only a build needs is never in a layer** (#557): uv's download cache is a cache mount (`RUN --mount=type=cache,target=/root/.cache/uv`), and the compiler, `swig` and `curl` that build `lgpio` and `spidev` are installed, used and purged (`apt-get purge --auto-remove`) in one `RUN`. Kept, they were 157 MB and about 250 MB of a 1.35 GB image (now 0.88 GB). A new build-only tool goes the same way; check the drivers still import (the list `check` uses) and Chromium still renders after a removal.
  - **The commit and the code are the last layers** (#568): a layer is rebuilt, and downloaded again by every Pi, when anything listed before it changes, so the stages go `base` (pinned by digest, as uv is: a republished tag changed every layer), `deps` (the dependencies, the app's user), `device-deps` (`lgpio` and the `device` group), and only then `EINK_COMMIT`, `COPY python/` and the web bundle, in `app` and in `app-device` alike. When the code came before the drivers, every merge built `lgpio` again and every Pi downloaded the drivers again. A new step goes above the commit unless it changes with the code; check with two builds of commits that differ only in code: their layer lists (`podman image inspect -f '{{range .RootFS.Layers}}{{println .}}{{end}}'`) differ in the last two only.
  - The web stage keeps the repository layout (`/repo/app`, `/repo/python/tests`) because the type-check imports the shared rule cases from `python/tests`; copy any other cross-folder import it needs.
- **No secret goes into an image.** `.dockerignore` excludes `.storage` folders, `.env` files, and zips; test storage is only ever mounted.

- **Deployment is the container** (the readme's "Set up a Raspberry Pi", `deploy/bootstrap.sh` and `deploy/eink-container.sh`, below under Containers): a non-root user's rootless Podman, port 8080, the token passed to the container by name (never on a command line, which the process list shows). The old systemd unit for an install without a container is gone.

- **A build says which commit it is, and an update checks what it started** (#413 follow-up to a Pi that showed no front-end change after a rebuild): `deploy/eink-container.sh build` passes `--build-arg EINK_COMMIT=<short commit>`; the Dockerfile sets it after the dependency layers (web stage before `npm run build`, so a new commit always rebuilds the bundle and a cached bundle of another commit cannot be reused; app stage before `COPY python/`). The bundle carries it as `__APP_COMMIT__` (the header's `v0.1.0 (abc1234)`, `dev` outside an image), the server as `EINK_COMMIT` (`GET /api/system` `host.commit`, `unknown` unless it is a short alphanumeric), and the System page's Device card's Machine row warns when they differ (a tab opened before an update). `cmd_start` fails when the container's image is not the one just built, and prints `Running commit ...`. Anything else that must be known about a running build goes through the same build argument, never a file written at run time.

- **What only the device has stays in the `device` group, marked Linux** (`inky`, `gpiozero`, `lgpio` and what they pull: `spidev`, `smbus2`, `gpiod`, `gpiodevice`; `cysystemd` was dropped, nothing imported it): never in `dependencies`, no default group, and imported only inside the function that needs it (the Inky driver of #281, `python/display/inky_display.py`, when the display is initialized: `load_driver` turns a missing driver or a board that does not answer into a `PermanentError` in our words, which the telemetry hub's status shows as they are; a display that fails to start is **not** replaced by the mock one), so Windows and the container install and start without it. The Waveshare drivers (vendored: `python/display/waveshare_epd`, left out of `ruff`, `mypy` and `coverage`) are imported by name, from our list of the vendored files, in `python/display/waveshare_display.py` when the display is initialized. `test_pyproject` pins all three; `uv sync --frozen --all-groups --dry-run` on Windows makes no change.
