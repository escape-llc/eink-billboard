# Data sources, plugins and providers

Read before adding or changing a data source, a plugin or a provider: features, providers and contracts, metering, kept downloads and lists, the weather, calendar, AI, Comic Vine and Thunderforest sources, credits, and the lists kept in settings. These rules were moved out of `AGENTS.md` unchanged; `AGENTS.md` keeps the rules that apply to every change.

  **A list kept in settings, one entry chosen per task.** A plugin or data source keeps an `array` in its own `settings` (a feed list) and its `instanceSettings` offer the entries through a `settings` lookup:
  `"lookups": { "feed": { "settings": "feeds", "value": "name", "label": "name" } }`, used by a `string` property with `"lookup": "feed"`. The task stores the entry's `value` (its `key`, so reordering the list is safe; a renamed or deleted entry shows as a stale value the user must choose again).
  The choices are served by `GET /api/datasources/{id}/lookups/{lookup}` (`/api/plugins/...` likewise), for a lookup the descriptor declares; the form reaches it through `BasicForm`'s `owner`. Unlike a URL lookup the server can check membership, so a value that is not an entry is a 422 (and nothing is allowed while the list is empty).
  A field of the **settings themselves** may use a `settings` lookup too (a calendar row naming an account of the same settings): the server checks it against the document being saved, so an entry added in the same save is a choice; the form's list (`SettingsForm`'s `owner`) is the stored one until then.
  The RSS Feed data source is a second: its `feeds` (`name`, `url`, http or https only) are in its settings, a task picks one by name, and it is a list source (`media-list`) with one story per slide for the Slide Show plugin; its page is `render/rss.html`. The Image Folder data source is the first user: its `folders` (`name`, `path`) are in its settings, and a task's `folder` is a name (an unknown name is a `PermanentError`). Tests that run it write its settings first (`save_datasource_settings`).
  The calendar is the third, and the first with row secrets, row conditions and multi-selects. It is **a provider and its pages** (#513): the **Calendar Sources** (`python/datasources/calendar_sources/`, id `calendar-sources`, `data-calendar`, `CalendarSources` implements `CalendarApi` in `contracts/calendar.py`) hold `calendars` (iCal or CalDAV; `auth` none, basic or bearer, the secrets `writeOnly`), `accounts` and `holidays` (a country from the `holidays` package, by the URL lookup `/api/datasource/calendar-sources/lookups/countries`), and answer `open_async(dsec, { start, end, calendars, holidaySets })` with a `CalendarAnswer` (events, notes); the **Calendar** pages (`python/datasources/calendar/`, id `calendar`) ask `dsec.provide(CalendarApi)` and keep `weekStart` and `weekNumbers` in their own settings (they describe the pages); a task picks `views` (month, weeks, agenda: one page each, in that order; `weeks` is the current week and `weeksAhead` more as continuous rows, every other month tinted and each month named on its first day), `calendars` and `holidaySets` (none chosen: all enabled) and `agendaDays`.
  It reads every calendar once per slot (`open_async`), in the device zone. A calendar that fails is named in the page's footer (our words: never the address, which can be a secret); the slot fails only when every chosen one does (a `PermanentError` when all are settings problems). A calendar that **runs out** (nothing repeats, or every repeat ends, so it is empty past its last day, like a season's fixture file) says so in the footer and in its Test answer. The month grid fits as many events in a day as `Layout` (in `calendar.py`) counts from the page and text size: the CSS in `render/calendar.html` uses the same sizes, so change both together.
  The OpenWeatherMap API data source (`python/datasources/openweathermap_api/`, asked by the Weather pages and the Weather Overlay) is the first with an API key of its own (`writeOnly`, with a `link` to the sign-up page) and reads the device's `location` from the **system** settings: a missing one or a missing key is a `PermanentError` that tells the user where to set it. A key that rides in the address (OpenWeatherMap's `appid`) must not reach a log: `openweathermap_api.py` hides it in the `httpx` log lines, and its failures say what happened, never the address.
  **A Generated Image is a master that chooses its parts** (`python/datasources/ai_image/`, #324 and after): its `textSource` and `imageSource` are `schema` fields whose lookups ask for the capabilities `data-ai-text` and `data-ai-image`, so the text of one provider can go with the picture of another. The parts (`openai-text`, `openai-image`; contracts `AiTextApi` / `AiImageApi` in `python/datasources/contracts/ai.py`) are API data sources asked with `dsec.use(chosen, AiImageApi)`; each `uses` its **provider** (`openai-api`), the API data source that holds the key, keeps the model list (`modelsCacheHours`, the settings' revision in the cache name, so another key is another list) and makes the calls. **Every level's fields are in the one task content**: the server walks the choices at any depth (`chosen_sources`, `MAX_CHOICE_DEPTH` 3 in `documents.py`: defaults and validation, flat error paths), the form builds them the same way (a default that chooses a part brings the part's fields: `deepDefaults` and the `schema-change` passes in `BasicForm.vue`), and `test_item_audit` checks that a source and the parts it can choose, and the parts of two choices, share no field name. A master's code asks what the task chose, so a `schema` field stands for `uses`. An API data source chosen where a page source belongs (an `openai-image` track from before) is refused with where it went ("... is now chosen inside Generated Image"). **A settings document serves masked any value its schema does not declare** (`get_document(declared=)`): a key left by a setting that moved away is not sent as it is. The browser tests answer the provider's lookups in the browser (`page.route`), never OpenAI.
  **OpenAI asks OpenAI what the key may use** (`python/datasources/openai_api/`): the image and text model fields are URL lookups served by the provider's router (`/api/datasource/openai-api/lookups/image-models`, `/text-models`, `/qualities`; `/models` says what each image model takes; `/test` checks a key), from OpenAI's model list with the **saved** key (read on the server). The list gives only ids, so what a model takes comes from its family in `models.py`, found by the id's prefix (a dated snapshot or a new `gpt-image-*` needs no change): every GPT image model takes three fixed sizes, `gpt-image-2` and later any `WxH` (multiples of 16, 1:3 to 3:1), so the picture is asked in the panel's own shape; a quality the model lacks is the nearest one below. DALL·E is retired (a stored task says so, a `PermanentError`). Model names change every few months: never put one in a list in the descriptor, only a `default`. The SDK gets an HTTP client of ours (`openai_client`: `tls_context`, and the tests' fake internet, which answers `api.openai.com` by the key: `sk-good`, `sk-busy`, `sk-broke`, any other a 401); a failure is our words and OpenAI's error code, never its text (a 401's text quotes the key).
  **Google AI is a second provider, with the same parts** (`python/datasources/google_api/`, `google-text`, `google-image`): REST through our own client (`tls_context`, the tests' fake internet), no SDK. **The key is an AI Studio authorization key, `AQ.`** (the older `AIza` standard keys are refused: the settings field has the pattern, and the provider refuses any other before asking Google), sent **only in the `x-goog-api-key` header**: never in the address (where `AQ.` keys are refused, and logs show addresses) and never as a Bearer token. Google's errors are its status word and our sentence, never its message. **Google describes its API itself**: the discovery document (`https://generativelanguage.googleapis.com/$discovery/rest?version=v1beta`, public, no key; kept for `discoveryCacheHours`) lists the `ImageConfig` aspect ratios and sizes and the `responseModalities`; `models.read_discovery` takes an enum where the schema has one, else the values in backticks in the description, and falls back to today's values (logged) when it cannot be had, so a new ratio needs no change here. Its model list has **no output modality**, so which models draw is a rule by id (`-image`, `nano-banana`), with the limits Google documents outside the schema as exceptions (Flash Lite Image takes only `1K`, Nano Banana no `512`). The picture is asked at the discovered ratio nearest the panel's, at the size the quality asks (Auto/Low/Medium 1K, High 2K, Xhigh/Max 4K, clamped to the model). `imageModel` and `textModel` are one name for each provider's own list (`SAME_NAME_DIFFERENT`); the **fake Google** (`fake_internet.py`) keys on the header (`AQ.good`; `AQ.busy` 429; `AQ.broke` the unsupported key type), refuses a key in the address, serves the model list in two pages, and checks the ratio and size against the discovery fixture. **A write-only field's mask passes the length and pattern rules** (the stored value is checked once restored): on the form and the server alike, with a shared case in `form_rules.json`.


  The routes always answer 200 with our own words. The Calendar's Connect (`python/datasources/calendar_sources/accounts.py`) is the first user: Microsoft's device code flow and Google's code flow with PKCE (a pasted `localhost` address).
  OAuth tokens go in a file beside the settings (`tokens.json`, `_internal_save`), never in a settings document or an answer; a token belongs to the account's name *and* client ID. A refused refresh is a `PermanentError` ("Sign in ... again"). A provider's error reaches a message only as its error code, never its description.

- **A picture whose shape is not the panel's gets a blurred margin, not white bars** (`blurred_margin` in `python/utils/image_utils.py`): the whole picture, uncropped, centred on a blurred enlarged copy of itself (the blur grows with the canvas). The Image Folder, Wikipedia Picture of the Day, Newspaper and Generated Image sources use it (`enlarge=False` keeps a small picture at its size); a new image source does too. The Comic keeps its white page on purpose (a panel and its caption on paper).
- **A plugin and its data sources agree on features** (`test_layer_features`). A data source declares the layers it can serve (`layer-background`, `layer-foreground`, `layer-priority`, `layer-overlay`) and the media it makes (`media-image`, `media-list`). A plugin advertises its layer and the media it handles, and its `dataSource` lookup asks for **its layer**: Slide Show `layer-background` + `layer-foreground`, Priority Update (`priority-update`) `layer-priority`, Overlay `layer-overlay`. So a source that is only `layer-background` is never offered to a timer task, and a plugin is never offered media it cannot handle. A new source or plugin keeps the test green.
- **The feature lists say the same thing the same way** (`TestFeatureVocabulary` in `test_layer_features.py`; the words and their tooltips are in `ItemInfo.vue`). Listed in this order: what it needs (`internet`: it downloads itself; `filesystem`; `api-key`; `paid-service`), what it is (`api`: a data-only provider; `api-client`: it asks an API data source, by `uses` or by choosing AI parts, and so does not also claim `internet`, the provider downloads; `ai-provider`), what a provider supplies (its **capabilities**, `data-*`: `data-weather`, `data-ai-text`, `data-ai-image`), where it can be shown (`layer-*`), what it makes (`media-*`). **Providers and data sources** (#513, `TestCapabilities`): a provider is `api` (data only), a data source has a `layer-*`, and only a provider has a `data-*` feature; a data source names the capabilities it needs in `requires` (`"requires": ["data-weather"]`), each supplied by some provider and met by a `schema` field that chooses one or a provider it `uses`; `uses` names an id, for a vendor tie; only a provider is used. A new feature word goes in `VOCABULARY` and `ItemInfo.vue`'s tooltips. **Background or foreground**: a picture that overlays may draw on (a photograph, a generated or folder image) is `layer-background`; a page with text that must not be covered (a comic, a cover, a newspaper, a calendar) is `layer-foreground`, because overlays are drawn only over a background page. The Plugins, Data Sources and **Providers** settings tabs (a provider, `api`, is listed under Providers only, #513) show a descriptor in one table (`ItemInfo.vue`: name, id, version, enabled, description, features; for a data source what it requires and uses and whether it keeps its list; for a provider what it supplies, uses and is used by), one attribute to a row. The device's provider choices (`GET /api/lookups/providers/{capability}`) list every installed provider of the capability and name one that is not `configured` "(not set up)".

- **An API data source's client is a metered one** (`python/datasources/metering.py`, `docs/development.md`'s "API Metering", #440). It is made with `metered_client("<the descriptor's id>", ...)`, which counts every call by exact status (or why there was none), with the bytes of the bodies, per day, and `cached` / `fetch_cached` tell the same meter what the cache did (`hit`, `miss`, `stale`, `coalesced`, `revalidated`, `bypass`). A client made with `httpx.AsyncClient(` in an API source (features `api` and `internet`) fails `test_api_metering`, as one without `verify=tls_context()` fails `test_tls_context`. **Counts only: never an address, a key, a query or a body** (the id and a status code are all a count carries). The counters are in memory and written about once a minute and on quit, never per call (SD-card wear); a new kind of answer an origin gives gets its own cache setting (see "An origin's answers are kept by the data source", below), and its outcome is already counted. A new API source is on the System page's API usage card with no work of its own, and so is a source that downloads through `download_for`: the pool's client is metered with no source, and `download_for` names the data source for the length of the download (`metered_as`).
- **Enhancement is the photograph's, and the data source that returns one applies it** (`enhanced(dsec, picture)` in `python/datasources/data_source.py`, #723): the display settings' brightness, contrast, saturation and sharpness are applied to the photograph before anything is drawn over it (a caption, a page around it), so what is drawn stays on its exact inks. The display task enhances nothing, whatever layer a page is on; a page a source draws itself never goes through `enhanced`. A new source that returns a bare photograph calls it, and adds itself to `PHOTO_SOURCES` in `test_enhancement`, which fails for a source that calls it and is not listed.
- **A data source keeps its downloads in one pool, and the origin's headers decide how long** (`python/datasources/content_cache.py`, #400, `docs/development.md`'s "Kept Downloads"). A picture or feed that is fetched again and again goes through `download_for(dsec, url, default_hours=...)` (which calls `fetch_cached`), never `stream_to_buffer` directly, so it is kept in the data source's folder (`DatasourceConfigurationManager.read_blob` / `write_blob` / `delete_blob`: bytes go through `storage_files`, like the JSON) and shared by every task. A fresh download is read from disk and **nothing is sent** (no `HEAD`); an expired one is asked for with `If-None-Match` / `If-Modified-Since`; `Cache-Control` and `Expires` can shorten `contentCacheHours`, never lengthen it. The pool is capped (`contentCacheMB`) and tidied (`staleDays`, and `retain(scope, urls)` for a list that was just loaded: scoped, so another feed's pictures stay). The description is written before the bytes and a pair that disagrees in size is a miss; a file name is a hash of the address, which can carry a key. A source whose address always gives something new (a camera snapshot) keeps the default at 0.
- **A media list can outlast a visit, and the plugin that shows it keeps it** (`python/plugins/kept_list.py`, #222). The Slide Show opens the data source's list (`open_async`), shows the head, drops it and saves the rest in `plugins/slide-show/list-<hash of the slot>.json` (through its `PluginConfigurationManager`); only when nothing is left, or the list is older than the task's `refreshHours`, does it open the data source again. The **slot** is `PluginExecutionContext.slot`, the playlist's id and the track's (track ids repeat across playlists, so a track id alone is not an identity), and a slot runs one visit at a time, so there is nothing to share, lock or retry: two slots on one feed each have a list. A file carries a fingerprint (the data source, the task's settings that choose the list, the data source's settings revision), so a slot pointed at another feed starts anew. The **task** chooses `listMode` (`continue`, the default, or `restart`: a new list every visit) and `refreshHours`; the plugin's settings choose `staleDays` (a list unused that long, a deleted track's, is removed; 0 never; every file records `last_used`). The **data source** only says `"keepsList": true` in its descriptor (RSS Feed, Image Folder, Comic: every feed or folder is shown item by item until it is used up, then fetched again and started over, so new items turn up in time; no tracking of what was seen, `refreshHours` defaults to 0 = only when used up; `test_item_audit` lists the sources that are not kept): a source whose list is made fresh every time (the calendar's and the weather's pages are views of now) never is. An item is dropped once it has been shown (or failed), so a restart or cancel does not show it twice; an old list is used when the origin does not answer; a list that cannot be kept (too big, not JSON, an unwritable disk) is used from memory, so a slide is never lost to the disk. Another plugin that shows a list uses `open_list`. **A data source is called from several threads at once** (`open_async` and `render_async` run on the playlist layer's loop and the timer layer's, and for the settings routes' tests): it keeps no mutable state on the instance, or guards it; its files go through the configuration manager, whose objects lock and check the revision.
- **The generators' system prompts are the Master Prompts, a device-wide settings document** (`master-prompts`, its own Settings tab; #271): `inventInstructions`, `inventRequest`, `rewriteInstructions`, `rewriteRequest` and `canvas`, read by `python/datasources/ai/prompt.py` (`master_prompts`, `rewrite_request`, `with_canvas`) for the Generated Image and its image parts; nothing is hard-coded in Python. **The factory text is the `default` of the schema shipped in the NVE** (`python/storage/schemas/master-prompts.json`): a new storage is seeded with it, `GET /api/settings/{name}/defaults` serves it (`ConfigurationManager.shipped_settings`, from the NVE and not the stored schema or document), and the form's "Restore default" (a field) and "Restore defaults" (the tab) put it into the form for the user to save or not; a value missing or empty reads as the factory text. A new prompt is a new property in that schema (and its default). **A text's fields** (`{name}`, `{{` and `}}` for a brace; `python/utils/prompt_tokens.py`, `PromptTokens.ts`): a string property with `tokens: [{ name, description }]` may use only those names (any other is "Unknown field {name}" on the form and from the server, a shared case in `form_rules.json`), and the form lists them under the field. **Whatever supplies the values supplies that list**: a data-only source says its `tokens` (names with descriptions) and fills them, so a field is never a guess. A field with no value drops out of the text.
- **The Weather Visualizer** (`python/datasources/weather_image/`, #271) is the Generated Image with a prompt that talks about the weather, and the model of a prompt whose fields are **supplied by a capability**: the weather contract lists `tokens` (`TOKENS` in `contracts/weather.py`, names with descriptions) and fills them from any provider's `Report` (`prompt_fields`, only what is known; a field with no value is left out; `test_weather_image` checks the two agree). A task property says `"tokensFrom": ["data-weather"]` (capabilities, never a vendor's id; it also `requires` them) and the configuration manager copies the contracts' lists into its `tokens` when the descriptors are read (`_resolve_tokens`, `contracts.tokens_of`), so the form, which lists them under the field, and the server, which refuses another name, read one list whichever provider supplies the values. The generation after the prompt (rewrite by the text part, the image part, the blurred margin) is shared with the Generated Image (`ai/generate.py`). **Soft by default**: when the weather provider cannot be reached (not a `PermanentError`) the prompt is made with what is known and the picture is still drawn; a missing key or location reaches the error page. A dropped field leaves the words around it, so a prompt is best written so that it reads without any one field.
- **Comic Vine is the second API data source with a key in the address** (`python/datasources/comicvine_api/`, asked by Comic Vine Covers, `comic_vine/`, #237): the same shape as the weather (a page source `uses` an `api` source). `api_key` is hidden in the `httpx` log lines (`HideKey`), its failures are our words with the site's status code at most, and it sends a browser-like `User-Agent` (the site refuses the HTTP library's). It makes its own HTTP client (`comicvine_client`, as the Google source does) so the web app's Test route and the layers ask it the same way; the Test of a task's `series` (`test.url`) is a route of the API source's own router. A search keeps its answer for `volumeCacheHours` and a page of issues for `issuesCacheHours`; the page source picks a random page of the issue list, shuffles it, and is a kept list (`keepsList`), so each cover is shown once before the series is asked for again. Covers are portrait: `blurred_margin`, never a crop.
- **Thunderforest is the third API data source with a key in the address** (`python/datasources/thunderforest_api/` and `thunderforest_map/`, #428): the same split as Comic Vine (an `api` source holds the key, `contentCacheHours` and the kept maps and makes the Static Maps call; the page source `uses` it, holds the `places` list (a name and a `location` each) a task picks from by name, or the device's own location, and draws the map). The key is `apikey=` (hidden in the `httpx` log lines, `HideKey`), a failure is our words from `refusal(status)` and never the service's text (which quotes the key), and an `HTTPStatusError`'s text, which holds the address, is never chained. **Thunderforest's terms require the attribution on the map**: the page draws it (a solid strip, so the panel does not dither a tint), and a map is a foreground page so no overlay covers it. Only a style from `STYLES` ever reaches the address.
- **Transit is a provider and its pages, under a small quota** (#429; `python/datasources/contracts/transit.py`, `transitland_api/`, `transit/`). The contract (`TransitApi`, `data-transit`) answers a `TransitReport` for one of the provider's **My Stops** by name (`open_async(dsec, { "stop": name })`): the stop, its departures soonest first (`when` is the live estimate or the timetable's, `live` says which, `status` scheduled, cancelled, skipped or added), its alerts each once, `fetched_at`, the entry's `walk_minutes`, notes in our words and the credit; `catchable(now)` leaves out what can no longer be caught, counting the walk (a cancelled trip stays, to be struck out). One provider today, so the contract names no system setting (a second, GTFS read directly #437, adds `transitProvider`). **Transitland** keeps the key (the `apikey` header only, never the address; the fake internet refuses one in the address), My Stops (a row each: `name`, `stopKey` from the URL lookup `/lookups/stops` of the stops near the device's `location`, kept `lookupCacheHours` by the rounded point and the radius, with a Test of its own; the lookup is a `search` too, **the stop finder** (PR 6): `q` is a name, searched within `SEARCH_RADIUS` of the device (10 km, Transitland's most for a geographic query; anywhere with no location), or a key (`looks_like_key`: a Onestop ID or `<feed>:<stop_id>`), asked as `stop_key`, which is how the form names a stored stop the nearby list lacks; each kept `lookupCacheHours` by what was asked; `walkMinutes`; `routes`, a filter applied to the kept answer), and the kept answers. **The cache guards the quota, not the trigger rate**: `departuresCacheMinutes` has `minimum` 15 and a file below it is raised to it (`minutes_of`), so a stop is at most about 3,000 calls a month however fast tasks fire; the answer is kept with the moment it was asked, which the board shows as "as of". `monthlyQuota` defaults to the free plan's 5,000, and **routine refreshes stop at `routineShare` of it** (default 80%, `METER.share`), raising `QuotaUsedUp` so the kept answer serves while the lookup and Test keep the rest; the budget guard (#586) stops everything at the whole plan. **The Departure Board** (`transit`) draws by e-ink's rules: clock times, never countdowns; "as of" rounded down to 5 minutes, so an unchanged answer draws the same picture and the display skips it; live (●, with the delay) and timetable (○) told apart by a symbol as well as a colour; a route's colour in the nearest ink the panel has (`inks.nearest_ink`), the strong chip when that is the page's own; "Waiting for the clock to be set" while `ClockSync` says the clock is not set (#785). Every page and overlay of transit draws the credit (`CREDIT`, the descriptor's text: `test_credits`); an overlay has room for a word, so it carries the provider's name on its first line (`credit_name`).
  **Service Alerts** (`transit-alerts`, PR 3) is an overlay *and* a page from one source: **an Overlay task's settings name its `zone`, a Slide Show track's do not**, so `render_async` draws outlined text in the zone with one and a page without (its overlay-only and page-only fields cannot be hidden by `visibleIf`, which reads only the source's own fields, so their descriptions say which). With nothing in force the overlay is taken off (`None`). A stop's own alerts come with its departures at no cost; **`routeAlerts`** also asks `/routes?serves_stop_onestop_id=` for the alerts of every route that serves the stop, kept `alertsCacheMinutes` (30, `minimum` 15), off by default because it is a call of its own (about 1,500 a month for a stop shown around the clock), and only for a stop with a Onestop ID (a `<feed>:<stop_id>` key cannot ask it). An alert seen on several routes and stops is one (`AlertsSeen` by its key, naming them all). A consumer that needs every stop asks the contract's `stop_names`, never the provider's settings.
  **Next Departure** (`transit-overlay`, PR 4) is the overlay of one stop: a line per route and destination (`lines_of`: the catchable departures that run, grouped in the order of each group's first), `perLine` times each (2: a refresh just after one leaves still shows one), in the task's `timeStyle`, clock times both (`clock`; `leave-by`, the walk taken off). **Never a countdown** (the maintainer's rule, #429): this is not a real-time display, and "in 4 min" is wrong a minute after the refresh; a stored `countdown` reads as `clock`. A mark is a character the overlay's font has, measured as it is drawn (`fit_line` measures with PIL): `~` before a timetable time, `+3` after a late live one, never `●` or `→`, which the theme's fonts may not have. It reads the same kept answer as a board of the stop, and nothing left to catch takes it off.
  **Alert Takeover** (`transit-takeover`, PR 5) is a `layer-priority` source for the Priority Update plugin, which needs no change: `render_async` answers `None` unless an alert in force meets the task's `severity` (`severe` by default) and, when chosen, one of its `effects`, and is new. **An alert is shown once per activation** (`activation`: its key and the start of its period in force), whatever the task's rate, so a task every 15 minutes does not take the panel every 15 minutes; an alert back in a new period is shown again. The ones shown are kept by the source in memory, not stored (a restart shows one in force once more), seen again on each run and forgotten a day after they were last seen, and marked only after the page is drawn, so a takeover held back by an unset clock is still new. It draws Service Alerts' page (`transit_alerts`' render folder) with only the new alerts, and shares the stops' kept answers. The Priority Update plugin hands `render_async` the list `open_async` answered, not its item: a priority source takes either.
- **An origin's answers are kept by the data source, for all its tasks** (`python/datasources/response_cache.py`). The OpenWeatherMap API data source keeps what OpenWeatherMap answered in `datasources/openweathermap-api/cache-<hash of the question>.json` for **the time its settings give that kind of answer: one setting per kind of response** (`currentCacheHours`, default 0.5, and `forecastCacheHours`, default 6; 0 asks every time; neither cuts the other; `cached(..., setting=)`; a data source with another kind of answer gets another setting; `staleDays` removes an answer nobody used, default 30), through `cached(...)`: one task at a time asks the origin and the others wait for its answer, the old answer is used when the origin does not answer (never a `PermanentError`, so a refused key is not hidden), and a cache that cannot be read or written is no cache. The key is not part of the file name or the content. **The Calendar Sources keep what each calendar answered the same way** (`cacheHours`, default 0.25, and `staleDays` in its settings; it reads whole days and at least `MIN_READ_DAYS` so a page and an overlay of the same days share an answer). The Reminder Overlay (#158) asks it (`dsec.provide(CalendarApi)`), on demand, from the overlay task's own trigger: nothing runs between runs. Its `calendars`, and the pages', are chosen from the **provider's** list: a `settings` lookup with `"from": "<data source id or capability>"` reads another data source's list, and `"from": "data-calendar"` is the device's provider of it (`from_source` in `documents.py`: the system setting `calendarProvider` when it names an installed provider, else the only one; the lookup route and the task's validation do it; `test_web_api` checks the list). **A data source says which others it uses** (`"uses": [ids]` in its descriptor) and asks them with `dsec.use(id, Class)` (the source and the context to ask it with; a source that is not loaded is a `PermanentError` in our words): `test_item_audit` checks the ids exist, no cycle, and that the descriptor says `uses` exactly when the code asks (`use` / `context_for`); the form warns under the data source field when a chosen source's `uses` is not on the device (a disabled source is not loaded; `DataSourceUses.ts`). **A data source that needs another's data asks that data source**, never its origin (#157): it gets it from the `DataSourceManager` by its id and asks it with `dsec.context_for(other)` (both through `use`), a context whose settings and files are the other's (opened by its id). So the settings, the cache and its lock are shared, not copied, and a page and an overlay of the same hours make one call.
  **The data of an origin is an API data source** (`DataSourceApi` in `python/datasources/data_source.py`): `open_async(dsec, params)` answers the origin's data for `params`, possibly a kept answer, and it **renders nothing** (no `MediaRenderAsync`). Its descriptor has the `api` feature and no `layer-*` or `media-*` one, so no plugin offers it; it holds the origin's settings (key, kept times) and another source `uses` it or requires what it supplies (`test_layer_features`). **A provider operates on a contract** (#513, `python/datasources/contracts/`): each capability (`data-*`) has one, a `ProviderContract` subclass with the data it answers (`WeatherApi` and `Report`, `AiTextApi`, `AiImageApi`) and, where a prompt reads it, its `tokens`; a provider implements it, and a consumer imports only `contracts` (`test_layer_features` fails on an import of a provider's module the consumer does not `use`). A consumer asks **`dsec.provide(Contract)`**, which chooses among the loaded providers: the device's (the contract's system setting, `weatherProvider`) when it is `configured` (its settings are complete, never its last call), the only one configured, the device's anyway, the only one there is (so its own error says what to set), else a `PermanentError` naming the capability; `GET /api/lookups/providers/{capability}` lists the choices. **OpenWeatherMap is the model**: `open_async(dsec, { "needs": ["current", "forecast"] })` answers a `Report`; the Weather pages, the Weather Overlay and the Weather Visualizer only draw it, and its settings problems reach them in its words. `uses` stays for a vendor tie (a part and its key holder, a map and Thunderforest's styles). **A weather report is SI** (Celsius, metres per second): the units a person reads are the device's, never a provider's (system settings `units`, the master: auto, metric or imperial, and `temperatureUnit` / `speedUnit`, each overriding it for its kind, so units may be mixed; `units_of` / `device_units` in `contracts/weather.py`), applied by whatever shows the report (a page, the overlay, the prompt fields). A new kind of measurement a page shows gets its own override setting. **Open-Meteo is the second weather provider** (`python/datasources/open_meteo_api/`, #513 phase 5): no key, so it is set up as installed and a new device has weather at once; one call (`timeformat=unixtime`, `wind_speed_unit=ms`) fills the same `Report`, its WMO codes mapped to OpenWeatherMap's icon groups (`WMO` in `open_meteo_api.py`; the contract's icon codes are OpenWeatherMap's). Free for non-commercial use (a hobby device), data CC BY 4.0: **a report carries its provider's credit** (`Report.credit`), which the Weather pages draw (never a provider's name in a template); an overlay has no room for it (a longer line shrinks the whole overlay, its icon too), so the pages and the Credits carry it. With OpenWeatherMap's key set as well, two providers are set up and the device must choose (`weatherProvider`). **Settings that move to another data source** go through `SETTINGS_MOVES` in `configuration_manager.py` (once, in `upgrade_settings`, logged by key name): the values are copied and **removed from the old document**, whose schema no longer marks a key write-only, so the settings route would otherwise send it as it is.
- **Every credit is in one list** (the **Credits**, the Help drawer's last section, `CreditsList.vue`, asked for from `GET /api/credits` when it is first opened; `python/web/credits.py`, #534), never spread over descriptions and the drawer's other sections. Whoever downloads says whose data it is: a descriptor with `internet` declares `"credit": { "text", "license"?, "url"? }` (an `https` address), unless it only reads the user's own addresses (`USERS_OWN`, with the reason); a font we ship is credited in `FONT_AUTHORS` (and `NOTICE`); other software by others the device or the app carries is in `SOFTWARE`. `test_credits` checks all three. Only what a service's terms ask to be next to its data is also on the panel or the map: the weather provider's footer (`Report.credit`) and the Thunderforest strip, each its descriptor's `text` from one constant (`test_credits` compares them), and the map picker's OpenStreetMap attribution. **A free public service is used by its usage policy**: the map picker's tiles come from `tile.openstreetmap.org`, and its address search (Nominatim, `AddressSearch.ts`) runs only on Search or Enter, never as you type, one at a time, at most once a second, every picker sharing one limit and the answers kept (#537). A new service or bundled part gets its credit in the same PR.

- **A data source's folder is its id.** `create_datasource_context` opens its settings by `ds.id`, as the settings routes do; the display name ("RSS Feed") is for people. Opening them by name read a folder that did not exist, so every list kept in settings looked empty at run time; tests with a fake settings manager could not see it.
- **The clock's faces are a catalogue, read through the configuration manager** (`python/datasources/clock/`, #694). `render/faces.json` lists the faces in the order they are offered, and the first is the descriptor's default (`test_clock` holds the two together). An `artwork` face names its PNG layers in `render/` by leaf name (a dial, an hour and a minute hand drawn pointing at 12, optional shadows); a `digital` or `words` face is drawn with PIL in the theme's inks, no antialiasing (`fontmode = "1"`; PIL's text **stroke** is antialiased whatever the mode, so the digital clock's unlit outline is a mask grown by one pixel, not a stroke). The layers are read with `cm.datasource_assets("clock")` (`DatasourceAssetsManager`: read-only, a name and never a path, the manager adds the extension), not opened from a path, and a decoded layer is cached by that manager (equal by its folder). The task's Face field is a URL lookup of `GET /api/datasource/clock/faces`, so a face added to the catalogue is offered with no change to the descriptor. The old clock was copied from a GPL project and was deleted; the word grid and the digital layout are our own.
- **The Gallery keeps the pictures worth keeping** (`python/datasources/gallery/`, #238): a data source that owns its storage (its own folder, through its `DatasourceConfigurationManager` like any other) and shows what it holds as a list (`media-list`, `keepsList`), so a picture a paid service drew can be shown again for what it cost once. **A producer reaches it with a message, not a call**: `offer_to_gallery(dsec, origin, picture, title, prompt)` (`gallery/offer.py`) sends a `GalleryOffer` addressed to the Gallery (`source_id` names the receiver, as every message of the `DataSourceManager` does), which delivers it to the source with that id and **drops it when there is none** (a disabled Gallery is not loaded), so publishing is opt-in and never an error. Offer the picture **as it was drawn** (before it is fitted or enhanced): the Gallery fits and enhances when it shows it, so today's display settings apply (`enhanced`, #723). `accept` returns at once; one worker keeps the offers in order, so a slide never waits for the disk. Today `ai/generate.py` offers (the Generated Image and the Weather Visualizer, under their own id); a new producer is one call.
  **The storage rules** (`gallery/store.py`): a picture is a binary file named by its content (`gallery-<sha256>.bin`), so it never changes under its name and the same picture twice is one; **one** index document (`gallery-index.json`) describes them, and every change is a read-modify-write under that `ConfigurationObject`'s lock (`with cob:`): the layers and the web app share one object per file (the configuration manager is the factory), so there is no lock of the Gallery's own. The bytes are written before the index names them (a crash leaves a file nobody lists, swept at the first use); the bounds (`maxPictures`, `maxMB`) drop the oldest unpinned picture first and never a pinned one. **The prefix `gallery-` is kept out of backups** (a backup holds JSON only: the pictures cannot be in it, and an index with no pictures would be wrong) and counted as kept on the System page. Do not copy `content_cache`'s habit of saving a description and then its bytes under one name: that is safe only while nothing is saved concurrently (`_keep` ignores the save's result).
  **Which pictures are offered is the task's choice**: the Generated Image and the Weather Visualizer each have `keepInGallery` (default on; `generate` offers unless it is `false`), so the person decides per task, and a Gallery that is not enabled keeps nothing whatever the tasks say. **Its routes** (`gallery/api.py`, mounted under `/api/datasource/gallery`): `GET /items` (newest first, with the totals and limits), `GET /items/{id}/image?size=thumb|full` (a JPEG, immutable: a picture never changes under its id), `PUT /items/{id}/pin`, `DELETE /items/{id}`, `POST /items` (the picture is the body, as the push API's: found by its content, at most 10 MB; kept whole as a JPEG, fitted when shown) and `POST /items/from-display` (`{ digest, title }`: keeps a picture the panel showed lately from the telemetry hub's memory, **as it was shown**, with any caption or overlay on it). An id in an address is matched against the index and never made into a path (the 404 does not echo it). The routes are plain `def`s over the same store, so they take the same index lock as the producers. `web/uploads.py` (`read_limited`) is the bounded body both the push API and the Gallery read. Every Gallery event names those routes as `changed` (`offer.CHANGED`), the way a stored file's change does, so **the page needs no listener of its own**: the cache's link sync refreshes the list. **The page** (`app/src/views/Gallery.vue`, #517) reads them through `useGallery` (a Colada query of `/items`; a change here also marks it stale at once), and its Recently shown tab shares `useRecentlyShown(link)` with the System page (the telemetry link's state, not a query); "Save to Gallery" on the System page is `useSaveShown`, which does not read the list.
  **Only a paid source keeps its pictures by itself** (the per-task switch); **any other picture is kept when the person asks** (#768): a picture source sets `MediaRenderResult.original` (the picture before it was fitted, enhanced or captioned: Museum Art, NASA, Wikipedia, Comic Vine, an Image from a Web Address, and the Generated Image's drawn picture), the Slide Show sends it with the page (`DisplayImage.original`, a `SourcePicture` naming the source), and when that page is the whole of the panel (`ImageCompositor.original`: a background with or without overlays, an override page; never one under a blend) the display keeps it beside the `shown` event as a JPEG (`keep_as_jpeg`, the Gallery's own encoder, so a paid picture saved again is a duplicate) and the hub keeps it with the panel picture (`TelemetryHub.original`); the event says only `original: true`. `POST /items/from-display` keeps the original, under the source's id, unless `asShown`. The Image Folder (the person's own files) and the Gallery set none. A new picture source sets `original=`, not more.
