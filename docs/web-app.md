# The web app

Read before changing `app/`: the build and the browser tests, how the app talks to the API and caches it, the editors, the pages (Scheduler, System, Help), the look (theme tokens, glyphs, `rem`). These rules were moved out of `AGENTS.md` unchanged; `AGENTS.md` keeps the rules that apply to every change.

- The built app uses hash routes (`/#/settings`), and Vite's default layout: `index.html` and `public/` files at the root, bundles in `assets/`. The bundles are served `immutable` (their names carry a hash), everything else `no-cache` (`_mount_web_app`): an `index.html` with only a `Last-Modified` was kept by the browser, which ran the old app after an update. A tab that was open before an update still runs the old app until it is reloaded: the next page it opens asks for a chunk the update replaced, which is a **404** (a missing file under `assets/` is never the app's page, which a browser cannot run as a module: "Failed to fetch dynamically imported module"), and the app **reloads itself once** at that page (`StaleBuild.ts`, `router.onError`; the reload is marked in `history.state`, so a broken build does not reload for ever; not on `vite:preloadError`, which fires first and does not know the route). `stale-build.spec.ts` refuses the chunk until the tab reloads (Vite preloads it, then imports it).
- **Browser tests** (`app/e2e/`, Playwright Test): `playwright.config.ts` starts real servers, each on a storage built by `scripts/e2e_storage.py` (the factory defaults plus the **synthetic** fixtures in `app/e2e/fixtures/storage`: schedules, a system settings file, a fake API key).
  No secret and none of the real test storage is involved, so they run on fork PRs. One server is open (port 8099), one requires a token (8098, `e2e-token`), and two are unclaimed devices (8097, and 8096 for the phone project: a device is claimed once).
  **Two projects** (#510 A5): `chromium` (a desktop) runs every spec, `phone` (a Pixel 7) the specs in `PHONE_SPECS`: the first steps (setup, settings, the playlist), the lookups, the location picker, and `phone.spec.ts`, which fails when a view or a settings tab scrolls sideways (the page or the view's own area) on either. **A form row is a label column beside its control** (`.field-row`, `.field-label`, `.field-title` in `src/assets/main.css`, the width a `--label-width`); below 40rem the label is a line of text above the control, so a new row of a label and a control uses those classes, never a width of its own. A view's two columns stack below 40rem too, a dialog is never wider than `95vw`, and a grid's columns are `minmax(0, 1fr)` (a bare `1fr` does not shrink below its content). They need `uv sync` and, once per Playwright version, `npx playwright install chromium` (CI does this itself). `@playwright/test` is no longer pinned to the cloud sandbox's preinstalled browser; a sandbox session installs the matching one the same way.
  `watchProblems()` in `e2e/support.ts` fails a test on any page error, console error, failed request, or HTTP error that the test did not declare, so a page that merely renders is not enough.
  Gotchas: the servers serve the **built** `app/dist`: `npx playwright test` alone runs the last build, so a build that failed (a `vue-tsc` error) leaves the old bundle under test; use `npm run e2e`, or build first. The app uses hash routes (`/#/settings`); PrimeVue option accessible names are not their text, so match options by visible text; the factory `location: null` leaves Save disabled, so the fixture sets one.
- **ESLint** (`app/eslint.config.js`, #510 A7): JavaScript's and typescript-eslint's recommended rules and Vue's `essential` set, nothing about formatting (tabs on purpose). `no-undef` is off (vue-tsc knows every name, Vite's defines too), a name starting with `_` is unused on purpose, and `no-explicit-any` is on for the form engine (`BasicForm`, `BasicFormField`, `ArrayField`, `FormDefs.ts`, `FormValidation.ts`, typed in #510 A3: a field is a `ResolvedField`, a choice of a `schema` lookup a `SchemaChoice`, an installed item a `Descriptor`, the values `FormValues`) and off elsewhere for now. Lint is clean; keep it so.
- CI: `.github/workflows/web.yaml` runs the `web` job (lint, build, unit tests) and the `e2e` job (browser tests) on pull requests and pushes to `master`. They are not required checks until the maintainer adds them to the ruleset, and neither is CodeQL: the ruleset requires `unittest` alone, so whoever merges checks the others (WORKFLOW.md steps 7 and 9). **Every Action is pinned to the commit of a release** (`uses: owner/action@<full sha> # vX.Y.Z`, the commit looked up, never guessed: an annotated tag is dereferenced to its commit) and the Dockerfile's uv image by version and digest; Dependabot (`github-actions`, `docker`) proposes the updates (#456).

- **The web app's surfaces follow the theme.** Colors in the app's own CSS are PrimeVue tokens (`var(--p-content-background)`, `--p-content-border-color`, `--p-content-hover-background`, `--p-highlight-*`, `--p-text-muted-color`), never a literal color, so dark mode and the theme presets work (the track list was a light panel in dark mode). A panel paints its own surface (`--p-content-background`), or it shows the page through it (the Activity gutter did). A test that reads a computed color catches it; layout tests do not. The weather and palette previews are the exception: they show the panel.

- **The sign-in is a dialog, not a browser prompt** (`AuthPrompt.ts`, `AuthDialog.vue`; `ApiClient.signIn` opens it on a 401). It asks what `GET /api/access` says the device needs: the setup code and a new password (`setup`), the password, or the API token. **The setup code is eight digit boxes** (`InputOtp`, #731): typing moves on to the next, and a paste of the code as the panel shows it (`1234 5678`, spaces and all) fills them (`pasteCode`: the component alone refuses the space). A code forced with `EINK_SETUP_CODE` (the tests do) must therefore be eight digits. **The panel's QR code opens `#/claim/<digits>`** (#491; the fragment is never sent to a server): the route (`router/index.ts`) keeps the digits in `authPrompt.claim`, takes them out of the address bar at once and redirects to the home page, whose first request gets the 401 that opens the setup dialog with the boxes filled (`takeClaimCode`, once, and only for a device that asks for a setup; a claimed one just asks for its password). The person still chooses the password: nothing is claimed by arriving. **Any address that is no route goes to the home page** (the last route, `/:pathMatch(.*)*`). The device password is changed in a dialog opened from the System page's toolbar (`PasswordForm.vue`). **A sign-in loads the whole page again** (`SignedIn.ts`: `App.vue` reloads when `signInCount` moves, once every request that waited for the sign-in has been answered, so a waiting save is done first): what it showed was read before (or not at all), the storage may have changed, the device may run a newer build, and the System page starts over too. The reload is marked in `history.state` (not storage), and the reloaded page shows a success toast saying so. A browser test waits for that toast before typing into the page. Browser tests sign in with `signInWith` (`e2e/support.ts`); the third e2e server (`--require-auth`, `EINK_SETUP_CODE`) is an unclaimed device.
- **Glyphs: one set, Material Symbols** (Apache-2.0, `@material-symbols/svg-400`, outlined; #544: PrimeIcons is not installed, two sets were two looks and 0.6 MB of fonts). PrimeVue's widgets draw their own SVG icons; every glyph of ours is `<i class="mi mi-skip-next">`, or `icon="mi mi-stop"` in any PrimeVue icon slot (the class is the name with hyphens). `.mi` is an inline-block in the text color with the glyph as a CSS mask, 1rem square whatever the font size around it (`--mi-size` changes it: `style="--mi-size: 1.5rem"`), injected by `installMaterialIcons()` in `main.ts`. Each glyph is imported by name in `app/src/components/MaterialIcons.ts` (the package has ~7,800 and only the listed ones reach the bundle; a name that is a reserved word, `delete`, `public`, is imported as another and listed as its own); never the whole font or a CDN (the device may have no internet). `MaterialIcons.test.ts` fails on a `mi-*` class that is not in the table (it would draw nothing) and on any PrimeIcons class. Choose the glyph for what the button does, not the old shape: Material has more (`playlist_add` for a new playlist, `my_location` for Locate Me, `settings_backup_restore` for Restore default). Material draws inside a margin, so a glyph that is small in itself (`stop`) looks small: make it bigger with `--mi-size`.
- **No `em` anywhere: CSS is in `rem`** (the web app, and the pages rendered for the panel, `python/**/render/*.html`). An `em` follows the font size of whatever holds the element, so the same glyph or margin comes out a different size in each place (the gutter's glyph shrank with every nested `em`); `rem` is the same everywhere. A rendered page puts its computed size on `html { font-size: ... }` (the weather page's, the calendar's `font_px`), so `1rem` is the page's size, and where an element's own size varies a custom property holds it (`--fs`, the weather table's `--u` and `--p`) and its lengths are `calc(k * var(--fs))`. Check a conversion by rendering the pages before and after and comparing the pixels (the render tests write them to `.test-output`).

- **The web API is typed from the server's OpenAPI document** (#590). `scripts/export_openapi.py` builds the app as the server does (core routers and every enabled plugin's and data source's own) and writes `app/src/api/openapi.json`; `openapi-typescript` generates `app/src/api/schema.d.ts` from it; both are committed, and `cd app && npm run api` regenerates both. **Changing a route or its models means running it**: `test_openapi_document` (Python) and `schema.test.ts` (Vitest) fail on a stale file. New code calls `api.get("/api/...")` / `api.put(path, { path: {...} }, body)` from `src/api/client.ts` (through `ApiClient`, so sign-in and errors are as before): a path that is not the server's, or a missing path parameter, is a build error, and the answer has the route's declared type. A route declares its answer with `**answers(Model)`, an `Answer` (`python/web/openapi.py`), **only a model whose fields are ours and fixed**: FastAPI drops every field a response model does not name, so a settings document, a schedule or a descriptor (keys only its descriptor knows) never gets a closed one. An `Answer` refuses a field it does not name (the route fails in its own tests instead of losing the field: a field added to an answer is added to its model), and a field the route leaves out stays out of the answer, not `null`. A body the route reads itself is described with `openapi_extra=json_body(Model)`, so its checks keep their own words and paths. An answer that carries what a person may have written into a file (a schedule: one odd value must not fail the whole list) or keys only a descriptor knows (a settings document, the descriptor lists, as open models) is `described(Model)` instead: the document names the model and nothing is checked or dropped at run time, so a test validates the real answers against it (`TestDescribedAnswers`, `TestDescribedSettings`). The web app reads a descriptor as `FormDefs.ts`'s `Descriptor` (or `PluginDef`), which `DescriptorSchema.test` holds to every descriptor. Every route has its answer typed except the telemetry events (their kinds are the hub's), the device schemas (JSON Schema files) and the AI providers' `/models` (read by no page). **A route a descriptor names** (a Test, `test.url`; a row action, `items.action.url` and its `/start`, `/continue`, `/poll`; a URL lookup) is called by the form by that address, so it cannot be typed by path: it declares the shared answer (`**test_route()`, `**row_step_route()`, `**answers(list[Choice])` in `python/web/openapi.py`), the components read that generated type (`TestAnswer`, `RowStep`), and `TestDescriptorAddresses` fails for an address of any descriptor or shipped schema that is not such a route. `SettingsForm` is given a `target` (a device document by name, or a plugin's or data source's settings), never an address.
- **Server data that more than one view or form reads is the cache's** (`app/src/api/resources.ts`, Pinia Colada, #549): its key is the route's path, so the server's `changed` paths (the telemetry link's `config-changed` and `restore`, opened once by `App.vue`) mark what they cover stale, and an open page shows a change made elsewhere (another tab, the CLI, a hand edit, a restore) without a reload. What is installed is `useCatalog()` (never `provide`/`inject` under a string key: a view that forgot one gave the form an empty list), a form's lookups are followed (`followResource`, so a provider set up elsewhere changes the choices) or read (`readResource`) through it. **Edit state is never the cache's**: an editor copies what it loads (the editor machine owns the draft), so a change from elsewhere cannot overwrite what a person is typing, and a 409 is the machine's to resolve. A composable that uses the cache runs in its test inside `inApp()` (an app with Pinia and the cache). **A view's own reads go through it too, followed while shown** (`followResource` / `readResource` with the typed call as `query`, keyed by the address with its query: the Scheduler's window and its task documents, the playlist page's list of playlists; an editor's own load stays a direct call, the server's answer now), and **what the page itself saved is marked stale at once** (`changedHere`), so a read after its own save is never the old answer. **The history the link opens with is acted on once**: its `changed` paths are collected and invalidated together after the burst (`REPLAY_SETTLE_MS`), since a change between a page's load and its link's opening is in it; that costs one fetch of what may be fresh already. A fetch replaced while under way (a change invalidated it) is answered by the one that replaced it (`readResource` waits for it), and a path another one covers is not invalidated twice. A test that changes a stored file and puts it back waits until the server reads it again (the watcher's event evicts the cached document): the next spec loads it.
- **A view's data lives in a composable** (`app/src/composables/use*.ts`, #510 A6): the loading, the saving and the editing state, with every API call, are a `use...()` function that returns refs and operations; the view keeps its template, its dialogs, the form instance and the toasts. What goes wrong is told through a `notify(severity, detail)` callback (the view turns it into a toast), and what needs the form (a 422 on a field) is handed in as a function, so the composable runs without a component. Its test (`use*.test.ts`) stands in for the API with `vi.mock("../api/client")`; a shared service it uses (the telemetry link, the transport) is an option that defaults to the shared one (`useSystem(notify, { link, transport })`), so a test passes a fake. A timer the page needs (polling, the midnight check) is started and stopped by the view, which calls the composable's `start`/`stop` or `checkDay`. `usePlaylists`, `useSchedule`, `useSettings` (and `useThemePreview`) and `useSystem` are the four.
- **An editor's cycle is one state machine** (`app/src/composables/editorMachine.ts`, `useEditor.ts`, #550): load, edit, save, conflict, discard, leave. The form reports (`validate`, `submit`), the editor decides; the document stays with the editor, which tells the machine what happened (`values`, `edit`, `loaded`) and asks it to load or save (`useEditor` runs them and sends the outcome). **Unsaved is a comparison**: the values' key (`valuesKey`: unset is missing, `_`-keys left out) against the baseline, the first values the form reports after a load (a form fills in defaults and masks as it opens), so an edit put back is clean; an edit that cannot be compared (`edit`) is unsaved until saved or discarded. **A save needs a change**: in `clean` the machine refuses `SAVE` for a stored document (it has a revision), so every editor's save button starts disabled; only a document not stored yet is saved as it opened (created from its defaults). Leaving asks when `hasUnsaved` (the `unsaved` tag). A 409 is a conflict: keeping mine takes the server's revision from the 409, so the next save is not refused again, and taking theirs loads. **A loaded document is shown after the machine is told** (`load` answers `{ rev, show }`), or its first values would not be the baseline. The machine is pure (no invoked actors), so `editorMachine.test.ts` walks every path `@xstate/graph` finds and checks the rules at each step; a new state or event is added to its `EVENTS`. A revision that changes under the edits (a playlist renamed on its own) is `revised`, which leaves what is unsaved as it was. `SettingsForm`, `usePlaylists` (the playlist's values are its tracks: one moved and moved back is no change, and Discard puts back the copy it loaded) and `useSchedule` (one task dialog at a time; a fresh form for every task shown, `formKey`, so its first values are that task's) use it; a delete's 409 is a notice with Reload only, not the machine's conflict. **An editor follows its document** (`useEditor`'s `follow`: the address and how to read the stored revision): a `changed` path of the telemetry link that covers the address, a `gap` or the link coming back makes it ask for the stored revision, and only one that is not its own is a change (the watcher reports the editor's own saves too, and the replayed history is checked as well, since a save between the load and the link's opening is in it). With nothing unsaved the document is loaded again; with edits it is `stale` (still `unsaved`): the banner "Changed elsewhere" offers Reload or Keep editing (unsaved until saved or discarded), and a save then goes over the loaded revision, so the 409 asks whether to overwrite. **Work the machine does not compare is `held`** (`follow.held`: the playlist's draft, or a track edited and not applied, which the page tells as `trackPending`): a load would drop it, so a change elsewhere is stale then too. `SettingsForm`, the playlist (the selected track stays selected by its id) and the Scheduler's task dialog (a stored task; a new one follows nothing) follow. A browser test that changes a stored file and opens a page next waits until the server serves it (`untilServed`), or the page loads the old copy and then hears of the new one.
- **Web app, schedules.** The Scheduler shows a **day**, a **week** or a **list** (each task once, its next run and runs in that week), from an offset in days from today (`SchedulerView.ts`; the list also has each task's *Run At Startup*): a week is the seven days from today's weekday, not a calendar week, and nothing before today is shown (Back stops there). A later window is asked for with `start=YYYY-MM-DD&days=` (today is the server's own). `Scheduler.vue` saves one task at a time (see the editors above for playlists) (`PUT /api/schedule/timer/{doc}/items/{id}`, `POST .../items` for a new one, `DELETE ...?rev=`); a task carries the document id and its `_rev` from the render response, a 409 offers Reload/Overwrite, a 422 for `task.content.<field>` shows on that field. A stored task can be saved once it differs from what the dialog first showed; closing the dialog with its own close button or Escape, or leaving the page, asks while it does (Cancel is "close without saving"). The fixture timer tasks must stay valid for the plugin descriptors (the server validates a `PUT`).

- **The Help drawer says how to use the app, and is kept true** (`app/src/components/HelpDrawer.vue`, opened by the toolbar's help button; a PrimeVue `Drawer` from the right, `help.spec.ts`): the first steps, the pages, how a picture reaches the panel (layers), play/stop/next, API keys, safety, what to do when something is wrong, and how to set up the data sources that need it (weather, calendars and their sign-ins, generated pictures). A change to a page, a toolbar command, a layer rule, a data source's settings or a Pi command that the drawer mentions changes the drawer in the same PR; it names only what exists. **How to use the app belongs in the drawer, not the readme** (a consumer never reads the readme): every plugin and data source has its entry there, and so does every setting a consumer chooses (the panel, buttons, kept downloads, strike-outs, backups, API usage). **The readme is not documentation** (#578): it says what the project is, its known limitations and how to install a Pi (which happens before the app exists), and links to `docs/`, where everything else about the code and the Pi's commands goes. Both say only what is so now: no "used to", "moved", "now", "from before" or issue numbers (those are in git and the issues).
- **The System page is the one place that shows how the device is** (`app/src/views/System.vue`, `GET /api/system`, `python/web/system_info.py`, #390): the parts' status, the machine, a Raspberry Pi's own readings (only when `/proc/device-tree/model` says Raspberry Pi), the storage by plugin and data source, and, in the right column, two panels of their own (Now showing, Activity). Its toolbar holds the commands that open a dialog: Back up, Restore, Device password. **The playlist panel** (the right column's first card, `usePlaylistPanel.ts`) holds the transport (play/stop, next) and the playlist the layer is on, its tracks in a row that wraps with the one playing marked: where the layer is comes from `GET /api/transport` (`playlist_id`, `track_id`, the layer's `position`) and then from each `track-started` event (which carries the same ids), and the playlists are the cache's list, followed. The app's toolbar has no activity button and no transport; the page is in the left menu. **The device's state is on every page** (#520): the header's indicator (`DeviceStatusTag.vue`, `useDeviceStatus.ts`, a link to the page, not a button) says Running, Starting or Problem, or the link's state while the page cannot hear from the device, with the same words as the Device card (`deviceStateOf`, `LINK_WORDS`). It asks `GET /api/status` when the link comes up and on the start's events, never on a timer: **the Application, which runs the start, says each step** (`configured`, `configure-failed`, `running`, `waiting-for-setup`, `set-up`, sent to the hub as the configure notices are, `_startup`); the hub keeps the notices for the status and makes no events of them. Every card on the page opens and closes (`SystemCard.vue`); Storage and API usage start closed and show a line of their own (`storageLine`, `usageLine`), and which are open is not remembered (the browser stores only the theme). **The response is numbers and our own words**: no host name, address, user or path (`test_system` checks the body against the temp folder, machine and user names). The storage is counted by `ConfigurationManager.storage_usage()` (names from `_LEAF`-checked folders, sizes only), never by a caller walking folders; reads of the machine's own `/proc` and `/sys` are in `system_info.py`, which is listed in `test_storage_access` as not storage. A reading the machine cannot give (a container, Windows) is left out, never an error. The telemetry link starts after the page's first request is answered, so on a device that asks for a sign-in it is never refused first.

## Rules for backend calls and browser storage

Moved out of `AGENTS.md` unchanged; `AGENTS.md` keeps the one-line rules.

- **Web app.** All backend calls go through `ApiClient` (`apiJson`/`apiPut`); do not call `fetch` directly, since it sends the session cookie, signs in when the server asks, and surfaces the server's message.
- **The browser stores nothing but the theme** (`localStorage`, key `theme-...`); everything else lives on the server, which is trusted. Never put a token, a session, or any other state in `localStorage`, `sessionStorage`, or a script-readable cookie (CodeQL flags it as clear-text storage of sensitive information, and it is not needed).
  The API token is the one case that looks like it needs storage: it is sent once to `POST /api/session`, and the server keeps the session (`python/web/sessions.py`) behind an `HttpOnly`, `SameSite=Strict` cookie. The e2e tests assert that only the theme is stored.
  The cookie is `Secure` only when the app itself sees `https`, which it does when it serves HTTPS itself (`--ssl`); behind a TLS-terminating proxy it would see plain `http` and not mark it (forwarded headers are deliberately not trusted), which is one reason HTTPS is the app's own. There is no rate limiting on `POST /api/session`; that is a documented tradeoff for a home-network device.
